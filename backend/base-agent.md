# 베이스 에이전트 구축

## 구축 사유

가장 기본적인 설정으로 실행하는 베이스 에이전트를 구축하여, 이후 변경이 얼마나 의미 있는지 비교·탐색한다.

## 비교 조건 및 검증 데이터

- 비교 조건은 **모델과 프롬프트**이다. 실행별로 사용한 모델과 프롬프트를 기록한다.
- 현재 단계의 검증에는 **번역된 회의 20개**를 사용한다. 비교 실행에는 동일한 회의 데이터를 사용한다.
- 청크 분량은 협의 중이며, 현재 제안은 **글자 수 기준 1,000자**이다. 비교 실행 간에는 동일한 분할 설정을 사용한다.

## 베이스 에이전트 기본 흐름

1. **입력**
   - 회의 전사록(`docx`, `hwpx`, `txt`)과 메타데이터(일시, 참가자, 제목)를 받는다.

2. **기계적 분할**
   - 전사록을 글자 수 기준 1,000자 단위로 나눈다(협의 전 잠정 기준).
   - 마지막에 남은 1,000자 미만의 내용도 청크로 포함한다.

3. **독립 추출**
   - 동일한 청크들을 요약 에이전트와 액션 추출 에이전트에 각각 전달한다.
   - 두 에이전트는 서로의 출력에 의존하지 않는다.

4. **청크별 처리**
   - 요약 에이전트: [summary_base.md](summary_base.md)를 참고하여 각 청크를 요약하고 저장한다.
   - 액션 추출 에이전트: [action-extract_base.md](action-extract_base.md) 정의된 유형에 따라 각 청크의 액션 아이템을 추출한다.
   - 액션 항목은 `유형`, `내용`, `담당자`, `기한`, `원문근거`로 구성한다.
   - 담당자와 기한이 명시되지 않은 경우 각각 `미정`으로 반환한다.
   - 액션이 없는 경우 빈 목록(`[]`)을 반환한다.

5. **병합**
   - 요약: 청크 요약들을 원문 순서대로 합쳐 최종 요약의 입력값으로 전달한다.
   - 합친 요약이 모델 입력 한도를 넘으면 명시적으로 실패 처리한다. 다단계 병합은 구현하지 않는다.
   - 액션: 청크별 액션 목록을 단순히 연결한다. 중복 제거, 변경·취소 반영 등의 추가 처리는 수행하지 않는다.

6. **최종 산출물**
   - 최종 요약문.
   - 회의에서 추출된 모든 액션을 담은 `회의명_액션.jsonl` 파일.

## 액션 출력 형식

추출 결과는 액션 객체의 목록으로 반환하고, 최종 파일에는 액션 객체 하나를 한 줄의 JSON으로 저장한다.

```json
{"유형":"업무 수행","내용":"발표자료 작성","담당자":"미정","기한":"미정","원문근거":"발표자료 작성해주세요."}
```

- `유형`은 업무 수행, 조사·검토, 수정·개선, 확인·보고, 의사결정 준비 중 하나이다.
- `원문근거`에는 해당 액션을 뒷받침하는 입력 전사록의 문구를 담는다.
- 회의 전체에 액션이 없으면 결과는 빈 목록(`[]`)이며, JSONL 파일은 액션 레코드가 없는 빈 파일로 저장한다.

## 실패 처리 및 이번 단계의 범위

- 처리 중 실패가 발생하면 해당 실행을 `실패`로 기록한다. 부분 결과를 정상 완료 결과로 취급하지 않는다.
- 실패 자체도 베이스 에이전트의 개선점으로 확인한다.
- 이번 단계에서는 별도 검증 에이전트, 자체 ReAct 로직, 자동 복구·재시도 로직을 구현하지 않는다. 해당 기능은 추후 개선 대상으로 둔다.
- 정상적으로 액션이 없어 빈 목록이 반환된 경우는 실패가 아니다.
