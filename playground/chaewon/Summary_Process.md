# 요약문 생성 자동화 프로세스

사람이 직접 작성한 것처럼 자연스럽고 신뢰도 높은 요약문 생성 자동화

-   **목표:** 정확도, 품질, 신뢰도 모두 확보
    -   틀린 것이 없는 요약문
    -   중요한 내용이 빠지지 않는 요약문
    -   핵심 요소들로만 구성된 요약문

### 요약문 생성 및 검증 목표
-   **정확성:** 원문에 없는 내용이나 잘못된 사실이 포함되지 않아야 한다.
-   **완전성:** 중요한 논의, 의견, 결정사항, 미해결 이슈가 누락되지 않아야 한다.
-   **구체성:** 핵심 내용과 논의의 맥락 및 결과가 충분히 드러나야 한다.
-   **간결성:** 핵심 요소 중심으로 구성하고 불필요한 반복을 줄여야 한다.
-   **추적 가능성:** 요약문 각 항목이 어떤 원본 발화를 근거로 생성되었는지 확인할 수 있어야 한다.
-   **부분 수정 가능성:** 전체 요약문을 다시 생성하지 않고 문제가 있는 문장만 수정할 수 있어야 한다.
-   **입력 길이 관리:** 후속 청크에 전달하는 기존 안건 정보와 프롬프트를 최소화해야 한다.

### 핵심 설계 원칙
1.  원본 발화는 `utterance_index`를 기준으로 추적한다.
2.  안건은 `agenda_id`를 기준으로 관리한다.
3.  요약문은 가능한 한 세분화된 JSON 항목으로 저장하고, 각 수정 가능한 문장에는 시스템이 고유 ID를 부여한다.
4.  LLM은 문장 고유 ID를 생성하지 않는다. LLM 출력물을 받은 뒤 코드가 ID를 생성하고, 이후 검증·수정 단계에서 해당 ID를 유지한다.
5.  추정 경계 Segment의 `Core`는 논의 항목을 생성·갱신하는 기준으로 사용하고, `Overlap`은 앞뒤 논의 맥락을 이해하는 참고 정보로 사용한다.
6.  전체 안건 이력은 시스템 내부에 저장하되, LLM에는 현재 Segment와 관련성이 높은 최소한의 안건 정보만 전달한다.
7.  구조·자료형·ID 참조 등 기계적으로 검증할 수 있는 항목은 코드로 검증하고, 의미 판단이 필요한 항목에 LLM을 활용한다.

## 0. 입력 데이터 및 용어 / 처리 원칙 / 전체 파이프라인

### 0-1. 추정 경계 Segment 데이터

주제 경계 탐지 결과인 `segments`를 요약문 생성의 기본 입력으로 사용한다.

각 Segment는 다음 영역으로 구분한다.

  --------------------------------------------------------------------------------------
  영역                   | 구성                             | 요약 프로세스에서의 역할
  ----------------------- --------------------------------- ----------------------------
  `utterances`          | 해당 Segment의 핵심 발화 (Core)    | 새로운 논의 항목 생성 및 기존 논의 갱신의 기준

  `overlap_before`      | 이전 Segment에서 가져온 발화        | 이전 논의의 맥락과 연속성 파악

  `overlap_after`       | 다음 Segment에서 가져온 이후 발화    | 논의의 맥락을 참고하여 현재 발화의 의미 파악
  --------------------------------------------------------------------------------------

**중요:** Segment는 확정된 안건 경계가 아니라 주제 경계가 추정된 구간이다. 하나의 안건이 여러 Segment에 걸쳐 이어질 수 있고, 한 Segment에 복수 안건의 내용이 포함될 수도 있다.

따라서 Segment ID와 Agenda ID를 동일한 개념으로 취급하지 않는다.

### 0-2. 발화 인덱스 기준

-   모든 발화 위치는 `utterance_index`를 사용한다.
-   인덱스는 0부터 시작한다.
-   Segment의 `start`와 `end`는 양 끝을 포함한다.
-   요약문 근거 발화 인덱스는 원본 전사문에서 해당 발화를 찾기 위한 참조값이다.
-   동일한 발화가 여러 Segment의 Overlap에 포함될 수 있으므로, 발화 인덱스를 기준으로 중복 추출을 방지한다.

### 0-3. Core와 Overlap 처리 원칙

-   **Core 발화:** 해당 Segment가 소유하는 핵심 발화다. 새로운 논의 항목을 생성하거나 기존 논의 항목을  갱신하는 주된 기준으로 사용한다.
-   **Overlap 발화:** 논의의 앞뒤 맥락을 보완하기 위한 참고 발화다. Overlap만을 근거로 이미 처리한 논의 항목을 반복 생성하지 않도록 한다.
-   단, 현재 Core 발화의 의미를 이해하거나 이전 논의와 연결하기 위해 Overlap 발화를 근거로 함께 참조할 수 있다.
-   이전 Segment에서 시작된 논의가 현재 Segment에서 결론에 도달한 경우, 기존 논의의 근거 발화와 현재 결론의 근거 발화를 함께 연결할 수 있다.

## 1. 추정 경계 청크별 1차 요약문

### 목적

각 추정 경계 Segment의 Core 발화를 중심으로 논의 내용을 추출하고, 기존 안건과의 연속성을 고려하여 안건별 요약 항목을 생성한다.

### 입력 데이터

1.  현재 Segment의 `utterances` (Core)
2.  현재 Segment의 `overlap_before`
3.  현재 Segment의 `overlap_after`
4.  현재 Segment와 관련된 기존 안건 후보 목록
5.  요약문 구조 및 태그 정의에 관한 공통 Prompt

### 안건 List 활용 목적

후속 Segment의 요약문을 생성할 때 기존 안건 List를 참고하여 다음을 판단하도록 한다.

-   현재 Segment에서 기존 안건과 관련된 발화가 등장했는가?
-   기존 안건의 논의가 계속 이어지고 있는가?
-   기존 안건과 관련된 새로운 논의가 등장했는가?
-   기존 안건의 논의가 구체화되거나 결정사항으로 발전했는가?
-   기존 안건과 별개인 새로운 안건을 생성해야 하는가?

### 안건 List 구조

안건 List에는 안건 고유 ID, 안건 제목, 해당 안건과 관련하여 확인된 발화 인덱스 범위를 저장한다.

``` json
{
  "agenda_list": [
    {
      "agenda_id": "TS3003c_a1",
      "agenda_title": "로그 보존 정책 논의",
      "evidence_utterance_indices": [60, 95]
    },
    {
      "agenda_id": "TS3003c_a2",
      "agenda_title": "서비스 배포 일정 논의",
      "evidence_utterance_indices": [110, 125]
    }
  ]
}
```

안건 고유 ID의 경우, 회의 고유 ID를 참고하여 '회의 고유 ID_agenda number'의 꼴이 될 수 있다.

`evidence_utterance_indices`의 의미는 다음과 같다.

-   첫 번째 값: 해당 안건과 관련된 최초 근거 발화 인덱스
-   두 번째 값: 해당 안건과 관련된 가장 마지막 근거 발화 인덱스
-   두 번째 값은 안건 내용의 종료 위치를 의미하지 않는다. 현재까지 해당 안건과 관련된 근거가 마지막으로 확인된 발화 위치다.
-   해당 안건이 다시 등장하면 마지막 근거 발화 인덱스를 갱신한다.

예를 들어 `[60, 95]`는 해당 안건의 근거가 60번 발화에서 처음 확인되었고, 95번 발화에서 가장 최근에 확인되었다는 의미다. 이는 60\~95번 발화가 모두 해당 안건에 속한다는 뜻은 아니다.

### 안건 List의 입력 길이 관리

전체 안건 List와 전체 근거 이력은 시스템 내부 Registry에 저장한다. 모든 안건 정보를 매번 LLM에 전달하지 않는다.

현재 Segment의 Overlap 발화 인덱스 및 Core 발화 내용을 활용하여 관련 안건 후보를 선별한 뒤, 해당 후보만 LLM 입력에 포함한다.

권장 처리 순서:

1.  현재 Segment의 Overlap 발화 인덱스와 기존 안건의 근거 인덱스 범위를 비교한다.
2.  인덱스가 연결되는 안건을 우선 후보로 선정한다.
3.  Overlap 인덱스가 직접 연결되지 않더라도, 현재 Core 발화와 기존 안건 제목·요약 정보의 의미적 유사도가 높은 안건은 추가 후보로 선정할 수 있다.
4.  선별된 후보만 LLM에 제공한다.
5.  LLM은 실제 발화 내용과 문맥을 바탕으로 기존 안건과의 연속성 및 신규 안건 여부를 판단한다.

**주의 사항**

-   인덱스 범위는 안건의 진행 이력을 빠르게 탐색하기 위한 후보 검색 정보다. 해당 범위 안의 모든 발화가 그 안건에 속한다고 단정해서는 안 된다.
-   인덱스가 겹치지 않는다고 기존 안건이 다시 등장할 가능성을 배제해서는 안 된다.
-   의미적 유사도는 후보 탐색에 활용하며, 최종적으로 같은 안건인지 여부는 발화 내용과 문맥을 기준으로 판단한다.
-   전체 근거 발화 목록이나 논의 항목별 ID를 매번 Prompt에 누적 전달하지 않는다.

### 1차 요약문 생성 구조

각 Segment에서 추출하는 결과는 가능한 한 세분화된 JSON 구조로 생성한다.

예시:

``` json
{
  "segment_id": "TS3003c_s1",
  "agendas": [
    {
      "agenda_id": "TS3003c_a1",
      "agenda_title": "로그 보존 정책 논의",
      "discussion_background": [
        {
          "text": "서비스 운영 과정에서 로그 보존 기간을 설정할 필요성이 제기됨.",
          "evidence_utterance_indices": [60, 61]
        }
      ],
      "major_discussions": [
        {
          "tag": "제안",
          "text": "원문 로그를 30일간 보존하는 방안이 제안됨.",
          "evidence_utterance_indices": [63]
        },
        {
          "tag": "반대·우려",
          "text": "30일은 장애 발생 시 원인 분석에 부족할 수 있다는 우려가 제기됨.",
          "evidence_utterance_indices": [68]
        }
      ],
      "decisions": [],
      "unresolved_issues": [],
      "next_meeting_topics": []
    }
  ]
}
```

위 예시는 구조 설명을 위한 예시이며, LLM이 `item_id`와 같은 고유 ID를 생성하지 않는다는 점에 유의한다.

각 항목별 설명은 다음과 같다.

agenda_title : 안건 제목
> 안건을 잘 나타내는 20자 이내의 명사구 형태로 작성한다.
> 안건의 경우, 작은 논의 안건 단위로 분류해서는 안된다. 큰 범주의 안건 단위로 나뉠 수 있도록 한다.
discussion_background : 논의 배경 및 근거 발화 문장 번호
> 안건이 다루어진 배경을 간략히 설명하며, 없을 경우 작성하지 않는다.
major_discussions : 주요논의 요소 및 근거 발화 문장 번호
> 소주제별 핵심 의견을 정리한다.
decisions : 결정사항 요소 및 근거 발화 문장 번호
> 논의 내 최종 결정 사항을 작성한다.
unresolved_issues : 미해결 이슈 및 근거 발화 문장 번호
> 논의 내 미정, 미해결 이슈 등을 작성한다.
next_meeting_topics : 다음 회의 후보 안건 및 근거 발화 문장 번호
> 다음에 다시 다루어야 할 주제를 명시적으로 논의 된 것을 작성한다.

### 문장별 고유 ID 부여

LLM이 JSON 결과를 반환하면, 후처리 코드가 각 수정 가능한 문장 항목에 고유 ID를 부여한다.

예시:

``` json
{
  "agenda_id": "TS3003c_a1",
  "agenda_title": "로그 보존 정책 논의",
  "major_discussions": [
    {
      "item_id": "TS3003c_a1_d1",
      "tag": "제안",
      "text": "원문 로그를 30일간 보존하는 방안이 제안됨.",
      "evidence_utterance_indices": [63]
    },
    {
      "item_id": "TS3003c_a1_d2",
      "tag": "반대·우려",
      "text": "30일은 장애 발생 시 원인 분석에 부족할 수 있다는 우려가 제기됨.",
      "evidence_utterance_indices": [68]
    }
  ]
}
```

ID 부여 원칙:

-   LLM에게 고유 ID를 생성하도록 요청하지 않는다.
-   LLM 출력 결과를 파싱한 후 코드에서 ID를 생성한다.
-   ID는 회의 ID, 안건 ID, 섹션 및 일련번호 등을 조합하여 생성할 수 있다.
-   ID는 문장 내용이나 순서가 변경되어도 가능한 한 유지한다.
-   수정·검증·병합 단계에서 동일한 문장을 식별하는 기준으로 사용한다.
-   문장 추가 시 새 ID를 부여하고, 문장 삭제 시 삭제 이력을 관리한다.
-   하나의 항목에 여러 독립적인 문장이 들어 있다면 수정 단위에 맞게 분리한다.

권장 ID 예시:

  대상             ID 예시
  ---------------- --------------------
  안건             `TS3003c_a1`
  논의 항목        `TS3003c_a1_d1`
  결정 항목        `TS3003c_a1_dec1`
  미해결 이슈      `TS3003c_a1_un1`
  다음 회의 후보   `TS3003c_a1_next1`

ID 규칙은 구현 시 일관되게 정의한다. 위 형식은 예시이며, ID의 고유성과 안정성이 우선이다.

### 논의 상태 태그

LLM은 아래의 태그 정보를 이해하여 연관된 태그를 연결하며, 임의로 새로운 태그를 생성하지 않는다.

#### 주요 논의 태그

  -----------------------------------------------------------------------
  태그                               | 의미
  ----------------------------------- -----------------------------------
  `제안`                             | 새로운 아이디어나 대안을 제시

  `반대·우려`                        | 제안에 반대하거나 위험·문제점을 제기

  `질문`                            | 설명을 요청하며, 답변되지 않았거나 별도 논의로 발전하는 질문

  `정보`                            | 사실, 현황, 수치, 진행 상황 등을 공유
  -----------------------------------------------------------------------

`동의` 태그는 사용하지 않는다. 모든 동의 발언을 개별 요약하면 회의록이 불필요하게 길어질 수 있으므로, 의미 있는 논의 변화가 있을 때만 반영한다.

#### 결정 상태 태그

  -----------------------------------------------------------------------
  태그                               | 의미
  ----------------------------------- -----------------------------------
  `결정`                             | 명시적으로 합의된 사항. 잠정 결론 포함

  `조건부 결정`                       | 특정 조건이 충족되는 경우에만 유효한 결정

  `보류`                             | 결론을 의도적으로 연기하거나 의견 차이로 결론을 내리지 못한 상태

  `공유`                             | 별도 의사결정 없이 보고·공유한 사항
  -----------------------------------------------------------------------

이후 논의에서 결정이 번복되면 이전 결정을 최종 결정으로 유지하지 않는다.

#### 미해결 이슈의 선택적 세부 태그 및 해소 조건

-   `확인 필요` : 사실/데이터/정보 확인 필요
-   `승인 필요` : 상위자나 타 부서의 승인/협의
-   `세부 미정` : 의도적 연기 / 방향은 정해졌고 일정, 수치, 범위 등 세부만 남음
-   `미논의` : 제기되었지만 시간 부족 등으로 다루지 못함

#### 후속 처리 태그

-   `결과 공유` : 확인, 검토 결과를 다음에 보고
-   `재논의` : 이번에 결론 나지 않은 안건을 다시 논의

## 2. 안건 기준 1차 병합

1번 단계의 생성 결과를 모두 JSON으로 값을 분할한 후, `[고유ID]` 즉, **안건 기준으로 내용을 병합**

### 목적

Segment별로 생성된 요약 결과를 안건 기준으로 통합하고, Overlap으로 인해 발생한 중복 논의 항목을 제거하거나 기존 항목에 연결한다.

### 처리 원칙

안건 제목의 중복만 제거해서는 안건 내부의 주요 논의·결정사항 중복을 방지할 수 없다. 따라서 안건 병합과 논의 항목 병합을 구분한다.

### 병합 처리 방법

---------------------------------------------------------------------------------
유형                                    | 처리 방식
---------------------------------------- ----------------------------------------
동일한 발화가 여러 Segment에서 추출됨       | `utterance_index` 기준으로 중복 제거

서로 다른 발화지만 동일한 논의 내용을 반복함  | 의미적 중복 후보를 확인한 뒤 하나의 항목으로 통합하고 근거 발화 연결

동일 안건에서 새로운 논의가 발생함           | 기존 안건에 새로운 논의 항목 추가

기존 제안이 이후 결정으로 발전함            | 제안과 결정을 구분하여 유지하고 결정 상태 갱신

기존 안건과 관련 있지만 독립적인 논의임      | 필요하면 별도 안건으로 분리
----------------------------------------------------------------------------------

### 처리 절차

1.  `agenda_id`를 기준으로 Segment별 결과를 그룹화한다.
2.  동일한 `evidence_utterance_indices`가 반복된 항목은 중복 후보로 분류한다.
3.  동일 발화 ID가 반복된 경우 코드로 중복을 제거한다.
4.  서로 다른 발화지만 내용이 유사한 경우 의미적 중복 후보로 분류한다.
5.  의미적 중복 여부와 논의 상태의 차이를 확인한다.
6.  동일 논의라면 기존 항목에 근거 발화 인덱스를 추가한다.
7.  새로운 논의라면 새로운 항목으로 추가한다.
8.  제안·우려·결정 등 논의 상태가 달라진 경우 서로 다른 항목으로 유지한다.

**중요:** 중복 제거를 내용 검증 Agent에 전적으로 맡기지 않는다. 1차 병합 단계에서 중복을 최대한 줄이고, 내용 검증 Agent는 남은 중복이나 잘못된 병합을 확인한다.

## 3. 내용 검증 Agent

검증 기준에 따른 수정이 필요한 특정 문장 검출 및 검증 판단 근거 생성

### 목적

병합된 안건별 요약문을 원본 회의 전사문과 대조하여 사실 오류, 근거 오류, 중요 내용 누락, 결정 상태 오류 및 요약의 깊이 부족 등을 검증한다. 이를 통해 수정이 필요한 문장에 대해 추가/삭제/병합을 요청할 수 있다.

### 검증 기준

  -----------------------------------------------------------------------
  검증 항목                           | 확인 내용
  ----------------------------------- -----------------------------------
  가짜 근거                           | 제시된 근거 발화가 실제로 존재하는가?

  원문에 없는 내용                     | 원문에서 확인할 수 없는 사실이나 해석이 추가되었는가?

  과장 및 왜곡                        | 발언의 강도나 의미가 원문보다 과장되었는가?

  결정 상태 오류                      | 제안·보류·조건부 결정·최종 결정이 잘못 구분되었거나 없는 태그를 사용했는가? 

  근거 연결 오류                      | 해당 요약문이 연결한 발화가 실제 문장의 근거가 되는가?

  중요 항목 누락                      | 중요한 논의, 우려, 결정사항, 미해결 이슈가 누락되었는가?

  중복 요약                          | 동일한 논의가 여러 문장이나 항목에 중복 기록되었는가?

  깊이 부족                           | 논의의 핵심 맥락이나 결과가 지나치게 축약되었는가?

  요약 범위                           | 생성된 요약문이 핵심을 넘어 지나치게 많은 내용을 담고있지는 않은가?
  -----------------------------------------------------------------------


### 검증 Agent 입력

- 현재 병합된 안건별 요약문
- 안건과 연관된 원본 발화 정보를 담고있는 주제 경계 청크
- 검증 기준

### 검증 Agent 출력 구조

내용 검증 Agent는 수정이 필요한 문장별로 다음 정보를 반환한다.

``` json
{
  "validation_result": "FAIL",
  "issues": [
    {
      "target_item_id": "TS3003c_a1_d1",
      "current_text": "원문 로그는 30일간 보존하기로 결정함.",
      "reason": "30일 보존은 제안 단계이며, 원문에서는 이후 90일 보존으로 결정되었음.",
      "evidence_utterance_idices": [63, 68, 95],
      "revision_instruction": "회의록 원문을 다시 확인하여 최종 결과로 수정할 것. 30일 보존은 제안으로 표현하고, 90일 보존이 최종 결정임을 구분하여 수정할 것."
    },
    {
      ...
    }
  ]
}
```

각 필드의 의미:

  필드                       설명
  -------------------------- ------------------------------------------
  `target_item_id`           수정이 필요한 문장의 고유 ID
  `current_text`             현재 요약문에 작성된 문장
  `reason`                   수정이 필요한 이유 및 검증 판단 근거
  `evidence_utterance_idices`   판단 근거가 되는 원본 발화 인덱스 목록
  `revision_instruction`     재수정 시 반영해야 할 구체적인 수정 방향

`target_item_id`는 검증 Agent가 새로 생성하는 ID가 아니라, 입력 요약문에 이미 부여된 ID를 그대로 반환하도록 한다.

### 검증 결과 처리

-   수정이 필요한 항목이 없으면 `PASS`로 처리한다.
-   수정이 필요한 항목이 있으면 `FAIL`과 함께 `issues`를 반환한다.
-   수정 대상이 아닌 항목은 변경하지 않는다.
-   근거 발화가 불충분하거나 판단이 불확실한 경우, 임의로 수정 방향을 단정하지 않고 추가 확인이 필요하다는 상태를 반환할 수 있다.

## 4. 특정 문장 재수정

### 목적

내용 검증 Agent가 반환한 피드백을 참고하여 수정이 필요한 문장만 재작성한다. 전체 안건 또는 전체 요약문을 다시 생성하지 않는다.

### 재수정 Agent 입력

-   연관된 회의록 원문 주제 경계 청크
-   이전에 생성한 요약문 문장
-   `target_item_id`
-   `current_text`
-   `reason`
-   `evidence_utterance_idices`
-   `revision_instruction`

### 재수정 Agent 출력 구조

``` json
{
  "revision_result": [
    {
      "target_item_id": "TS3003c_a1_d1",
      "revised_text": "원문 로그는 30일 보존 방안이 제안되었으나, 최종적으로 90일간 보존하기로 결정함.",
      "evidence_utterance_idices": [63, 68, 95]
    }
  ]
}
```

각 필드의 의미:

  필드                       설명
  -------------------------- -------------------------------------------
  `target_item_id`           수정 대상 문장의 기존 고유 ID
  `revised_text`             재수정한 문장
  `evidence_utterance_idices`   수정한 문장을 뒷받침하는 근거 발화 인덱스

### 수정 반영 원칙

1.  재수정 Agent는 지정된 문장만 반환한다.
2.  `target_item_id`는 기존 ID를 그대로 유지한다.
3.  시스템은 `target_item_id`로 기존 JSON 항목을 검색한다.
4.  해당 항목의 `text`와 근거 발화 인덱스만 갱신한다.
5.  수정 대상이 아닌 다른 문장과 항목은 변경하지 않는다.

### 내용 검증 및 재수정 반복

-   재수정 후 수정된 항목을 중심으로 내용 검증을 다시 수행한다.
-   수정된 항목과 의미적으로 연결된 항목은 함께 재검증할 수 있다.
-   전체 요약문을 매번 다시 검증·생성하지 않는다.
-   반복 횟수에는 상한을 둔다. (현재는 3-5회 정도로 상한을 설정하나, 평균적인 재수정 사이클 횟수를 확인하여 최종 결정한다.)
-   더 이상 재수정 피드백이 없거나, 반복 횟수 제한의 상한에 도달했을 경우, 다음 단계로 넘어간다.
-   반복 횟수 초과 후에도 해결되지 않은 항목은 `REVIEW_REQUIRED` 등 별도 상태로 표시한다.
-   검증을 통과하지 못한 항목을 정상적으로 검증된 내용처럼 처리하지 않는다.

## 5. 가독성 검증 Agent

### 목적

내용의 정확성과 완전성을 유지하면서 최종 요약문의 가독성과 자연스러움을 개선한다.

### 검증 기준

### 검증 기준

-   문장 간 연결이 자연스러운가?
-   불필요한 반복 표현이 있는가?
-   문장이 지나치게 길거나 복잡하지 않은가?
-   핵심 의미가 명확하게 전달되는가?
-   회의록에 적합한 객관적이고 일관된 문체인가?
-   논의의 주체와 대상이 혼동되지 않는가?
-   간결하게 표현하더라도 중요한 맥락이 훼손되지 않았는가?

### 가독성 검증 및 수정 원칙

-   가독성 개선을 이유로 원문에 없는 내용을 추가하지 않는다.
-   결정 상태, 논의의 강도, 조건 및 수치 등 사실관계를 변경하지 않는다.
-   수정이 필요한 문장만 대상으로 한다.
-   기존 `item_id`를 유지한다.
-   문장 수정으로 근거와 의미가 달라지면 근거 발화 연결도 다시 확인한다.
-   가독성 개선과 내용 정확성이 충돌하면 내용 정확성을 우선한다.

가독성 검증 결과도 수정 대상 ID와 수정 전후 문장, 수정 이유를 구조화하여 반환하도록 한다.

### 가독성 검증 및 재수정 반복
- 재수정 후 가독성 검증을 다시 수행한다.
- 반복 횟수에는 상한을 둔다. (현재는 3-5회 정도로 상한을 설정하나, 평균적인 재수정 사이클 횟수를 확인하여 최종 결정한다.)
- 더 이상 재수정 피드백이 없거나, 반복 횟수 제한의 상한에 도달했을 경우, 다음 단계로 넘어간다.

## 6. 구조 검증 Agent

### 목적

최종 병합 및 렌더링 단계에서 사용할 JSON 데이터가 사전에 정의한 구조와 자료형을 만족하는지 확인한다.

### 검증 방식

구조 검증은 LLM의 반복적인 판단에 의존하지 않고, 코드 기반 검증을 중심으로 수행한다.

  ---------------------------------------------------------------------------------
  검증 대상               | 확인 내용                         | 권장 방식
  ----------------------- --------------------------------- -----------------------
  JSON 파싱              | 유효한 JSON인지                    | 코드

  필수 필드              | 필수 Key가 모두 존재하는가           | JSON Schema / Pydantic

  자료형                 | 문자열, 배열, 객체 등 자료형이 맞는가 | JSON Schema / Pydantic

  허용 태그              | 정의된 태그만 사용했는가             | 코드

  ID 고유성             | `agenda_id`, `item_id` 중복 여부   |  코드

  ID 참조               | 수정 대상 ID와 근거 ID가 실제 존재하는가 | 코드

  근거 인덱스            | 원본 발화 범위 안의 인덱스인가         | 코드

  필수 섹션              | 안건별 필수 섹션이 존재하는가         | 코드

  의미적 적합성           | 내용이 적절한 섹션에 배치되었는가?    | 필요 시 LLM
  ---------------------------------------------------------------------------------

### 구조 검증 실패 시 처리

구조 검증은 다음 순서로 처리한다.

1.  최초 구조 검증을 수행한다.
2.  누락된 선택 필드, 빈 배열 등 안전하게 처리할 수 있는 오류는 코드로 보정한다.
3.  자료형이나 필드 구조 오류는 가능한 범위에서 자동 복구한다.
4.  내용 생성 자체가 잘못되어 코드로 복구할 수 없는 경우에만 LLM에 수정 요청한다.
5.  수정된 결과를 동일한 구조 검증 기준으로 재검증한다.
6.  제한된 재시도 이후에도 실패하면 정상 결과로 다음 단계에 전달하지 않고 오류 상태로 격리한다.

### 반복 횟수 초과 시 상태 예시

``` json
{
  "validation_status": "FAILED",
  "retry_count": 1,
  "error_type": "SCHEMA_VALIDATION_ERROR",
  "error_details": [
    {
      "field": "major_discussions",
      "expected": "array",
      "actual": "string"
    }
  ],
  "requires_manual_review": true
}
```

**중요:** 반복 횟수 제한은 구조 검증을 통과하지 못한 결과를 정상 결과로 인정하기 위한 조건이 아니다. 반복 횟수 초과 시에는 오류 상태로 격리하고, 구조 검증을 통과한 데이터만 다음 단계로 전달한다.

### JSON을 내부 표준으로 사용

LLM 생성부터 검증/수정/병합까지 내부 데이터는 JSON으로 관리한다.

## 7. 최종 병합 및 회의록 렌더링

### 목적

구조 검증을 통과한 안건별 요약 항목을 하나로 통합하고, 사용자에게 제공할 최종 회의록 형태로 변환한다.

### 최종 회의록 구조 예시

``` text
■ 회의 정보
  제목
  일시
  참석자
  원본 문서

■ 안건 목차
  1. ○○○ [결정 2 · 미해결 1]
  2. ○○○ [결정 0 · 미해결 2]
  3. ○○○ [결정 1 · 미해결 0]

■ 회의 결과
  · [결정] 원문 로그는 90일 보존으로 운영 [안건1]

■ 안건별 상세

  안건 제목

  논의 배경

  주요 논의
    2-1. 보존 기간
    · [제안] 원문은 30일, 요약 결과는 1년 보존 [근거 발화 연결]

  결정사항
    · [결정] 원문 로그는 90일 보존으로 운영 [근거 발화 연결]

  미해결 이슈

  다음 회의 후보 안건
```

### 최종 구성 원칙

-   **회의 정보:** 원본 파일의 메타데이터를 활용한다. 별도 LLM 생성은 필요하지 않다.
-   **안건 목차:** 안건별 상세의 안건 제목을 기반으로 생성한다. 대괄호 내부의 값은 안건별 상세 중 결정 사항과 미해결 이슈의 개수를 카운트하여 표기한다. 별도 LLM 생성은 필요하지 않다.
-   **회의 결과:** 안건별 결정사항, 미해결 이슈 및 후속 논의 후보를 취합한다. 안건별 상세 중 결정사항, 미해결 이슈, 다음 회의 후보 안건의 정보를 활용한다. 별도의 LLM 생성은 필요하지 않다.
-   **안건별 상세:** 각 안건에 속한 논의 배경, 주요 논의, 결정사항, 미해결 이슈, 다음 회의 후보 안건을 표시한다.
-   **근거 연결:** 각 요약 항목에 연결된 발화 인덱스를 활용하여 원본 전사문의 해당 발화를 UI에서 확인할 수 있도록 한다. 발화 인덱스는 내부 참조값으로 관리하며 사용자 화면에서는 표시하지 않는다.

## 8. 추가 명세

### 8-1. 생성 결과의 독립 관리

-   각 프로세스에서 생성되는 값과 요약문은 서로 독립적으로 활용하고 수정할 수 있어야 한다.
-   요약문은 가능한 한 세분화하여 저장한다. 하나의 항목을 수정할 때 다른 항목까지 함께 수정하거나 다시 생성하지 않도록, 개별 문장 또는 의미 단위별로 분리한다.
-   생성 결과는 JSON 구조로 관리한다.
-   각 수정 대상 문장 및 항목에는 고유 ID를 부여한다.
-   **고유 ID는 LLM이 생성하지 않는다.** LLM의 결과를 파싱한 후 시스템 코드에서 ID를 부여한다.
