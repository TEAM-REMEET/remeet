# 회의록 기반 Follow-up AI Agent PRD

- **문서 버전:** v0.2
- **문서 상태:** 초안
- **제품 유형:** 기업용 AI 회의 후속 업무 관리 서비스
- **개발 범위:** MVP
- **주요 사용자:** 회의 주관자, 회의 참여자, 업무 담당자, 시스템 관리자

## 1. 제품 개요

### 1.0 제품 정의

회의록 Follow-up AI Agent는 사용자가 작성한 회의록과 참고 자료를 분석하여 회의의 주요 결정사항, 논의 쟁점, 미해결 이슈 및 액션아이템을 구조화하고, 적절한 업무 담당자를 추천한 뒤 회의 주관자의 검토와 승인을 통해 실제 후속 업무로 연결하는 AI 기반 업무 지원 서비스이다.

본 서비스는 회의록의 작성과 요약을 자동화하는 데 그치지 않고, 회의에서 논의된 내용이 구체적인 실행 과제로 이어지고 지속적으로 관리될 수 있도록 지원하는 것을 목표로 한다.

### 1.1 목적

회의 전문에서 주제별 의미 단위로 분석해 안건별 논의·결정·미해결 이슈와 실행 가능한 액션아이템을 구조화한다. 담당자가 정해지지 않은 업무에는 구성원 정보를 바탕으로 후보를 추천한다. 회의 주관자는 원문 근거를 확인하고 결과를 수정·승인한다. 승인된 결과는 저장되며, 수행 결과물은 slack, mail 등 외부 협업툴 또는 개인 작업 도구로 전달하는 MCP룰 수행한다. 

제품 흐름은 **이해 → 추출 → 추천 → 검토·확정 → 축적 → 전달**이며, 세부적인 흐름은 "입력 → 전처리 → 주제 분석·청킹 → Sumarry 및 Action 추출을 위한 병렬 Agent 실행 → 작업 검증 → HITL → 확정·축적 → 전달"이다. AI는 결과를 제안하며, 사람의 승인 없이 업무를 배정하거나 외부 도구로 전송하지 않는다.

### 1.2 해결할 문제

| 문제 | 결과 |
|---|---|
| 결정사항과 논의 결과가 불명확함 | 참석자마다 회의 내용을 다르게 이해함 |
| 회의록 정리와 후속 업무 등록을 수작업으로 처리함 | 정리가 늦고 담당자의 부담이 커짐 |
| 대화 중 언급된 업무가 누락됨 | 결정이 실행되지 않음 |
| 담당자가 불명확함 | 책임 공백과 재확인이 발생함 |
| 회의 간 결정과 업무 진행이 이어지지 않음 | 같은 논의가 반복됨 |
| 액션이 메신저와 메모에 흩어짐 | 진행 상황을 파악하기 어려움 |

### 1.3 대상 사용자

- **주 사용자:** 회의 후속 정리를 맡는 PM·회의 주관자
- **협업 사용자:** 팀 리드, 액션아이템 담당자, 회의 참여자
- **관리자:** 구성원 프로필과 조직 설정을 관리하는 시스템 관리자

대표 사용자는 여러 회의의 액션을 정리하는 PM과 팀원 역량·업무량을 고려해 담당자를 정해야 하는 팀 리드다.

### 1.4 제품 목표

1. 회의 후속 업무를 정리하는 데 걸리는 시간을 줄인다.
2. 주제별 회의 분서을 통해 회의 주요 정보 누락과 맥락 혼동을 줄인다.
3. 액션아이템마다 담당자·기한의 확정 여부를 명확히 보여준다. 불명확한 값은 임의로 채우지 않고 미정으로 둔다.
4. 원문 근거와 검토 이력을 제공해 AI 결과를 확인하고 수정할 수 있게 한다.
5. 지식자산화를 통해 추후 회의 연결성을 더한다.

## 2. MVP 범위와 원칙

### 2.1 포함 범위

- 회의 전문 입력: 텍스트 붙여넣기 및 `.txt`, `.md`, `.docx`, `.hwpx` 업로드
- (사용자가) 회의 메타데이터 입력 및 구성원 선택
- 회의록 파싱·정제 및 원문 위치 보존
- 임베딩 기반 주제 전환 후보 탐지 및 LLM 기반 실제 주제 전환 여부 검증
- 검증된 주제 경계에 따른 의미 단위 청킹
- Summary 및 Action Extraction 단계 병렬 실행
- Summary 단계에서 회의 요약·결정 사항·미해결 이슈 추출
- Action Extraction 단계에서 액션아이템 및 기한 추출, 명시적 담당자, 원문 근거 연결
- Summary Validator 및 Action Validator의 병렬 수행 결과물 독립 검증 (Summary 단계 결과물은 Summary Validator, Action Extraction 단계 결과물은 Action Validator가 독립 검증)
- 구성원 프로필 관리 및 MVP용 시드 데이터
- 담당자 미지정 업무에 대해 '미지정' (human-in-loop)
- 담당자 미지정 업무의 담당자 추천을 위한 구성원 Graph RAG 구축
- 구성원의 업무 기록, 과거 수행 기록, 보유 스킬 등을 고려한 담당자 미지정 업무의 담당자 추천
- 회의 주관자의 결과 수정, 승인·거절, 수동 액션 추가
- 분석 상태·오류 관리, 결과·수정 이력 저장
- 확정 결과 저장, Markdown/JSON 내보내기, MCP 연동용 표준 Payload 생성
- Slack·이메일 공유, 캘린더 등록, Jira/Notion 이슈 생성 등 외부 MCP 실제 호출


### 2.2 후속 범위

- 액션아이템 우선순위 구조화 (human-in-loop)
- 회의별 접근 권한 및 조직 단위 데이터 격리
- 통합 업무 대시보드와 업무 상태 자동 동기화
- 과거 회의 열람 및 회의 간 액션 연결 편집
- 리마인더와 기한 임박·지연 알림

### 2.3 제품 원칙

- **사람이 최종 확정:** AI 결과는 모두 초안이며, 승인 전 확정 데이터나 외부 전송 데이터로 취급하지 않는다.
- **LLM 기반 경계 검증:** 임베딩 유사도만으로 주제 전환을 확정하지 않는다.
- **Agent 독립성:** Summary와 Action Extraction은 동일한 주제별 원문 청크·메타데이터를 입력받고 서로의 결과에 의존하지 않는다
- **개별 검증:** 두 Agent의 출력은 각각 전담 Validator가 검증한다.
- **근거 우선:** 결정사항과 액션아이템에는 원문 발화 ID를 연결한다. 근거가 없거나 불충분하면 생성하지 않거나 추정·검토 필요로 표시한다.
- **확정과 제안 구분:** 논의 중인 안건을 확정된 결정으로 표시하지 않는다.
- **미정 허용:** 담당자와 기한을 원문에 근거해 확인할 수 없으면 미정으로 둔다. 담당자 추천은 제안이며 자동 배정이 아니다.
- **고정 출력 구조:** 요약과 액션아이템은 시스템 정의 스키마에 맞춰 생성·검증한다. 사용자 정의 템플릿은 후속 범위다.

## 3. 사용자 흐름 및 기능 요구사항

### 3.1 기본 사용자 흐름

1. 사용자가 회의 제목·일시·참석자 등 메타데이터를 입력하고 전문을 업로드한다.
2. 문서를 파싱·정제하고 원문 위치를 기록한다.
3. 임베딩 유사도 분석으로 주제 전환 후보를 탐지한다.
4. LLM이 후보 전후 문맥을 검토해 실제 주제 전환 여부를 검토, 판단한다.
5. 검증된 경계를 기준으로 의미 단위 원문 청크를 생성한다.
6. 요약 및 액션아이템 추출을 실행한다. 각 작업은 병렬 실행한다. 결과에 원문 근거를 반드시 포함한다.
7. 요약 단계에서는 회의 요약과 관련하여 회의 목적, 세부 주제, 결정사항, 미해결 이슈 등을 추출한다.
8. 액션아이템 추출 단계에서는 액션아이템 및 기한 추출, 명시적 담당자, 원문 근거 연결 작업을 포함한다. 담당자가 없는 액션에 대해 '미지정'으로 둔다.
9. 요약 및 액션 아이템 추출 단계에서 수행한 결과를 Summary Validator와 Action Validator가 각 결과를 독립 검증한다.
10. 수행 단계 각각에서 관리자 에이전트가 스키마, 근거, 중복, 모순을 확인하고, 단계 수행 결과를 관리한다.
11. 구성원의 업무 기록, 협업 기록, 과거 수행 기록 등을 통해 구성원의 Graph RAG를 구축한다.
12. 액션아이템 추출 결과, 담당자 미지정 작업에 대해 Graph RAG를 통해 해당 작업에 가장 적합한 담당자를 추천한다.
13. 회의 요약 결과 및 액션아이템 추출 처리 결과를 취합해 사용자 화면에 제공한다. 
14. 회의 주관자가 리뷰 화면에서 결과를 수정·승인·거절하거나 액션을 추가한다.
15. 승인된 수행 결과를 저장한다.
16. 수행 결과를 Slack·이메일 공유, 캘린더 등록, Jira/Notion 이슈 생성 등 외부 MCP를 호출하여 전달한다.

### 3.2 입력 및 전처리

- 지원 입력: `.txt`, `.md`, `.docx`, `.hwpx`, 직접 붙여넣기. PDF와 이미지 범위는 회의 참고 자료용으로 고려하고 이에 대한 처리는 추후 결정한다.
- 메타데이터 : 회의 제목·일시·참석자(부서/알파벳)는 필수이며, 목적·참고자료는 선택 항목으로 둘 수 있다.
- 입력 검증 : 형식, 파일 크기, 손상 여부, 빈 문서, 최대 길이 및 필수 메타데이터를 검증한다.
- 원본 문서와 파싱 결과의 연결을 유지한다.
- 주제 전환 후보 탐지 : 정제된 원문을 분석 단위로 나눠 임베딩을 생성하고, 인접 구간의 의미 유사도를 비교한다. 유사도 변화가 기준을 넘는 지점을 주제 전환 후보(Candidate)로 탐지하며, 후보 위치와 점수를 보존한다.
- 주제 경계 검증 : LLM이 후보 앞뒤 문맥을 분석해 실제 주제 전환 여부를 판단하고, 판단 결과와 사유를 기록한다. 임베딩 유사도만으로 경계를 확정하지 않는다.
- 의미 단위 청킹 : 검증된 경계를 기준으로 주제별 청크를 생성한다. 각 청크에는 주제 ID, 주제명, 원문 구간 범위, 순서, 회의 메타데이터를 연결한다.
- 분할 정책 : 짧거나 단일 주제인 회의록은 불필요하게 분할하지 않는다. 긴 단일 주제는 모델 입력 한도에 맞춰 원문 연속성을 보존하며 추가 분할하고, 동일 주제 ID를 유지한다.
- 멱등성 : 동일 요청의 중복 처리와 중복 데이터 생성을 방지한다.

### 3.3 요약 및 액션아이템

요약에는 회의 개요(목적 및 목차), 안건별 논의, 결정사항, 미해결 이슈 및 다음 회의 후보 안건을 포함한다.
액션아이템은 실제 수행 업무와 단순 제안·논의를 구분하고, 업무 내용·담당자·기한·관련 안건·근거를 기록한다.

#### 3.3.1 Agent 입출력
- Summary Agent : 주제별 원문 청크·메타데이터를 입력받는다. 출력은 회의 목적, 주제별 주요 논의, 결정사항, 미해결 이슈, 다음 회의 후보 안건과 각 항목의 원문 근거다.
- Action Extraction Agent : Summary 출력이 아닌 동일한 주제별 원문 청크·메타데이터를 직접 입력받는다. 출력은 실제 수행 업무, 명시적 담당자, 기한, 관련 주제, 원문 근거, 검토 필요 여부다.
- 두 Agent는 병렬 실행하며 서로의 결과에 의존하지 않는다. 주제별 출력은 각 Validator 검증 후 회의 단위로 취합한다.

#### 3.3.2 처리 규칙
- 업무 구분 : 실제 수행 업무와 단순 제안·논의를 구분한다. 논의 중인 안건을 확정된 결정이나 업무로 표시하지 않는다.
- 명시적 담당자 : 명시적 담당자가 있는 업무는 `explicit` 출처로 표시한다. 추출한 이름은 참석자·구성원 목록과 매칭한다. 매칭에 실패하면 원문 표기를 보존하고 확인 필요로 표시한다.
- 담당자 미기재 : 담당자가 원문에 없으면 미지정으로 두며, 이 항목은 3.4 담당자 추천의 대상이 된다.
- 기한 : 상대 날짜는 회의 일시를 기준으로 절대 날짜로 변환한다. 확정할 수 없으면원문 표현을 보존하고 기한은 미정으로 둔다.
- 중복 : 여러 발화에서 같은 업무가 반복되면 Validator에서 중복을 확인하고 병합하되 근거는 모두 보존한다. 자동 병합이 불확실하면 후보로 표시한다.
- 추정 항목 : 근거가 부족하거나 암묵적으로 추출된 업무는 추정 배지와 검토 경고를 표시한다.
- 초기 상태 : AI가 만든 항목의 초기 상태는 `draft`다.

#### 3.3.3 결과 검증 및 단계 관리
- Summary Validator : 요약 항목이 원문에 근거하는지(사실성), 근거 구간 ID가 실제로 존재하는지, 스키마를 준수하는지, 미확정 논의를 결정으로 표시하지 않았는지 검증한다.
- Action Validator : 액션의 근거 존재 여부, 중복·모순(같은 업무에 상충하는 기한·담당자 등), 스키마 준수, 미정 항목의 임의 채움 여부를 검증한다.
- 두 Validator는 각 Agent의 결과만 독립 검증하며, Agent 간 교차 검증은 하지 않는다.
- 관리자 에이전트(Supervisor) : 
  -- 전 단계(전처리, 주제 분석, 추출, 검증, 추천, 전달)의 실행 순서와 상태를 관리한다. 
  -- 각 단계 출력이 다음 단계로 넘어갈 수 있는지 판단하는 품질 게이트 역할을 한다. 결과 내용 자체의 검증은 전담 Validator가 맡는다.
  -- Validator 결과에 따라 통과, 해당 단계만 제한적으로 재실행, 경고와 함께 통과, 실패 중 하나를 결정하고 그 이력을 기록한다.
  -- 스키마 검사처럼 결정적으로 판단할 수 있는 항목은 규칙적으로 처리하고, 의미 해석이 필요한 경우에만 LLM을 사용한다.

### 3.4 담당자 추천

담당자가 미정인 액션에 대해 후보 Top-3, 점수, 점수 구성, 추천 사유를 제공한다. 필수 자격·권한을 만족하지 않는 구성원은 제외한다. 정보가 부족하거나 임계 점수 미만이면 추천을 보류하고 담당자 확인이 필요하다고 표시한다.

#### 3.4.1 구성원 Graph

| 구성 | 내용 |
|---|---|
| 노드 | 구성원, 부서·역할, 스킬, 프로젝트, 과거 업무(확정 액션), 회의 |
| 관계 | 소속, 보유 스킬, 업무 수행, 협업, 프로젝트 참여, 회의 참석 |
| 데이터 소스 | 구성원 프로필*MVP 시드 데이터 포함), 업무 기록, 협업 기록, 확정된 과거 액션 |

- 구성원 Graph는 회의 분석과 별도로 사전 구축한다. 프로필 변경과 회의 확정 시점에 갱신한다.
- 회의 확정 시에는 HITL에서 승인된 담당자·업무만 수행 이력으로 반영하고, AI 추천값 자체는 반영하지 않는다.

#### 3.4.2 초기 점수식

초기 점수식은 설정값으로 두며, 확정 전에 검증한다.

```text
Score = 0.4 × 스킬 적합도
      + 0.4 × 부서·역할 적합도
      + 0.2 × 업무 여유도
```

- 정량 점수는 결정적 함수로 계산하고, LLM은 업무의 요구 스킬 추출과 추천 사유 작성을 보조한다. 
- 이번 회의에서 이미 추천된 업무량도 반영해 한 사람에게 추천이 쏠리지 않도록 한다. 
- 정보가 부족하거나 최고 점수가 임계치 미만이면 추천을 보류하고 "담당자 확인 필요"로 표시한다.
- 추천 결과는 suggested로 표시하며 자동 배정이 아니다. 회의 주관자 HITL에서 선택해야 담당자로 확정한다.
- 기본 후보군(참석자 또는 팀 전체)과 점수 가중치·임계치는 미결정 사항으로 남긴다.

### 3.5 검토 및 확정

리뷰 화면은 원문과 구조화 결과를 함께 보여주고, 결과 항목을 선택하면 연결된 발화를 하이라이트한다. 사용자는 요약과 액션의 내용을 수정하고, 담당자·기한·우선순위를 변경하고, 항목을 승인·거절하거나 누락된 액션을 수동 추가할 수 있다.

- 후보 Top-3 또는 구성원 검색을 통해 담당자를 선택한다.
- 정보가 불명확하면 담당자·기한을 미정으로 남길 수 있다.
- 근거 부족, 기한 누락, 담당자 미정, 업무 과부하 등 경고를 표시한다.
- AI 초안과 사람의 수정본을 시각적으로 구분하고 변경 전후 이력 및 승인자를 저장한다.
- 담당자 미지정 액션에는 추천 후보 Top-3와 추천 사유·근거를 함께 표시한다. 사용자는 후보를 선택하거나, 구성원을 검색해 직접 지정하거나, 미지정으로 남길 수 잇다.
- 담당자 표시는 출처별로 구분한다 : 원문 명시(explicit), AI 추천(suggested), 사용자 지정(manual).
- 최종 확정 시 상태를 `CONFIRMED`로 전환하고 확정 데이터와 연동 Payload를 저장한다. 외부 전달은 3.6절차에 따라 별도로 승인한다.
- 리뷰 중에는 결과가 확정된 업무로 오인되지 않도록 상태를 명확히 표시한다.

### 3.6 외부 도구 전달

#### 전달 범위
- CONFRMED 상태의 결과만 전달한다. 사람의 승인 없이 외부 도구로 전송하지 않는다.
- 지원 대상 (초기) : Slack 공유, 이메일 공유, 캘린더 등록, Jira/Notion 이슈 생성.

#### 전달 절차
- 사용자가 전달 대상(채널, 수신자, 캘린더, 프로젝트)과 전달 항목을 선택한다.
- 시스템이 표준 Payload를 대상별 형식으로 변환하고 미리보기를 제공한다.
- 사용자가 전송을 승인하면 MCP 도구를 호출한다.

#### 전송 안전장치
- Agent는 승인된 Payload만 전송한다. LLM이 회의록 내용을 근거로 MCP 도구를 임의 호출할 수 없도록 허용 목록(allowlist)과 승인 절차로 제한한다.
- 대상별 멱등 키(회의·항목·대상·확정 버전)로 중복 전송을 방지한다.
- 대상별 전송 상태(PENDING / SENT / FAIlED)와 외부 결과(이슈 URL, 메시지 ID 등)를 저장한다.
- 실패한 대상만 제한적으로 재시도한다.
- 외부 도구 인증은 조직 또는 사용자 단위로 연결하며, 토큰은 비밀 키 관리 정책에 따른다.
- 확정 이후 수정이 생겼을 때의 재전송 정책(기존 항목 갱신 또는 신규 생성)은 미결정 사항으로 둔다.

### 3.7 회의 목록, 상태 및 오류 처리

회의 목록은 처리 중, 검토 대기, 확정, 전달 완료, 실패 상태로 필터링한다. 분석 상태는 SSE로 전달한다. 실패 작업은 제한적으로 재시도할 수 있고, 마지막 정상 단계의 결과를 보존한다.

| 예외 상황 | 처리 |
|---|---|
| 지원하지 않는 형식 | 처리 전 차단하고 지원 조건 안내 |
| 문서 파싱 실패 | 실패 사유와 재업로드 안내 |
| 주제 전환 후보 없음 | 단일 주제 청크로 처리 |
| 주제 경계 LLM 검증 실패 | 제한된 재시도 후 기본 분할 정책 적용 또는 검토 필요 표시 |
| 과도한 청크 분할 | 최소 길이·원문 연속성 정책에 따라 재조정 |
| 개별 Validator 검증 실패 | 해당 Agent 결과 재생성 또는 경고 표시 |
| 액션아이템 없음 | 결과를 안내하고 수동 추가 기능 제공 |
| 담당자 미기재 | 임의 배정하지 않고 미지정 후 추천 단계로 전달 |
| 근거 부족 | 확정하지 않고 검토 필요로 표시 |
| MCP 전송 실패·인증 만료 | 대상별 실패 사유 표시, 재인증 안내, 실패 대상만 재시도 |
| 권한 없는 조회 | 접근 거부 및 정책에 따른 감사 기록 |
| 승인 중 데이터 충돌 | 최신 내용을 다시 불러오고 재검토 요청 |

상태 흐름은 아래와 같으며, 처리 실패 시 `FAILED`로 전환한다. `SYNCED` 상태는 Phase 2에서 MCP 외부 호출을 지원할 때 추가한다.

```
UPLOADED → PROCESSING → REVIEW_PENDING → CONFIRMED → SYNCED
                └→ FAILED                     └→ SYNC_PARTIAL (일부 대상 전송 실패)
```               

## 4. Agent 파이프라인 및 시스템 구조

### 4.1 MVP 파이프라인

1. 회의록 업로드 및 메타데이터 검증
2. 문서 파싱 및 전처리: 문장·문단 분할, 출처 위치 부여. 화자 정보는 처리하지 않음
3. 임베딩 유사도 기반 주제 전환 후보 탐지
4. LLM 기반 주제 전환 후보 검증
5. 검증된 경계에 따른 의미 단위 원문 청킹
6. 병렬 실행: Summary Agent / Action Extraction Agent (각각 원문 청크·메타데이터 입력)
7. 개별 검증: Summary Validator / Action Validator
8. 검증: 스키마·근거·중복·모순 확인
9. 담당자 추천을 위한 Graph RAG 구축 (구성원 프로필, 업무, 협업 경험 등을 고려)
10. 담당자 추천 : Action Extraction 단계에서 검증된 액션 중 미지정 항목에 대해 Graph RAG 기반 Top-3 추천
11. 회의 요약문, 담당자 추천을 포함한 Action item 매칭 결과를 REVIEW_PENDING에서 HITL 수정·승인·거절·담당자 지정
12. 확정 결과 저장 및 표준 Payload 생성
13. 전달 대상 선택 및 미리보기, 전송 승인
14. MCP 도구 호출

### 4.3 Harness 역할

Harness는 결정적 파이프라인 제어를 기본으로 한다. LLM은 의미 해석이 필요한 단계에만 사용한다.

- 전처리 → 후보 탐지 → 경계 검증 → 청킹 순서 제어
- 주제별 원문 청크와 공통 `MeetingContext` 전달
- Summary와 Action Extraction의 병렬 실행
- 각 Agent별 Validator 실행 및 검증 결과·경고 취합
- Pydantic/JSON Schema 검증, 단계·청크 단위 제한적 재시도
- 타임아웃·Rate limit 처리, 체크포인트 복구, 멱등성 보장
- 단계별 SSE 진행 상태 제공
- 임베딩·경계 검증·Agent·Validator별 프롬프트/모델 버전·토큰·지연시간·비용 Trace 기록

## 5. 비기능 요구사항

| 영역 | 요구사항 |
|---|---|
| 보안·개인정보 | 회의 자료 접근 권한을 조회·처리 전 과정에서 검증한다. 전송 구간 암호화, 저장 데이터 암호화, 비밀 키 관리, 민감 정보 로그 최소화, 보존·삭제 정책을 적용한다. 외부 모델 API 전송은 승인된 배포 정책에 따른다. |

| 프롬프트 보안 | 회의록은 데이터로 취급하고 시스템 지시와 분리한다. MVP Agent에는 외부 실행 권한을 부여하지 않는다. |
| 신뢰성 | 단계별 상태와 체크포인트를 저장하고 제한된 재시도로 복구한다. 동일 작업 재실행 시 중복 회의·액션을 만들지 않는다. 승인·저장의 정합성을 보장한다. |
| 추적성·AI 품질 | 원문 위치 → 주제 경계 후보·판단 → 청크 → Agent 출력 → 개별 Validator 결과 → HITL 수정 이력 연결 |
| 성능 | 목표 초안: 30~40 분량 회의록의 업로드부터 리뷰 진입까지 10분 이하. 최대 길이와 처리 시간은 부하 평가 후 확정한다. 일반 API P95 300ms 이하(LLM 제외)를 목표로 한다. |
| 가용성 | MVP 목표와 측정 기간·제외 조건은 운영 설계 시 확정한다. |
| 사용성 | 한국어 우선, 영어 혼용 회의록을 처리한다. 데스크톱 웹 우선으로 구성하고 원문과 결과의 상호 하이라이트 및 AI/사람 수정 구분을 제공한다. |
| 관측성·비용 | 임베딩 경계 검증·Agent별 입력·출력·토큰·지연·비용 Trace와 에러율·처리시간을 기록한다. 회의별 LLM 비용 상한은 목표를 정한 뒤 모니터링한다. |
| 확장성 | 파일 처리와 분석 모듈을 독립 구성한다. MCP·과거 회의 연결을 단계적으로 추가한다. |

구성원 Graph는 회의 분석과 별도로 사전 구축하며, 구성원 프로필 변경 및 회의 확정 시 갱신한다. Graph 저장 방식은 관계형 DB 기반 구조와 그래프 DB 도입 여부를 비교하여 결정한다.

청크별 요약·액션 결과와 Merge 결과는 원문 근거 연결을 유지해야 한다. 별도 테이블 또는 JSONB 저장 방식은 구현 단계에서 결정한다.

외부 연동 토큰 등 인증 정보는 보안 정책에 따라 관리하며, 일반 로그나 API 응답에 노출하지 않는다.

## 7. 성공 지표 및 검증

### 7.1 MVP KPI

| 구분 | 지표 | 정의 | 목표 |
|---|---|---|---|
| 청킹 | 주제 경계 탐지 Precision/Recall | 실제 주제 전환 지점과 탐지 결과의 일치 정도 | Gold Set 기반 기준 수립 |
| 청킹 | 주제 청크의 의미적 일관성 | 동일 청크 내 내용의 주제 관련성 | 정성·정량 평가 후 기준 확정 |
| 요약 | 요약 사실성 및 주요 정보 포함률 | 원문 기반 사실 정확성과 주요 정보 포함 정도 | Gold Set 기반 기준 수립 |
| 품질 | 액션 추출 Recall | 정답 액션 중 추출된 비율 | ≥ 85% |
| 품질 | 액션 추출 Precision | 추출 결과 중 유효 액션 비율 | ≥ 80% |
| 품질 | 근거 위치 일치율 | 연결된 Evidence가 원문에 실제 존재하는 비율 | 100% |
| 품질 | 담당자 추출 정확도 | 원문에 명시된 담당자를 올바르게 식별한 정도 | Gold Set으로 기준 확정 |
| 추천 | Top-3 적중률 | 적합 담당자가 추천 상위 3명에 포함된 비율 | Gold Set 기반 기준 수립 |
| 추천 | 담당자 추천 수용률 | 추천 후보 중 사용자가 최종 선택한 비율 | 내부 베타 후 확정 |
| 추천 | 추천 보류 적절성 | 정보 부족 또는 자격 미달 시 추천을 보류하는 판단의 적절성 | 평가 기준 수립 |
| 연동 | 외부 전송 성공률 | 승인된 전송 요청 중 정상 완료된 비율 | 내부 베타 후 목표 확정 |
| 연동 | 중복 전송 방지 | 동일 전송 요청의 중복 실행 방지 여부 | 테스트 통과 |
| 효율 | 리뷰 수정률 | 확정 전 수정 필드 수 / 전체 검토 필드 수 | 내부 베타 후 확정 |
| 효율 | 처리 시간 | 30~40분 분량 회의록 업로드부터 리뷰 진입까지 | P95 ≤ 600초 |
| 효율 | Follow-up 소요 시간 | 업로드부터 사용자 최종 확정까지 | 내부 베타 후 확정 |
| 사용 | 확정 완료율 | 분석 대상 중 최종 확정된 회의 비율 | 내부 베타 후 확정 |
| 비용 | 회의당 LLM 및 임베딩 처리 비용 | 회의록 1건 처리에 발생하는 모델 사용 비용 | 상한 설정 후 모니터링 |

근거 위치 일치율은 원문 구간의 존재 여부를 측정하며, 추출 결과를 실제로 뒷받침하는지는 별도의 근거 타당성 평가로 확인한다.

담당자 추천이 MVP에 포함되므로 Top-3 적중률과 추천 수용률을 MVP KPI에 포함한다.

### 7.2 검증 방법

회의 유형과 길이가 다른 테스트 데이터 또는 비식별화 자료를 활용해 Gold Set 최소 30건을 구축한다.

**평가 항목**

- 실제 주제 전환 지점과 탐지된 후보 비교
- LLM 경계 검증 전후 Precision/Recall 비교
- 주제별 청킹과 문장·문단 청킹의 성능 비교
- Summary Agent의 요약 사실성 및 정보 포함률
- Action Extraction Agent의 Precision/Recall
- 담당자·기한 추출 정확도
- 청크별 결과 Merge 과정의 정보 누락·중복 여부
- 각 Validator의 오류 탐지 및 오탐 비율
- 원문 근거의 존재 여부와 의미적 타당성
- 미정 항목을 임의로 채우는 오류율
- Graph RAG 기반 담당자 추천의 Top-3 적중률 및 추천 보류 적절성
- 추천 점수와 추천 사유의 일치 여부
- MCP 외부 전송 성공·실패·중복 방지 및 승인 절차 검증

**평가 데이터**

- QMSum: 긴 회의 맥락 이해 및 요약 평가에 활용 검토
- AMI: 회의 대화 및 액션 관련 분석에 활용 검토
- 한국어 회의 데이터: 실제 서비스 도메인과 유사한 회의록 기반 평가
- 자체 Gold Set: 주제 경계·요약·액션·담당자·기한·근거 라벨 구축
- 담당자 추천 평가 데이터: 구성원 스킬·역할·업무 이력과 적합 담당자 정답을 포함한 별도 평가 자료 구축

QMSum과 AMI는 본 서비스의 출력 스키마와 완전히 일치하지 않을 수 있으므로 부족한 정답 라벨은 별도로 구축한다. 담당자 추천 평가에는 구성원 프로필 및 업무 적합성 정보가 추가로 필요하다.

**회귀 평가**

Agent·모델·프롬프트·청킹 정책·추천 점수식 변경 시 기존 평가 데이터를 활용하여 회귀 평가를 수행한다.

Summary는 우선 파인튜닝 없이 평가하며, Action Extraction은 순정모델의 성능이 목표에 미달할 경우 파인튜닝을 검토한다.

**내부 베타 평가**

내부 베타에서는 검토 시간, 수정률, 승인률, 사용자 만족도, 담당자 추천 수용률, 외부 전송 성공률을 측정한다. 정량 목표는 베타 결과를 통해 현실성을 확인한 뒤 확정한다.

### 7.3 MVP 출시 기준

- Gold Set 기준 액션 Recall ≥ 85%, Precision ≥ 80%
- 근거 위치 일치율 100%
- 주제 경계 및 청킹 평가 기준 수립과 테스트 통과
- 30~40분 회의록 처리 P95 ≤ 600초
- 청크별 Merge 및 Agent별 Validator 동작 검증
- Graph RAG 기반 담당자 Top-3 추천 기능 동작 및 평가 기준 충족
- 담당자 추천의 근거·점수 표시 및 추천 보류 기능 검증
- MCP 외부 전송의 사용자 승인, 중복 방지, 실패 복구 기능 검증
- 기본 인증·접근 제어 및 민감 정보 보호 점검 통과
- 사용자가 결과를 수정·승인하고 승인 전후 상태와 원문 근거를 확인 가능
- 담당자가 미기재된 액션은 자동 배정하지 않고 미지정 표시
- 사용자 승인 없는 외부 전송 차단

추천 품질과 전송 성공률의 구체적인 출시 통과 수치는 평가 데이터 및 내부 베타 결과를 바탕으로 확정한다.

| S4 | HITL 확정·Payload, MCP 연동, 승인·중복 전송 방지·실패 복구, 성능·보안 점검 | 리뷰 완성, 담당자 선택, 전송 대상 선택·미리보기·승인·상태 확인 |

### 8.3 우선순위

**P0 — MVP 필수:** 회의록 입력·파싱, 임베딩 기반 주제 전환 후보 탐지, LLM 경계 검증, 의미 단위 청킹, 병렬 Summary·Action Extraction, 청크별 Merge, 개별 Validator, 원문 근거, 구성원 Graph RAG, 담당자 Top-3 추천, HITL, 확정 데이터 저장, 오류 처리, Payload 생성, MCP 기반 외부 도구 실제 호출 및 전송 상태 관리.

**P1 — MVP 이후 안정화:** 입력 형식 확장, 문서 파싱·근거 위치 표시 개선, 청킹 정책 개선, 주제 경계 탐지 임계값 최적화, 부분 재생성, 원문 하이라이트 개선, Markdown/JSON 내보내기 개선, 상세 수정 이력 및 품질 운영 기능.

**Phase 2:** 외부 연동 대상 확대, 업무 상태 자동 동기화, 필요시 리마인더와 기한 임박·지연 알림.

**Phase 3:** 과거 회의 검색, 회의 간 액션 연결·중복 검토, 지식자산화 및 통합 업무 대시보드.

**후속 검토:** 우선순위 자동 구조화, HR 연동, 모바일 앱, 담당자 추천 모델 및 Graph RAG 고도화.

| 청크별 결과 Merge 과정의 정보 누락·중복 | 요약 및 액션 결과 정확도 저하 | 원문 근거 연결 유지, 병합 전후 누락·중복 검사 |

| 담당자 미정으로 인한 후속 처리 지연 | 업무 실행 책임 확정 지연 | Graph RAG 기반 후보 추천 및 리뷰어 최종 선택 |
| Graph RAG 데이터 부족·노후화 | 부정확한 담당자 추천 | 프로필 갱신, 데이터 신뢰도 확인, 정보 부족 시 추천 보류 |
| 담당자 추천의 특정 구성원 편중 | 업무 과부하 및 불공정한 업무 배분 | 업무량 반영, 추천 분포 점검, 사람 최종 선택 |
| 추천 점수와 추천 사유 불일치 | 추천 결과 신뢰도 저하 | 점수 계산 결과와 추천 근거의 일치 여부 검증 |
| Validator 오탐·미탐 | 정상 결과 누락 또는 오류 통과 | 검증용 Gold Set 구축 및 오류 유형별 평가 |
