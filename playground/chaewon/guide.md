# GCS 전사문 기반 주제 경계 탐지 및 검증 파이프라인

## 1. GCS 전사문 처리

### 입력
- 녹음 전사문 파일: `txt`, `md`, `hwpx`, `docx`
- Metadata
  - 참가자
  - 회의 제목
  - 회의 일시

### 필요 프로세스
1. **파일 파싱**
   - `hwpx`, `docx` 파일을 파싱할 수 있는 Parser 구현
2. **전사문 전처리**
   - 발화별 순서 인덱스 추가
   - 발화 텍스트 정제

### 출력
- JSON
  - 회의록 ID
  - 녹음 텍스트
  - Metadata

---

## 2. 주제 경계 후보 탐지를 위한 전처리(청킹)

### 입력
- 1단계의 출력값(JSON)

### 필요 프로세스
1. **최적의 청킹 파라미터 도출**
   - 최적의 `chunk_size` 도출
   - 최적의 `chunk_overlap` 도출
2. **청킹 및 Metadata 추출**
   - 설정된 `chunk_size`, `chunk_overlap`을 기준으로 단순 청킹 수행
   - 청킹별 인덱스 생성
   - 청킹별 토큰 수 계산

### 출력
- `chunk_size`, `chunk_overlap`을 기준으로 생성한 단순 청킹값
- 청킹별 Metadata
  - 청킹 인덱스(`chunk_index`)
  - 토큰 수(`token_count`)

---

## 3. 주제 경계 후보 탐지

### 입력
- 2단계의 출력값(청킹값 및 Metadata)

### 필요 프로세스

#### 3.1. 임베딩 모델 탐색 및 성능 확인
- BGE-M3 임베딩 모델 탐색 및 성능 확인

#### 3.2. 유사도 비교를 위한 임베딩 방안 설계
- 청킹 전체를 임베딩하는 방식 검토
- 문장별로 임베딩하는 방식 검토
- 각 방식의 유사도 비교 및 주제 경계 탐지 성능 확인

#### 3.3. 주제 경계 검증 방안 설계
- 임베딩 유사도를 활용한 주제 경계 후보 검출 방안 고안
- 검출된 경계 후보의 실제 경계 여부를 검증하기 위한 방안 고안

### 출력
- 검출된 경계 후보의 앞뒤 발화 청킹을 JSON 구조로 전처리
- 각 경계 후보의 위치와 주변 문맥을 포함하여 이후 단계인 LLM 주제 경계 검증에 전달

#### 출력 예시 2

```text
=== [11] | [12] — 위치 11 ===
왼쪽 문맥:
[9] ‘인터페이스 콘셉트’인가요?
[10] 네, 그건 제 자료예요.
[11] 그건 당신 자료군요. 트렌드 조사도 당신 담당이고요.
오른쪽 문맥:
[12] 이건 부품 디자인입니다.
[13] 부품 디자인이요.
[15] 좋아요.

=== [17] | [18] — 위치 16 ===
왼쪽 문맥:
[15] 좋아요.
[16] 먼저 케이스는 플라스틱으로 만들 수 있다고 생각했습니다. 처음에는 플라스틱을 생각했지만, 나중에 보니 고무나 티타늄, 심지어 나무도 가능하더군요. 그러니 어떤 재료를 쓸지 결정해야 합니다. 아마 플라스틱이 가장 유력하겠죠. 적외선 송신기는 기성품을 구매하면 됩니다. 조이스틱도 사용할 경우 플라스틱이나 고무로 만들 수 있을 겁니다. 다음 슬라이드로 넘어가 주세요. ‘조사 결과’ 부분인데, 두세 장 아래에 있을 거예요.
[17] 네.
오른쪽 문맥:
[18] 제가 찾아본 결과 사용할 수 있는 배터리 방식은 세 가지입니다. 손으로 돌리는 발전기를 쓰거나, 시계에 쓰이는 운동 에너지 방식 배터리를 쓰거나, 태양광 배터리를 사용할 수 있습니다.
[19] 네, 그런데…
[20] 음…

=== [43] | [44] — 위치 39 ===
왼쪽 문맥:
[40] 비싸기도 하지 않나요?
[41] 가볍기도 하죠. 아마 비싸기도 할 겁니다.
[43] 산악자전거도 티타늄으로 만들지 않나요? 상당히 가벼운 재료니까요.
오른쪽 문맥:
[44] 궁금한 게 있는데, 지금 바로 설명하기 어려울 수도 있겠지만 단일 곡면형과 이중 곡면형의 예를 들어 주실 수 있나요?
[45] 네, 그러니까…
[46] 그림으로 그려 주실 수 있을까요? 완벽할 필요는 없어요. 두 형태의 차이를 제가 잘 이해하지 못한 것 같아서요.

=== [52] | [53] — 위치 48 ===
왼쪽 문맥:
[50] 알겠습니다.
[51] 네, 이런 식이죠. 이쪽은 곡선이 두 개 있으니 이중 곡면형이라는 뜻인 것 같습니다.
[52] 알겠습니다.
오른쪽 문맥:
[53] 물론 단일 곡면형보다 보기에는 더 좋아 보이지만, 티타늄을 사용할 수 없다는 점이 아쉽습니다. 티타늄은 괜찮은 재료니까요.
[54] 음.
[55] 버튼은 PC 마우스에 쓰이는 스크롤 휠을 사용할 수도 있습니다. 하지만 이를 사용하려면 더 비싼 칩이 필요하고, LCD까지 사용한다면 비용이 더 올라갑니다. 따라서 장단점을 따져 봐야 합니다. 이중 곡면형 컨트롤러를 고무로 만든다면 버튼도 고무로 만들 수 있습니다. 다만 요즘은 채널이 많기 때문에 숫자 키패드도 필요할 것 같습니다. 원하는 채널에 도달할 때까지 계속 스크롤하고 싶지는 않을 테니까요. 채널 번호를 알고 있다면 바로 입력할 수 있어야 합니다. 그래서 숫자 키패드는 필요하다고 생각하는데, 어떻게 생각하세요?
```

#### 출력 구조 및 검토 사항

- `boundary_position`: 경계 검출값
  - 경계 검출값을 중앙에 두고, 검출값 앞뒤의 발화를 각각 하나의 청킹으로 구성
  - 이후 단계인 LLM 주제 경계 검증을 통해 실제 주제 경계가 맞는지 판단

- 임베딩 방식
  - `direct`: 청킹 전체의 임베딩값을 활용하여 경계 검출
  - `pooled`: 문장 하나하나의 임베딩값을 활용하여 경계 검출

## 4. LLM 주제 경계 검증

### 입력
- 3단계의 출력값
- 경계 후보별 앞뒤 문맥을 묶은 JSON 데이터

### 필요 프로세스

#### 4.1. 경계 기준 설정 및 추가 검토
- 경계 검증 기준 설정 및 추가 검토
- 우선 좁은 범위의 기준부터 적용
- 경계 검증 기준 토글 참고

#### 4.2. 경계 정의 및 LLM 판정 기준

**경계 기준**

> 하나의 결론(결정·보류·이관)을 목표로 하는 논의(안건) 단위

- 의미 단위를 기준으로 주제 경계를 판단

**경계 정의**

> 주제 경계는 논의 대상, 즉 “회의 참여자가 무엇에 대해 결론을 내리려 하는가?”가 바뀌는 지점으로 정의한다.

**LLM이 경계를 검증할 때 확인할 판정 질문**

| 판정 항목 | 판정 질문 |
|---|---|
| 대상 변경 | 뒤 구간이 앞 구간과 다른 대상(다른 기능, 문서, 이슈, 일정, 의사결정 건)을 다루는가? |
| 종결 신호 | 앞 구간이 결론(결정·보류)으로 정리되었거나, “다음 안건”, “그건 그렇게 하고”와 같은 전환 표현이 존재하는가? |
| 독립 요약 가능성 | 뒤 구간을 앞 구간 내용 없이 따로 요약해도 의미가 통하는가? |

**경계 판정 규칙**

- 위 세 가지 판정 질문 중 하나라도 포함될 경우 경계로 판정

**경계에 포함되지 않는 경우**

다음과 같은 경우에는 경계로 판정해서는 안 된다.

- 같은 대상 안에서 측면만 바뀌는 경우
- 잡담 등으로 잠시 다른 이야기를 하다가 원래 논의 대상으로 돌아오는 경우
- 같은 결정에 대한 재논의나 번복이 확인되는 경우

#### 4.3. 경계 검증 근거 설계

경계의 앞과 뒤 발화를 기준으로 각각의 논의 대상을 작성하게 하여 논의 대상의 일치도를 판별한다.

**검증 결과 예시**

```json
{
  "before_subject": "베타 테스트 대상 팀 선정",
  "after_subject": "로그 보존 기간 정책",
  "shift_type": "new_agenda",
  "shift_result": true
}
```

- `before_subject`: 경계 앞 구간의 논의 대상
- `after_subject`: 경계 뒤 구간의 논의 대상
- `shift_type`: 논의 대상 변경 유형
- `shift_result`: 논의 대상 변경 여부

#### 4.4. 출력 구조 선정

다음과 같은 다양한 출력 구조를 비교하여 최적의 방법을 선정한다.

- 구조화된 JSON 스키마
  - 경계 앞뒤 논의 대상
  - 논의 대상 변경 유형
  - 논의 대상 변경 여부
- 단순 판정 구조
  - `O/X` 검증 결과
  - 검증 근거

### 출력
- LLM의 주제 경계 검증 결과
  - 경계 여부: `O/X`
  - 검증 근거
- 경계 앞뒤의 논의 대상 및 논의 대상 변경 여부를 포함하는 구조화된 결과(선택한 출력 스키마에 따름)
