# Base Test 계획서

## 1. 목적

회의 전사문을 안건별 회의록과 액션 아이템으로 정리하는 베이스 파이프라인을 구축하고, 이후 검증·수정과 오버랩 적용의 효과를 비교할 기준을 마련한다. 1차 병합 전에는 지나친 압축보다 **원문에서 중요한 내용이 빠지지 않도록 충실하게 추출하는 것**을 우선한다.

이 문서는 구현 전 계획이다. 실험 결과나 성능에 대한 수치는 포함하지 않는다.

## 2. 실험 범위와 확정 조건

- 화자 분리가 **되어 있는 전사문**과 **되어 있지 않은 전사문**을 모두 입력 대상으로 실험한다.
- 전사문 전처리는 [PR #35](https://github.com/TEAM-REMEET/remeet/pull/35)의 `load_transcript` 구조를 따른다. 현재 검증 데이터에서는 UTF-8-SIG 텍스트의 앞 3줄을 메타데이터로 읽고 이후 비어 있지 않은 각 줄을 하나의 발화로 처리해 **0부터** 발화 번호를 부여한다. 머리말 줄 수와 발화 구분 방식 등은 데이터 형식에 따른 설정이며 고정된 입력 규격이 아니다.
- 앞단 청킹에는 기존 `chunking_method/bge_distance_experiment` 실험에서 선택한 **K=0.0 / gap=400자 / span=800자** 조건을 적용한다. 최종 추출용 청크 간 오버랩은 베이스에서 사용하지 않는다.
- 청크 크기는 **문장을 보존한 약 1,000자**를 권장한다. 경계가 발화 중간에 생기면 직전 발화까지 현재 청크에 포함하고, 해당 발화는 다음 청크에서 시작한다.
- 안건·논의 추출과 액션 추출은 **독립적인 에이전트**로 실행하되 같은 청크와 동일한 입력 조건을 사용한다.
- 안건·논의 추출에는 이전 청크까지 생성된 안건 목록을 제공한다. 목록에는 우선 안건 ID와 제목만 포함한다.
- 청크별 결과를 안건 ID 기준으로 1차 병합하고, 근거와 원 청크를 이용해 내용 오류와 누락을 검토한다.
- 검증에서 오류가 발견되면 해당 결과, 원 청크와 오류 내용을 전달해 재실행한다.
- 목록형 항목에 해당 값이 없으면 빈 리스트 `[]`를 반환한다. 요약과 액션 상세 구조는 팀에서 제공할 Markdown을 확인한 뒤 확정한다.

## 3. 처리 흐름

```text
전사문 + 회의 ID 및 메타데이터
              ↓
화자 분리 여부 확인 → 전처리 및 발화 번호 생성
              ↓
임베딩 기반 잠재 경계 탐지: K=0.0 / gap=400 / span=800
              ↓
문장·발화 보존 청킹: 약 1,000자, 오버랩 없음
              ↓
청크별 동일 입력 구성: 회의 ID + 청크 + 안건 목록
              ↓
    ┌───────────────────┬──────────────────┐
    ↓                   ↓
안건·논의 추출       액션 추출
독립 에이전트        독립 에이전트
    └───────────────────┴──────────────────┘
              ↓
안건 ID 기준 1차 병합
              ↓
근거 발화 및 원 청크 대조
  ├─ 통과 → 병합 결과 저장
  └─ 오류 → 해당 결과 + 청크 + 오류 전달 → 재실행 후 재검토
```

안건 목록이 앞선 청크의 결과로 갱신되므로 청크 간 처리는 순서대로 진행한다. 두 에이전트의 실행 순서 또는 병렬 실행 가능 여부는 공통 입력과 안건 ID 확정 방식을 정한 뒤 확정한다.

## 4. 단계별 입출력

### 4.1 전사문 전처리

**입력**

- 회의 ID, 원본 전사문, 제공된 회의 메타데이터
- 화자 분리 여부가 확인된 입력 또는 분리되지 않은 입력

**처리**

1. PR의 `load_transcript` 흐름을 따른다. 현재 검증 데이터의 설정에서는 TXT 파일을 UTF-8-SIG로 읽고 줄 단위로 분리한다.
2. 현재 검증 데이터에서는 앞 세 줄을 머리말로 취급하고, 각 줄을 첫 번째 `:` 기준으로 나눠 공백을 제거한 키와 값을 메타데이터로 저장한다. 머리말은 발화 목록에서 제외한다.
3. 현재 검증 데이터에서는 이후 비어 있지 않은 줄을 앞뒤 공백 제거 후 각각 하나의 발화로 처리하고, 원래 순서대로 `utterance_index`를 **0부터** 생성한다.
4. 회의 ID는 입력 파일의 확장자를 제외한 이름으로 사용하고, `meeting_id`, `metadata`, `utterances`를 반환한다. 각 발화는 `utterance_index`, `text`를 가진다. 화자 표기가 줄에 있으면 텍스트로 남으며 별도 화자 필드로 분리하지 않는다.
5. 원문과의 연결에는 PR에서 생성한 회의 ID와 발화 번호를 그대로 사용한다.

**출력**

- `meeting_id`, `metadata`, `utterances`로 구성된 전처리 결과. 발화 항목에는 0부터 시작하는 `utterance_index`와 `text`가 포함된다.

**추가 정의 필요**

- 위의 세 줄 머리말, 콜론 구분 및 줄별 발화 처리는 **현재 검증 데이터와 PR 설정에 따른 예시**다. 입력 데이터의 실제 구조에 따라 머리말 줄 수·메타데이터 추출·발화 분리 규칙을 변경할 수 있도록 설계하고, 실행마다 적용한 설정을 기록한다.
- 화자 분리 여부와 입력 형식에 따라 줄 단위가 실제 발화·문장 경계와 다를 수 있으므로 입력별 영향을 확인한다. 현재 PR에 없는 DOCX/HWPX 파싱은 별도 범위로 남긴다.

### 4.2 임베딩 기반 청킹

**입력**

- 회의 ID와 번호가 부여된 발화 목록
- 기존 실험 기준 임베딩 모델 `BAAI/bge-m3`와 잠재 경계 탐지 설정
- 선택한 후보 병합 조건: `K=0.0`, `gap=400자`, `span=800자`

**처리**

1. PR #35의 경계 탐지 흐름을 기준으로 발화 단위 200자 청크와 100자 오버랩을 만들고, 발화별 BGE-M3 임베딩을 글자 수로 가중합해 청크 벡터를 구성한다. 4자 이하 발화는 다른 발화가 있으면 풀링에서 제외한다. 좌우 블록 크기는 2다.
2. PR의 유사도·depth 계산과 후보 선정 방식을 사용한다. depth > 0이면서 회의별 depth 평균 + K × 표준편차 이상인 위치를 후보로 하며, K=0.0으로 설정한다.
3. 위치순 후보를 인접 후보 간 발화 글자 수가 400자 이하이고 그룹의 첫 후보부터 마지막 후보까지 범위가 800자 이하인 조건으로 순차 병합한다. 각 그룹에서는 depth가 가장 높은 후보를 대표 위치로 사용한다.
4. PR과 같이 대표 경계 발화부터 새 구간이 시작되도록 원문 발화 목록을 분할한다. PR 결과의 핵심 `utterances`는 구간 간 중복이 없다. 분할 구간 앞뒤 오버랩은 각각 별도 필드로 저장한다.
5. B0 에이전트에는 앞서 정한 대로 핵심 `utterances`만 제공한다. PR의 오버랩 필드는 보존하되 기본 입력에 합치지 않고 별도 비교 실험에 사용한다.

**기존 실험과 적용 범위**

PR의 임베딩 계산용 청크는 목표 200자, 오버랩 100자로 발화 단위로 구성된다. 이 오버랩은 **경계 탐지 내부 설정**이다. PR은 별도로 분할된 핵심 구간 앞뒤에 각각 목표 200자의 오버랩 발화를 저장하며 최소 한 발화를 포함하므로 개별 발화가 길면 200자를 넘을 수 있다. B0의 에이전트 입력에는 핵심 구간만 사용한다. `span=800`은 병합 전 후보 그룹의 범위 제한으로, 최종 청크 길이 제한이 아니다.

기존 보고서에서 이 조합은 20개 회의 중 경계 그룹이 15개 이하인 회의가 10개인 조건이었다. 보고서는 이를 호출량과 정답 거리의 절충으로 제시했으며, 최종 분할의 발화 보존, 실제 호출 및 요약 품질은 검증하지 않았다. 이번 계획에서는 사용자가 선택한 설정으로 적용하고, 그 품질은 별도로 실험한다. [기존 실험 보고서](../chunking_method/bge_distance_experiment/report.md)

**설정 해석 주의:** 기존 보고서는 윈도우 전체 임베딩과 유사도의 국소 최솟값 후보를 사용했다. PR #35는 발화 임베딩의 가중 pooled 방식과 양수 depth 임계값 기준을 사용하므로, K/gap/span 값이 같아도 결과가 동일하다고 가정하지 않는다. PR 구현을 기준으로 다시 측정한다.

**출력**

| 항목 | 정의 |
|---|---|
| 회의 ID | 원문을 식별하는 값 |
| 청크 ID | 회의 내에서 1부터 시작하는 정수 인덱스 |
| 시작 발화 번호 | 청크에 포함된 첫 발화 번호 |
| 종료 발화 번호 | 청크에 포함된 마지막 발화 번호 |
| 원문 | 해당 청크의 전사문 |
| 글자 수 | 청크 원문의 글자 수 |

원문과의 연결은 **회의 ID + PR의 0부터 시작하는 발화 번호**로 관리한다. PR의 `segment_id`는 0부터 시작하며, 기존 요구의 1부터 시작하는 청크 ID가 필요하면 후속 변환에서 `segment_id + 1`로 부여하고 원본 ID를 함께 보존한다. PR의 핵심 구간 `char_count`는 발화별 텍스트 길이의 합이며 연결 구분자는 포함하지 않는다.

**예외 및 추가 정의 필요**

- 발화 하나가 1,000자를 초과할 때의 처리: 우선 발화를 보존해 초과를 허용하는 안을 검토한다. 아직 확정된 규칙은 아니다.
- PR은 대표 경계로 구간을 나누며 최종 구간을 약 1,000자로 제한하지 않는다. 기존 1,000자 권장 조건은 PR 출력 뒤에 적용할 별도 후처리로 남기며, 추가 분할 여부와 경계 보존 규칙을 확정해야 한다.
- 기존 실험의 대표 경계 위치를 발화 경계와 약 1,000자 추출용 청크로 변환하는 구체적인 규칙 및 그 영향
- 모든 발화가 누락·중복 없이 순서대로 청크에 포함되는지 확인한다.

### 4.3 안건·논의 추출 에이전트

**입력**

- 현재 청크: 회의 ID, 청크 ID, 발화 범위, 원문과 글자 수
- 이전 청크까지 확정된 안건 목록: 안건 ID와 안건 제목
- 추출 지시와 추후 제공될 요약 구조 Markdown

**처리**

1. 청크의 논의를 기존 안건에 연결하거나 새 안건으로 식별한다.
2. 신규 안건이면 새 안건 ID를 발급한다.
3. 안건별 논의 내용을 추출하고 해당하는 원문 발화 번호를 기록한다.
4. 1차 병합 전에는 지나친 압축을 피하고, 논의의 맥락과 조건을 충분히 남긴다.
5. 처리 후 안건 목록을 갱신해 다음 청크에 제공한다.

**출력**

- 회의 ID, 청크 ID
- 안건 ID, 안건 제목, 기존 안건 연결 또는 신규 안건 여부
- 안건별 논의 내용과 각 항목의 근거 발화 번호
- 해당 안건이나 목록형 항목이 없으면 빈 리스트 `[]`

논의 항목의 세부 필드와 상태값은 추후 제공될 Markdown을 바탕으로 확정한다. 안건 ID 발급 방식, 하나의 청크가 여러 안건에 속하는 경우와 동일 안건을 잘못 나눈 경우의 처리도 명세한다.

### 4.4 액션 추출 에이전트

**입력**

- 안건·논의 추출과 동일하게 구성한 현재 청크, 회의 정보, 기존 안건 목록
- 액션 추출 지시와 추후 제공될 액션 구조 Markdown

**처리**

1. 독립적인 에이전트가 같은 입력에서 액션을 추출한다.
2. 회의 이후 구체적으로 수행하거나 관리할 일인지와 수행 의도가 확인되는지 판단한다.
3. 원문에 없는 담당자와 기한을 임의로 생성하지 않는다.
4. 액션의 근거가 되는 발화 번호를 기록한다.

**출력**

- 회의 ID, 청크 ID, 액션 목록 및 각 액션의 근거 발화 번호
- 액션이 없으면 `[]`
- 담당자·기한 등 단일 값이 없을 때의 표현은 상세 스키마 확정 시 정한다.

**연결 시 추가 정의 필요**

- 같은 청크에서 신규 안건이 생성되는 경우, 두 에이전트가 동일한 안건 ID를 사용하도록 하는 절차
- 액션 에이전트가 신규 안건 ID를 직접 생성할지, 추출 후 연결할지와 각 단계의 실행 순서
- 액션의 상세 필드, 선택·필수 조건 및 변경·취소 처리 방식

### 4.5 안건별 1차 병합

**입력**

- 모든 청크의 안건·논의 추출 결과
- 액션 추출 결과와 안건 연결 정보
- 회의 ID와 발화 번호로 조회한 해당 원 청크
- 추후 제공될 요약 및 액션 구조 Markdown

**처리**

1. 동일한 안건 ID의 결과를 모아 원문 순서에 따라 정리한다.
2. 안건별 논의의 중복을 정리하되, 서로 다른 의견이나 시간에 따른 변경을 보존한다.
   발화별 나열에 머무르지 않고 같은 쟁점을 통합해 문제·의견·결론 또는 미해결 관계를 이해할 수 있는 안건별 상세 초안을 만든다. 중요한 조건과 근거는 유지한다.
3. 액션은 확정된 연결 규칙에 따라 해당 안건과 연결한다.
4. 각 결과 항목을 근거 발화와 비교해 사실·상태·근거 연결 오류를 검토한다.
5. 원 청크와 결과를 비교해 중요 논의 누락 및 원문에 없는 내용이 있는지 검토한다.

**출력**

- 안건 ID별 병합 결과, 각 항목의 근거 발화 번호
- 검증 결과와 발견된 오류 목록
- 해당 내용이 없는 목록형 항목은 `[]`

안건별 상세에서 충실성과 기본 가독성을 함께 검토한다. 이후 회의록 전체를 조립한 뒤에는 제목·분량·중복·전체 흐름과 탐색성을 점검하며, 가독성 수정으로 내용이 바뀐 항목은 원문 근거와 다시 대조한다. 세부 프롬프트는 [요약 프롬프트](요약_프롬프트.md)를 참고한다.

**검토 범위**

근거 발화만 보면 이미 생성된 항목이 맞는지는 확인할 수 있지만, 추출되지 않은 내용의 누락은 찾기 어렵다. 누락 검토에는 해당 안건과 관련된 **원 청크 전체**를 함께 사용한다. 안건 식별 자체가 실패해 어떤 안건에도 연결되지 않은 내용의 누락을 어떻게 확인할지도 평가 설계에서 다룬다.

### 4.6 오류 재실행

**입력**

- 오류가 발견된 결과 항목 및 관련 안건 ID
- 해당 원 청크와 근거 발화 번호
- 오류 유형과 검증 판단 내용

**처리**

1. 오류와 관련된 내용 및 청크를 전달해 재실행한다.
2. 재실행 결과를 동일 기준으로 다시 검토한다.
3. 원래 결과, 오류 내용과 재실행 결과를 기록한다.

**출력**

- 수정된 결과 또는 해결되지 않은 오류와 검토 필요 상태

재실행 대상이 개별 항목인지 안건 전체인지, 최대 횟수, 반복 후 실패 처리 방식은 실험 전에 확정한다. 구조 오류를 해결하지 못한 결과는 정상 완료로 표시하지 않는다. 검증 결과 역시 사람 검토가 필요한 판단일 수 있다.

## 5. 스키마 및 단계 연결

요약·액션의 구체적 구조는 팀이 제공할 Markdown을 확인한 뒤 작성한다. 현재는 상세 필드나 허용 태그를 임의로 확정하지 않는다.

각 단계의 스키마가 정해지면 다음을 문서화한다.

1. 필드명과 자료형, 필수 여부와 빈 값 표현
2. 허용 상태값과 근거 발화 번호의 형식
3. 이전 단계 출력 필드와 다음 단계 입력 필드의 대응 관계
4. 신규 안건 ID 발급·전달 시점과 액션 연결 규칙
5. 스키마 버전 및 변경 이력

실험별로 **사용한 스키마 파일 자체**와 실제 출력을 함께 저장한다. 구조 검사와 내용의 사실성 검증은 별도로 기록한다.

## 6. 실험 계획

| 구분 | 베이스 조건 | 비교·확인 항목 |
|---|---|---|
| 화자 구분 | 분리된 입력과 분리되지 않은 입력을 각각 사용 | 발화 구분, 안건·액션 추출 및 근거 연결의 차이 |
| 오버랩 | 사용하지 않음 | 이후 오버랩 적용 조건과 경계 누락·중복·입력량 비교 |
| 잠재 경계 탐지 | BGE-M3, K=0.0 / gap=400자 / span=800자 | 기존 후보 병합 설정을 고정하고, 최종 청크 변환과 요약·액션 품질을 확인 |
| 안건 맥락 | 안건 ID와 제목만 전달 | 후속 청크에서 기존 안건 연결 오류 및 문맥 부족 사례 |
| 1차 병합 전 추출 | 지나친 요약을 피하고 논의 내용을 충실히 보존 | 중요 내용 누락, 반복과 병합 전후 정보 손실 |
| 내용 검증·재실행 | 근거와 원 청크를 대조 | 오류 탐지와 수정 결과, 새 오류 및 처리 비용 |

가능하면 동일 회의의 두 전사 형태를 사용하고, 데이터 차이를 포함한 실험 조건을 기록한다. 모델, 프롬프트, 스키마, 청킹 설정을 고정해 비교하되, 조건이 다른 경우 함께 기록한다. 화자 분리 여부와 오버랩은 각각의 효과를 구분할 수 있도록 따로 비교한다.

평가 항목은 사실 일치성, 핵심 내용 누락, 논의 상태 구분, 근거 연결, 안건 연결, 액션 오추출·누락, 가독성, 호출량·처리 시간·비용으로 구성한다. 실제 사례와 사람 검토를 통해 평가 기준을 구체화하며, 단일 LLM 평가만을 정답으로 취급하지 않는다.

## 7. 실험 결과 기록 및 완료 기준

실행별로 입력 식별 정보, 화자 분리 여부, 청킹 설정, 모델·프롬프트·스키마 버전, 청크별 출력, 안건 목록 변화, 병합·검증·재실행 결과, 호출량·시간·사용량과 오류를 기록한다. 큰 데이터와 모델 파일은 플레이그라운드 규칙에 따라 저장소에 올리지 않는다.

계획 단계의 완료 조건은 다음과 같다.

1. 팀이 요약 및 액션 구조 Markdown을 제공한다.
2. 단계별 필수 필드와 빈 값, 안건 ID 전달·액션 연결 규칙을 확정한다.
3. 청킹 예외와 검증·재실행 종료 조건을 정한다.
4. 각 단계의 출력과 다음 단계 입력을 연결하고, 동일 조건으로 결과를 기록할 실험 계획을 확정한다.

구현 이후에는 화자 분리·비분리 입력 각각에서 전체 흐름이 실행되고, 원문 연결과 오류 상태가 추적되는지 확인한다. 성능 개선 여부는 별도의 비교 실험으로 판단한다.
