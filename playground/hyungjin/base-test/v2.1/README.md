# 회의록 베이스 실험 v2.1

v2를 기준으로 2차 조립에서 안건 간 결정 상태와 내용 중복을 대조하고, 최종 회의록에 후속 업무 및 관련 안건 번호와 이동 링크를 표시한다. ID가 없으면 미연결로 표시하며 기존 액션의 안건 연결이 정확한지 새로 검증하지 않는다. v2.1에서 생성한 결과만 변경되고 기존 v2 결과는 유지된다.

상세 설계는 [계획서](계획서.md)를 참고한다. 실행 코드는 v1의 청킹·액션·병합·검증·최종 조립 코드를 불러오므로 `../v1` 디렉터리가 함께 있어야 한다. v1의 파일과 결과는 수정하지 않는다.

## 실행

저장소의 Python 환경에서 이 디렉터리를 기준으로 실행한다. `--check`는 API를 호출하지 않는다. 실제 실행은 모델 사용료가 발생하며 최종 검증 에이전트는 실행하지 않는다.

```powershell
python 실행하기.py --meetings all --check
python 실행하기.py --meetings TS3003c

# 중간 결과가 있고 최종 조립만 다시 시도할 때
python 실행하기.py --meetings TS3003c --resume-final './outputs/회의별_실행폴더'
# 청크 요약을 마친 뒤 안건 연결부터 다시 시도할 때
python 실행하기.py --meetings TS3003d --resume-agendas './outputs/회의별_실행폴더'

python 실행하기.py --meetings REAL_MEETING_001 --input '../v1/input/회의록 팔로우업 AI 서비스 개발 현황.txt' --check
python 실행하기.py --meetings REAL_MEETING_001 --input '../v1/input/회의록 팔로우업 AI 서비스 개발 현황.txt'
# 이미 준비된 v2 청크를 재사용할 때 (로컬 임베딩을 반복하지 않음)
python 실행하기.py --meetings REAL_MEETING_001 --prepared './outputs/준비폴더/00_입력.json'
```

실제 전사문의 `--check`는 발화 형식만 확인한다. 임베딩·경계 탐지와 오버랩 구성은 실제 실행에서 진행한다. 모델 입력 한도를 넘거나 API 호출이 실패하면 실패로 기록하고 실행을 중단한다. 자동으로 내용을 자르지 않는다.

청크 요약과 청크별 액션 추출은 각각 최대 3개를 병렬 처리한다. 사용자 제공 `gpt-6-luna` 한도에 맞춰 하나의 실행 프로세스에서 모델 호출 시작 간격은 분당 5,000회 기준으로 설정하며 재시도도 같은 제한에 포함된다. 완료 순서와 무관하게 결과는 청크 번호순으로 후속 단계에 전달하고, 성공한 청크 파일은 즉시 저장한다. 별도 프로세스나 다른 애플리케이션의 호출까지 합산해 제한하지는 않는다.

일시적인 요청 제한이나 서버 과부하 응답에만 최대 2회 재시도하며, 제공된 `Retry-After`를 따른다. 결제·사용 한도 오류는 재시도하지 않고 중단한다. 사용자 제공 토큰 한도는 2,000,000 TPM / 20,000,000 TPD다. 토큰 사용량은 응답의 사용량을 합산하지만 TPM·TPD를 사전 예약하거나 강제하지는 않으므로 다른 호출이나 큰 입력으로 서버 제한에 도달할 수 있다. 프로세스에만 적용되는 간격 제한과 서버의 실제 한도는 다를 수 있다. 병렬 처리 전후 시간은 실행정보의 단계별 경과 시간으로 비교한다.

## 처리와 결과

기존 경계 구간인 segment 전체를 핵심 청크로 사용하며 800자 또는 1,000자 단위로 추가 분할하지 않는다. TS3003의 `overlap_before`·`overlap_after`는 저장된 그대로 활용한다. 실제 전사문처럼 저장된 오버랩이 없는 경우에는 발화를 보존하며 앞뒤 각각 약 200자의 문맥을 구성한다. 각 segment의 길이가 다르므로 최종 입력도 일정한 글자 수가 아니다. 실제 길이와 발화 번호는 `00_입력.json`에 기록한다. 경계 후보 병합 설정의 `span=800`은 최종 청크 크기와 별도다.

각 청크를 기존 안건 목록 없이 요약하고, 결과 전체를 보고 안건과 논의 단위를 연결한다. 액션은 청크 원문에서 별도로 추출하고, 전체 안건 생성 후 회의 단위 병합에서 연결한다. 안건별 1차 병합·검증과 액션 병합·검증 뒤에 최종 회의록을 조립한다. 오버랩 중복의 병합 판단은 요약의 `review_notes`와 액션의 `change_log`에 기록하도록 지시한다.

2차 조립 프롬프트는 안건 간 같은 쟁점의 결정 상태와 반복을 대조한다. 입력 안건 ID와 순서는 유지하므로 안건 자체를 합치거나 삭제하지는 않는다. 조립 모델은 1차 병합과 검증 결과를 대조하며 전체 원문을 직접 받지 않는다. 최종 회의록에는 액션 수정 결과, 관련 안건 링크, 검토 필요 항목과 남은 액션 검증 지적이 별도 목록으로 표시된다. 검토 필요 항목의 스키마에는 안건 ID가 없어 안건을 임의로 연결하지 않는다. 모두 모델 결과로 사람의 확인이 필요하며 발화 ID는 내부 JSON에 보존한다.

`outputs/회의ID_시각/`의 주요 파일:

- `00_입력.json`: 핵심·오버랩 발화, 원본 식별자와 글자 수
- `01_독립청크요약/`: 안건 배정 전 청크별 논의 단위
- `02_안건연결.json`, `02_안건목록.json`: 전체 안건과 논의 단위 연결 및 미연결 사유
- `01_청크요약/`, `04_병합전검증/`~`08_비교.json`: 연결된 요약과 병합·검증·수정
- `03_액션/`, `09_액션병합.json`~`12_액션재검증.json`: 액션 후보와 병합·검증
- `14_최종회의록.json`, `최종_회의록.md`, `15_사람검토자료.json`: 최종 결과와 검토 사항
- `실행정보.json`: 과정별 호출 수·토큰·경과 시간, 프롬프트 해시·스키마, 실패 상태와 전체 합계. 단가를 지정하지 않으므로 비용은 계산하지 않고 `null`로 남긴다.

안건에 연결되지 않은 논의는 연결 기록과 검토 자료에 남고 최종 회의록에는 자동 삽입되지 않는다. 원문과 함께 사람의 확인이 필요하다. 모델의 중복 판단과 검증은 무오류를 보장하지 않는다.

현재 구현은 v2 최종 조건(독립 요약 + 오버랩)이다. 계획서의 A~D 비교 실험 전체와 정량 평가 자동화는 별도 구현이 필요하다. `outputs/`는 Git에서 제외되며 실제 회의 원문과 결과를 공유할 때 범위를 확인한다.
