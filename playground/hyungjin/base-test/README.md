# 회의록 베이스 실험

실행은 `실행하기.py`에서 진행합니다. 원본 청킹 결과는 BGE-M3, K=0.0 / gap=400 / span=800 조건의 기생성 결과를 재사용합니다. 기본 모델은 GPT-6 Luna / low입니다.

## 실행 방식

아래 명령은 이 폴더에서 Python 환경을 활성화한 뒤 실행합니다. `--check`는 입력만 확인하며 API를 호출하지 않습니다. 실제 실행은 모델 사용량이 발생합니다.

```powershell
# 네 회의의 전체 실행 입력 확인
python 실행하기.py full --meetings all --check

# 청크 추출 → 안건별 병합·검증 → 액션 병합·검증 → 최종 회의록
python 실행하기.py full --meetings TS3003c

# 이전에 추출한 액션 후보와 원문을 이용해 액션 병합·검증만 수행
python 실행하기.py actions --meetings TS3003a TS3003b

# 저장된 요약·액션 검증 결과로 최종 회의록 조립
python 실행하기.py final --meetings TS3003c
```

`--meetings`에는 `TS3003a`~`TS3003d` 또는 `all`을 지정합니다. `actions`, `final`은 기본적으로 `test_output/회의ID_test`를 읽습니다. 각 회의에서 생성된 파일은 새 `outputs/회의ID_시각` 폴더에 저장합니다. 기존 결과는 수정하지 않습니다.

다른 저장 결과를 사용하려면 회의를 하나만 선택해 경로를 지정합니다. `--summary`는 1차 병합 결과와 청크별 액션을 보유한 폴더이고, `--action`은 `11_액션수정.json`과 검증 결과가 있는 폴더입니다. `--action`을 생략하면 요약 폴더 자체 또는 그 안의 `03_액션`을 확인합니다.

```powershell
python 실행하기.py actions --meetings TS3003c --summary ./test_output/TS3003c_test --check
python 실행하기.py final --meetings TS3003c --summary ./test_output/TS3003c_test --action ./test_output/TS3003c_test/03_액션 --check
```

## 단계별 입출력 구조

아래는 `full` 실행 기준입니다. `actions`는 저장된 청크별 액션부터 회의 단위 병합·검증을 수행하고, `final`은 저장된 안건·액션 검증 결과부터 최종 회의록을 만듭니다. 출력 파일은 각 실행의 `outputs/회의ID_시각/` 아래에 저장됩니다.

```text
전사문 + 기존 청킹 결과
        ↓
    원문 청크 + 기존 안건 목록
        ├─→ 청크별 요약 ──→ 안건별 1차 병합 → 요약 검증·수정 ─┐
        └─→ 청크별 액션 ──→ 회의 단위 액션 병합 → 액션 검증·수정 ─┤
                                                               ↓
                                          안건별 결과 + 액션 결과 → 최종 회의록 조립
```

두 추출 작업은 같은 원문 청크와 처리 전 안건 목록을 각각 입력받습니다. 실제 호출은 요약을 먼저 실행한 뒤 액션을 실행하지만, 요약 결과를 액션 추출에 전달하지 않습니다.

### 1. 입력 준비와 청킹

| 구분 | 구조 |
|---|---|
| 입력 | 회의 ID, `playground/hyungjin/test/input/회의ID.txt`, 기존 경계 결과 `playground/chaewon/dataset/Text_Boundaries/회의ID_boundary_candidates.json` |
| 처리 | 기존 경계와 원문 발화의 일치 여부를 확인하고, 발화를 보존하면서 약 1,000자 단위로 추가 분할합니다. |
| 출력 | `00_입력.json`: `meeting_id`, `metadata`, `detection`, `chunks` |

각 청크는 `청크ID`, 원래 구간의 `segment_id`, `발화` 배열을 가집니다. 발화에는 `번호`와 `텍스트`가 있습니다. 발화 번호는 회의 내에서 0부터 시작하며, `청크ID`는 1부터 시작합니다.

```json
{
  "meeting_id": "TS3003c",
  "metadata": {},
  "detection": {},
  "chunks": [
    {"청크ID": 1, "segment_id": 1, "발화": [{"번호": 0, "텍스트": "발화 내용"}]}
  ]
}
```

위 값은 구조 설명을 위한 예시입니다. 실제 메타데이터와 구간 ID는 입력 데이터의 값을 사용합니다.

### 2. 청크별 안건·논의 추출

| 구분 | 구조 |
|---|---|
| 입력 | 회의 정보, 이전 청크까지 확정된 안건 ID·제목 목록, 현재 청크의 발화 |
| 모델 출력 | `chunk_summary`: `meeting_id`, `chunk_id`, `agendas` |
| 저장 | `01_청크요약/청크번호.json`, 갱신된 `02_안건목록.json` |

`agendas`의 각 안건에는 `agenda_id`, `new_key`, `title`, `background`, `discussions`, `decision_states`, `unresolved_issues`, `next_meeting_topics`가 있습니다. 내용 항목은 원문과 연결할 `evidence_utterance_ids`를 가집니다. 신규 안건은 모델이 임시 키를 제안하고 코드가 실제 안건 ID를 부여해 저장합니다.

### 3. 청크별 액션 추출

| 구분 | 구조 |
|---|---|
| 입력 | 회의 ID, 요약 호출 **직전**의 기존 안건 ID·제목 목록, 현재 청크의 발화 |
| 모델 출력 | `action_result`: `meeting_id`, `actions`, `review_needed`, `change_log` |
| 저장 | `03_액션/청크번호.json`: 모델 출력에 `chunk_id`를 덧붙인 구조 |

```json
{
  "chunk_id": 1,
  "meeting_id": "TS3003c",
  "actions": [{
    "action_id": "ACT001",
    "content": "업무 내용",
    "type": "조사·검토",
    "assignee": null,
    "due_date": null,
    "agenda_id": null,
    "criteria": {"actionable": true, "future": true, "intent": true},
    "evidence_utterance_ids": [0]
  }],
  "review_needed": [],
  "change_log": []
}
```

`criteria`는 실행 가능성·후속성·실행 의도입니다. 세 기준을 모두 충족하면 `actions`, 두 기준을 충족하면서 단순 의견·제안이 아닌 경우 `review_needed`로 분리합니다. 담당자·기한·안건을 알 수 없으면 `null`입니다. 액션 에이전트는 요약과 별도로 호출되며, 같은 청크에서 새로 식별된 안건 ID는 이 호출의 안건 목록에 포함되지 않습니다.

### 4. 안건별 1차 병합과 검증

| 단계 | 입력 | 출력·저장 |
|---|---|---|
| 안건별 병합 | 안건 ID·제목, 해당 안건이 식별된 청크별 요약, 해당 청크의 원문 | `agenda_merge` → `04_병합전검증/안건ID.json` |
| 내용 검증 | 병합 결과와 해당 안건에 연결된 원 청크 | `summary_review` → `05_검증/안건ID.json` |
| 수정·재검증 | 병합 결과, 검증 지적, 해당 원 청크 | `06_수정후/안건ID.json`, 지적이 있었을 때 `07_재검증/안건ID.json` |

병합 결과는 `meeting_id`, `agenda_id`, `title`과 청크별 요약의 논의 항목들, `review_notes`로 구성됩니다. 검증 결과는 `meeting_id`, `agenda_id`, `issues`, `review_needed`, `scope_limitations`를 가집니다. 각 지적에는 유형, 위치, 설명, 근거 발화 번호와 수정 방향이 있습니다. 수정 전후와 최초 검증 결과는 `08_비교.json`에도 저장합니다.

수정은 최초 검증에서 지적이 있을 때 한 번 수행합니다. 요약 검증은 안건에 연결되지 않은 청크까지 자동으로 검토하지 않습니다.

### 5. 회의 단위 액션 병합과 검증

| 단계 | 입력 | 출력·저장 |
|---|---|---|
| 액션 병합 | 회의 ID, 최종 안건 목록, 모든 청크의 액션 후보, 전체 원문 청크 | `action_result` → `09_액션병합.json` |
| 액션 검증 | 회의 ID, 병합 액션 결과, 전체 원문 청크 | `action_review` → `10_액션검증.json` |
| 수정·재검증 | 병합 결과, 검증 지적, 전체 원문과 안건 목록 | `11_액션수정.json`, 지적이 있었을 때 `12_액션재검증.json` |

병합 결과는 청크별 액션과 같은 `action_result` 구조입니다. 검증 결과의 `issues`에는 유형, 설명, 근거 발화 번호, 수정 방향이 담깁니다. 지적이 없더라도 `11_액션수정.json`에는 병합 결과를 저장합니다. 별도 `actions` 실행에서는 기존 후보와 출처도 `03_기존액션후보.json`, `기존_액션_출처.json`에 기록합니다.

현재 액션 검증 호출은 전체 원문을 받지만, **안건별 1차 병합 요약이나 안건 목록을 검증 입력으로 받지는 않습니다.** 액션 병합에는 안건 목록이 포함됩니다. 모델의 검증 결과와 남은 재검증 지적은 사람의 확인이 필요합니다.

### 6. 회의 전체 조립 — 2차 병합

| 구분 | 구조 |
|---|---|
| 입력 | 회의 메타데이터, 안건 목록과 안건별 수정 후 결과·검증 지적, 액션 수정 후 결과·검증 지적, 안건 미식별 청크와 범위 제한 |
| 모델 출력 | `final_assembly`: `meeting_id`, `meeting_results`, `agenda_details`, `review_notes`, `scope_limitations` |
| 저장 | `13_최종조립_입력.json`, `14_최종회의록.json`, `15_사람검토자료.json`, `최종_회의록.md` |

`meeting_results`의 항목은 태그·내용·관련 `agenda_ids`·`evidence_utterance_ids`를 가집니다. `agenda_details`는 안건 ID·제목, 배경, 소주제별 논의, 결정, 미해결 이슈, 다음 회의 후보 안건을 가집니다. 이 JSON에는 **모델 출력만** 저장합니다. 회의 정보·안건 목차와 결정·미해결 건수는 메타데이터와 안건별 상세를 이용해 코드가 Markdown 회의록을 만들 때 조립합니다.

`13_최종조립_입력.json`에는 조립 입력과 출처·유효 발화 번호가 기록됩니다. 이 중 `source_paths`, `valid_utterances`는 모델에 전달하지 않고 코드의 구조 확인과 추적에 사용합니다. 발화 ID는 JSON에 남기고 Markdown 화면에는 표시하지 않습니다. 별도의 최종 검증 에이전트는 아직 실행하지 않습니다.

### 공통 기록과 스키마

- `출력_스키마.json`에 단계별 API 출력 구조가 정의되어 있으며, 실행 시 사용한 사본은 `사용_출력_스키마.json`에 저장합니다. 위 예시에서 생략한 세부 필드와 허용 태그는 이 스키마가 기준입니다.
- `실행정보.json`에는 실행 상태, 모델, 출력 형식, 스키마 해시, 액션 정책, 호출별 단계·스키마·시스템 프롬프트 해시·토큰 사용량 등이 기록됩니다. 프롬프트 원본은 공통 파일로 관리합니다.
- 목록에 해당 내용이 없으면 `[]`를 사용하고, 담당자·기한 등 확인할 수 없는 값은 해당 스키마가 허용하는 경우 `null`로 둡니다. 스키마에 맞는 출력이라는 것은 내용의 사실성이나 근거의 적절성이 검증됐다는 뜻은 아닙니다.

## 결과와 주의점

- 청크별 결과, 안건별 병합·검증, 액션 병합·검증, 최종 회의록과 호출 기록을 각 실행 폴더에 단계별로 저장합니다. 단계별 파일의 상세 구조는 `계획서.md`를 참고하세요.
- `최종_회의록.md`는 눈으로 보는 결과이고 `14_최종회의록.json`은 근거 발화 ID를 보유합니다. 최종 검증 에이전트는 실행하지 않습니다.
- 액션 검증은 현재 전체 원문과 액션 후보를 사용합니다. 안건별 1차 병합 요약을 액션 검증에 별도로 제공하는 개선은 아직 구현되지 않았습니다.
- 사용 프롬프트 원본은 이 폴더에서 관리하고 실행별 사본은 만들지 않습니다. 새로운 호출의 시스템 프롬프트 해시와 스키마는 실행 기록에 남깁니다.
- 최종 회의록 조립은 결정과 조건부 결정을 모두 목차의 결정 건수에 포함합니다. 생성 결과와 모델 검증 지적은 사람이 확인해야 합니다.

## 코드 구성

- `실행하기.py`: 명령행에서 사용하는 공통 실행 진입점
- `experiment.py`: 모델 호출 및 청크·안건별 요약
- `action_pipeline.py`: 액션 추출·병합·검증
- `final_assembly.py`: 저장 결과를 불러와 최종 회의록 조립
- `출력_스키마.json`, `*프롬프트.md`: 출력 구조와 단계별 지시문
