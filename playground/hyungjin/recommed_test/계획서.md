# Markdown 연결 기반 회의 지식 탐색·답변 실험 계획

## 1. 목적

제공된 Neo4j 스키마를 지식 구조의 기준으로 삼되, 그래프 DB 대신 Markdown 문서와 링크로 회의 지식을 저장한다. 같은 구조와 입력에서 **안건의 Topic 연결, 질문에 필요한 지식 탐색, 답변 프롬프트**를 실험하고, 각각이 답변 품질에 미치는 영향을 확인한다.

스키마 자체의 재설계, Neo4j 적재, 벡터 검색, 서비스 UI 구현은 이번 범위에 포함하지 않는다. 이 문서는 계획이며 실험 결과가 아니다.

## 2. 고정할 지식 구조와 입력

Project, Topic, Meeting, Agenda, Discussion, ActionItem, Person, Team, Role, Skill의 속성과 관계는 사용자가 제시한 스키마를 따른다. 원본의 ID와 관계 방향을 유지하며, 노드 하나를 Markdown 페이지 하나로, 관계는 대상 ID를 포함하는 `[[위키링크]]`와 관계 속성으로 표현한다. 예를 들어 Agenda의 `ABOUT`에는 Topic 링크와 `confidence`, `linked_by`를 기록한다. 존재하지 않는 속성값이나 관계는 추정해 채우지 않는다.

Discussion은 PR #61의 입력처럼 소주제에 여러 논의 문장이 있을 수 있으므로, 각 문장의 내용·태그·근거가 대응되게 기록한다. 액션 태그의 문장은 해당 Discussion에서 나온 ActionItem으로 연결한다. 기한과 명시 담당자 표현은 원문을 보존하고 확정된 배정과 구분한다.

첫 실험의 입력은 `playground/eunje/ontology/data/summary_action/`의 TS3003a~d 회의 결과 JSON과 대응 회의록이다. 필요할 때 `data/users.json`, `data/skills.json`의 테스트용 조직 정보를 사용한다. 이는 더미 데이터이며 실제 사용자 DB 동기화 결과가 아니다. 회의록 생성 자체는 평가 범위가 아니다. 회의 시각이 같으면 회의 ID 순으로 처리하며, 그 순서가 실제 발생 순서인지 확인한다.

PR #61의 `scripts/load.py`는 참고 기준이다. 기존 `open`·`parked` Topic과 최근 연결 안건을 LLM에 제시하고 기존 Topic 또는 새 Topic을 고른다. 이 실험에서는 그 판단의 품질도 검토하며, 해당 방식을 정답으로 가정하지 않는다.

## 3. 예정 파일 구조

```text
recommed_test/
├─ 계획서.md
├─ raw/                 # 원본 회의·조직 데이터 스냅샷, 변경하지 않음
├─ wiki/
│  ├─ log.md            # 생성·검토·수정 이력, 끝에 추가
│  ├─ projects/         # 프로젝트와 Topic·Meeting 연결
│  ├─ topics/           # 여러 회의의 관련 안건 연결
│  ├─ meetings/         # 회의 페이지
│  ├─ agendas/          # 안건 페이지
│  ├─ discussions/      # 논의와 원문 근거 페이지
│  ├─ actions/          # 액션, 필요 역량, 추천·배정 상태
│  ├─ people/           # 인물 페이지
│  ├─ teams/            # 팀 페이지
│  ├─ roles/            # 역할 페이지
│  └─ skills/           # 스킬 페이지
└─ outputs/             # 실험 조건·탐색 경로·답변·평가
```

각 문서에서 관련 노드의 ID와 관계 방향을 확인할 수 있어야 하며, 논의의 근거는 회의 ID와 발화 인덱스로 원문까지 추적한다. 에이전트에는 노드·속성·관계와 조회 방법을 명시한 스키마를 제공한다. Markdown 조회 수단이 페이지를 읽고 조건과 링크를 평가한다. 재실행 시 원본을 바꾸거나 검토자가 확정한 내용을 자동으로 덮어쓰지 않는다. 조직 더미 데이터는 원본 두 파일을 `raw/`에 복사하고 노드별 페이지로 정리했다. 원본의 공통 참석자 목록은 특정 회의에 자동 연결하지 않는다.

## 4. 처리 흐름

1. **입력 고정**: 회의·조직 데이터 스냅샷을 `raw/`에 두고 출처와 버전을 기록한다. 회의별 ID, 검토 상태 및 발화 근거의 사용 가능 여부를 확인한다.
2. **스키마 기반 변환**: 활성 회의 항목을 Meeting → Agenda → Discussion → ActionItem으로 변환하고 프로젝트·참석자 등 확인 가능한 관계를 기록한다. 누락과 불일치는 검토 대상으로 남긴다.
3. **Topic 연결 실험**: 안건별 기존 Topic 연결 또는 신규 Topic 생성을 제안한다. PR #61 방식을 기준선으로 두고 후보를 찾는 방식과 판단에 제공하는 맥락·프롬프트를 비교한다. 제안한 후보, 선택 결과, 이유와 근거를 남기며, 사람 검토 후 수정한 연결은 `linked_by: hitl`로 표시한다. 상세 비교는 5절에서 정한다.
4. **위키 생성·갱신**: 노드의 ID·속성과 관계를 Markdown 및 링크로 기록하고 로그를 갱신한다. 재처리 시 같은 ID의 중복 여부를 검사하고 검토·배정 상태를 보존한다.
5. **질문별 조회**: 에이전트가 스키마를 참고해 자연어 요청을 Cypher 형태의 조회로 변환한다. Markdown 조회 수단이 유형·속성 조건과 관계 방향을 해석해 결과를 반환한다. 질의, 읽은 문서, 반환 결과와 오류를 기록한다.
6. **답변 생성과 평가**: 탐색 결과와 답변 프롬프트를 모델에 제공한다. 답변·근거·미확인 사항을 저장하고, Topic 연결과 탐색 및 답변을 각각 평가한다.

## 5. 실험 설계

### 5.1 Topic 연결

Topic은 여러 회의에 걸친 동일한 논의 흐름을 나타낸다. 잘못 합치거나 나누면 이후 탐색과 답변에도 영향이 생기므로 독립적으로 평가한다.

- **기준선**: PR #61처럼 같은 프로젝트의 `open`·`parked` Topic과 최근 연결 안건을 후보로 제공하고 기존 연결 또는 새 Topic을 판단한다.
- **비교 조건**: 후보의 제목만 제공하는 경우와, 최근 안건의 배경·결정·미해결 이슈·다음 주제를 함께 제공하는 경우를 비교한다. 후보 범위와 제시 정보가 어떤 차이를 만드는지 기록한다.
- **판단 프롬프트**: 같은 주제를 이어가는 기준, 유사하지만 별개인 주제를 구분하는 기준, 확신이 부족할 때 검토 대상으로 남기는 지시를 비교한다. 판단 이유와 관련 안건 근거를 요구한다.
- **평가**: 사전에 사람이 안건별 연결 및 신규 Topic 여부를 표시하고 판단이 애매한 경우도 별도 기록한다. 기존 Topic을 잘못 합친 경우와 새 Topic으로 잘못 분리한 경우를 구분하고, 후보 목록에 정답이 있었는지도 확인한다. 자동 연결과 사람 검토 이후 결과를 구분한다.

같은 회의 순서, 초기 Topic 상태, 입력과 평가표를 사용해 비교한다. Topic 연결이 바뀌면 후속 탐색 경로도 달라지므로, 답변 실험에서는 검토된 연결을 고정한 조건과 자동 연결을 사용한 조건을 구분한다.

### 5.2 탐색 방식

동일한 검토 완료 위키와 질문을 사용한다. 에이전트에는 노드 유형·속성·관계 방향 및 지원하는 조회 문법만 제공하고, 자연어를 Cypher 형태의 질의로 변환하게 한다. 예를 들어 `MATCH (p:Person)-[h:HAS_SKILL]->(s:Skill) WHERE p.is_active = true AND s.name = ... RETURN p, h.level`처럼 후보 조건과 관계를 명시한다.

Markdown은 Cypher를 직접 실행하지 않으므로 조회 수단을 별도로 만든다. 첫 실험에서는 필요한 `MATCH`, 관계 방향, 속성 조건, `RETURN` 등 제한된 문법부터 지원하고, 지원하지 않는 문법이나 모호한 값은 오류로 반환한다. 실제 지원 범위는 구현과 테스트를 통해 명시하며 완전한 Cypher 엔진이라고 가정하지 않는다. 페이지 형식과 링크를 파싱해 조건을 적용하고, 결과에는 값과 출처 페이지를 포함한다.

- **질의 생성 비교**: 동일 스키마·질문에서 관계 방향, 속성 조건, 반환 항목 및 모호성 처리에 대한 프롬프트를 비교한다.
- **조회 정확성**: 사람이 작성한 기대 결과와 실제 반환 행을 비교하며 다중 관계, 역방향 탐색, 없는 속성·결과, 지원하지 않는 문법을 검사한다. 별도로 질의 자체가 질문의 의도와 일치하는지 평가한다.
- **후속 업무**: 반환 결과를 사용해 Topic 연결, 답변 또는 담당자 추천을 수행한다. 쓰기 제안과 실제 Markdown 갱신은 구분하고, 수동 확정 내용은 보호한다.

각 실행에서 질문, 스키마·프롬프트 버전, 생성 질의, 조회 결과와 출처 페이지, 오류, 후속 답변을 보관한다. 조회 실패와 빈 결과는 구분하며 모델이 없는 결과를 추측하지 않도록 한다.

### 5.3 답변 프롬프트

동일한 질문과 동일한 검색 결과를 고정한 뒤 프롬프트를 비교한다.

- **기준선**: 제공된 자료를 바탕으로 질문에 답하고 출처를 제시하도록 지시한다.
- **비교 조건**: 결정·제안·보류와 모델의 추론을 구분하고, 회의 간 변화 및 상충 내용을 표시하며, 근거가 없으면 부족하다고 답하도록 구체화한다.
- 출력에는 답변에 사용한 회의·안건·논의 링크와 가능한 발화 인덱스를 포함한다. 추천 시에는 후보, 근거, 미확인 정보를 구분하고 자동 배정하지 않는다.

모델·설정·입력 자료를 고정하고 프롬프트 버전과 호출 정보를 기록한다. 모델 응답의 변동성을 확인할 수 있도록 동일 조건을 반복 실행하며 각 실행을 따로 보관한다.

## 6. 평가와 완료 기준

실험 전에 사람이 회의록을 검토해 Topic 연결 정답표와 질문별 기대 답변·필요 근거를 작성한다. 정답표에는 복수의 타당한 연결이나 답변, 판단 불가 항목을 허용하며 모델 입력으로 제공하지 않는다. 질문은 다음 유형을 포함한다.

1. 한 회의에서 내려진 결정과 그 이유·발화 근거.
2. 여러 회의에 걸친 Topic의 논의 변화와 미해결 사항.
3. 유사하지만 다른 Topic을 혼동하기 쉬운 질문.
4. 액션의 발생 맥락, 명시 담당자 또는 담당자 후보와 근거.
5. 회의록에 정보가 없거나 서로 다른 기록이 충돌하는 질문.

| 평가 대상 | 기록할 결과 |
| --- | --- |
| Topic 연결 | 안건별 정답 대비 연결 일치, 잘못 합침·분리, 판단 불가와 근거. 전체 건수 및 후보 포함 여부. |
| 탐색 | 질문별 필수 근거를 찾았는지, 불필요한 페이지를 얼마나 읽었는지, 끊긴 링크와 경로·입력량. |
| 답변 | 정확성, 결정과 제안 구분, 출처·발화 근거 일치, 누락·근거 없는 주장, 정보 부족 시의 처리. |
| 운영 | 호출 수, 토큰, 경과 시간, 오류 및 재실행 결과. 동일 입력 재처리 시 중복과 확정 내용 덮어쓰기 여부. |

질문별로 **연결 오류 → 탐색 누락 → 답변 생성 오류**를 구분한다. 자료가 검색되지 않은 답변 오류를 프롬프트 문제로만 분류하지 않는다. 각 조건의 분모, 개별 사례와 검토자 판단을 남기고, 정량 결과와 함께 실패 예시를 비교한다.

완료 조건은 네 회의의 변환 결과와 링크가 검증되고, Topic 연결·탐색·프롬프트 조건별 비교 결과와 오류 사례가 기록되는 것이다. 임의의 정확도 목표를 성공으로 가정하지 않는다.

## 7. 한계와 결정 사항

- 프로젝트 ID 추정, 공통 참석자 및 조직 데이터는 PR #61의 실험 편의이며 실제 사용자 데이터가 아니다. 누락된 조직 관계와 업무량은 미상으로 둔다.
- `confidence`는 검증된 점수가 있을 때만 기록한다. Topic 판단과 추천은 검토 전까지 제안이며 사람의 확정과 구분한다.
- 과거 회의 추가·수정 시 Topic 연결을 어디까지 재검토할지와 검토 승인 절차는 구현 전에 정한다.
- 원문과 인물 정보의 보관·공유 범위를 확인한다. 실험에는 실제 데이터 대신 제공된 테스트 데이터를 우선 사용한다.
