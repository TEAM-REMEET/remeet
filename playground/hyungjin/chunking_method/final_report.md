작성일: 2026-10-27

## 1. 실험 목적과 최종 결정

본 실험은 회의록 정리에 앞서 회의 전사문을 의미 있는 논의 단위로 나누어, 이후 액션 추출과 요약에 적합한 문맥을 제공하기 위해 진행했다. 단순히 일정 길이로 자르는 대신, 의미가 바뀌는 지점을 임베딩으로 탐지하고 LLM으로 검증하면 후속 작업의 입력 품질을 높일 수 있다는 가설에서 출발했다.

실험 결과, 임베딩 후보 주변에 정답 경계를 포함시키는 설정과 중복 문맥을 줄이는 병합 방식은 확보했다. 그러나 후보 주변에 정답이 존재한다는 사실이 LLM의 정확한 경계 선택으로 이어지지는 않았다. 입력 구성과 위치 선택 방법을 바꾼 v1·v2·v3에서도 경계 누락이 남았으며, 후속 LLM의 입력을 나누기 위해 별도의 LLM 검증 단계를 운영해야 하는 구조적 부담도 확인했다.

이에 **임베딩 후보를 LLM으로 검증하여 최종 경계를 확정하는 단계는 도입하지 않고, 해당 실험을 종료한다.** 후속 개발에서는 임베딩 기반 임시 의미 청킹을 적용하고, 이를 액션 추출·요약의 입력으로 사용하는 방향을 따른다. 채택 방법의 구체적인 알고리즘과 코드 경로는 본 보고서에서 확정하지 않는다.

이 결정은 의미 청킹 자체를 포기한다는 뜻이 아니다. 이번 실험의 산출물을 후보 탐지에 대한 근거로 남기되, 정확한 주제 경계 확정을 후속 처리의 필수 선행 단계로 두지 않겠다는 결정이다. 액션 추출·요약의 성능 향상은 이번 실험에서 직접 측정하지 않았으므로, 향후 검증할 목표로 남긴다.

## 2. 정답 정의와 평가 범위

AMI 회의 전사문 20개를 사용하고, 원래 AMI의 구간 주석 대신 프로젝트의 의도에 맞게 고지능 LLM으로 추출한 경계를 평가 기준으로 사용했다. 기준은 단어 또는 화제 변화 자체가 아니라, 회의 참여자가 결론을 내리려는 논의 대상의 변화다. 같은 대상의 측면 변경, 일시적 잡담 후 복귀, 같은 결정의 재논의 등은 경계에서 제외하도록 했다.

이 기준을 적용한 프로젝트용 정답은 총 153개 경계다. 정답 위치는 새 구간의 첫 발화를 나타내는 1부터 시작하는 발화 번호다. LLM 경계 검증에는 TS3003c 한 회의를 사용했으며, 726개 발화와 정답 경계 11개로 구성된다. 정답은 검증 LLM의 입력에 넣지 않고 로컬 평가에만 사용했다.

이 정답은 프로젝트 목적에 맞춘 **LLM 기반 참조 정답**이다. AMI 원래 주석보다 객관적으로 우수하다는 결론은 내리지 않는다. 저장된 정답에는 독립적인 인간 검수나 다중 평가자 합의를 수행하지 않았다고 명시되어 있으므로, 정답 생성 모델의 판단 편향과 경계의 주관성이 남는다.

입력·정답 위치는 각각 `playground/hyungjin/test/input/`, `playground/hyungjin/test/llm_golden/`이다. 데이터 목록과 해시는 [dataset_manifest.csv](embedding_experiment/dataset_manifest.csv), 정답 형식과 검수 범위는 [TS3003c 참조 정답](../test/llm_golden/TS3003c.json)에서 확인할 수 있다.

## 3. 슬라이딩 윈도우와 임베딩 후보 추출

전사문에 겹치는 슬라이딩 윈도우를 만들고, 이웃 윈도우의 임베딩 코사인 유사도를 계산했다. 유사도가 주변에 비해 낮아지는 지점을 의미 변화의 후보로 간주했다. 전체적으로 낮은 유사도뿐 아니라 주변 대비 하락 정도를 반영하기 위해 depth 방식과 quantile 방식을 비교했다.

depth는 유사도 곡선의 골이 얼마나 깊은지 나타낸다. 현재 유사도를 s_i, 현재 위치를 포함하는 좌우 최대 3개 이웃 범위의 최대 유사도를 각각 L_i, R_i로 두면 다음과 같다.

```text
L_i = max(s[max(0, i-3) : i+1])
R_i = max(s[i : min(n, i+4)])
depth_i = max(0, L_i + R_i - 2*s_i)
```

depth 방식은 국소 최솟값이면서 임계값 이상인 지점을 선택한다. 따라서 모든 유사도 하락을 곧바로 실제 주제 경계로 확정하는 방식은 아니다.

| 비교 항목 | 실험 범위 |
|---|---|
| 임베딩 모델 | BAAI/bge-m3, Gameselo/STS-multilingual-mpnet-base-v2, jinaai/jina-embeddings-v5-text-small-text-matching, alphabrothers/alpha-sts-v0 |
| 목표 윈도우 크기 | 200, 300, 400, 500자 |
| 오버랩 크기 | 50, 100, 150자 |
| 분할 방식 | 문장 보존 |
| 후보 선택 | depth, quantile |
| 임계값 | 0.02, 0.05, 0.10 |
| 정답 포함 평가 | 후보 중심 ±200자, ±300자 |

전체 288조건 중 144조건이 완전히 실행되었다. BGE와 Jina는 각각 72조건을 완료했지만 MPNet과 Alpha STS는 부분 실행 또는 실패가 있어, 네 모델 전체의 성능 순위를 확정할 수는 없다.

최종 사용 설정은 **BGE-m3 / 목표 200자 / 오버랩 100자 / 문장 보존 / depth ≥ 0.10**이다. Jina도 완전 실행된 비교 대상으로 남겼으나, 본 프로젝트의 상업 활용 방향에 맞춰 BGE를 후속 실험에 사용했다. 라이선스 검토 기록은 기존 임베딩 보고서의 BGE 정리 부분을 따른다.

| 선택 설정의 평가 범위 | 정답 포함 | 후보 수 |
|---|---:|---:|
| ±200자 | 144/153, 94.1% | 915 |
| ±300자 | 153/153, 100.0% | 915 |

따라서 ±300자를 후속 문맥 범위로 선택했다. 여기서 100%는 **20개 회의의 정답 경계가 적어도 하나의 후보 주변 범위에 포함되었다**는 뜻이다. 후보 915개가 모두 실제 경계라는 의미도, 최종 경계를 모두 정확히 찾아냈다는 의미도 아니다. 이 구분이 이후 LLM 실험의 필요성과 한계를 이해하는 핵심이다.

## 4. 중복 문맥 병합과 최대 1,200자 제안

후보마다 앞뒤 300자씩 제공하면 이웃 후보의 문맥이 반복되어 LLM 요청 수와 입력량이 증가한다. 이를 줄이기 위해 겹치는 범위를 보존한 채 최대 900자 또는 1,200자까지 합치는 방식과, 겹친 부분의 중앙을 새 중심으로 삼는 방식을 비교했다. 후보의 앞뒤에 동시에 중복이 있는 경우도 계산에 포함했다.

다음 요청 수는 병합 단계에서 계산한 입력 묶음 수이며, 이 단계에서 실제 LLM을 호출한 횟수는 아니다.

| 방식 | 요청 묶음 | 정답 포함 | 미병합 대비 묶음 감소 |
|---|---:|---:|---:|
| 미병합, 후보별 ±300자 | 915 | 153/153 | — |
| 범위 보존, 최대 900자 | 565 | 153/153 | 38.3% |
| 범위 보존, 최대 1,200자 | 347 | 153/153 | 62.1% |
| 겹치는 쌍의 중앙 재배치 ±300자 | 1,480 | 148/153 | 오히려 증가 |
| 겹치는 쌍의 중앙 재배치 ±500자 | 1,480 | 153/153 | 오히려 증가 |

범위 보존 1,200자는 기존 정답 포함을 유지하면서 묶음 수를 가장 많이 줄인 비교 조건이었다. 문맥 문자 수의 합계도 546,104자에서 353,840자로 약 35.2% 줄었다. 이에 LLM 투입용 병합 상한으로 제안했다. 이는 비교한 조건 안에서의 선택이며, 모든 회의나 모델에서 1,200자가 최적이라는 뜻은 아니다.

또한 1,200자 병합 묶음 347개 중 27개에는 정답 경계가 2개 이상 포함되었고, 최대 4개까지 존재했다. 묶음 하나를 곧바로 주제 하나로 간주할 수 없으며, 여러 후보와 경계를 한 요청 안에서 다뤄야 했다. 범위가 커질수록 요청 수는 줄지만 판정 구조는 복잡해질 수 있다.

상세 근거: [병합 실험 보고서](merge_experiment/report.md), [병합 집계](merge_experiment/aggregate.csv), [묶음당 정답 개수 분석](merge_experiment/gold_count_report.md). 정답 개수 분석은 실제 요청 범위와 선택 가능한 발화 ID를 기준으로 하므로, 문자 범위 기반 집계와 끝점 처리에 차이가 있을 수 있다.

## 5. 실제 LLM 경계 검증: v1·v2·v3

TS3003c의 후보 39개를 대상으로 미병합 39묶음, 최대 900자 병합 26묶음, 최대 1,200자 병합 16묶음을 비교했다. 검증 모델은 gpt-6-luna, reasoning effort는 low였다. 버전별 세 조건은 총 81개 요청으로 구성했다. 주제 경계 기준을 담은 시스템 프롬프트를 사용하되, 경계 위치를 제시하거나 선택하는 방식을 바꾸었다.

| 버전 | 판정 방식 | 확인한 한계 |
|---|---|---|
| v1 | 후보 주변 발화의 경계 선택지를 제공하는 방식 | 누락이 남고 일부 병합 요청의 처리 실패 발생 |
| v2 | 예상 경계 위치를 고정하고 후보별 O/X 판정 | 위치 보정 불가. 후보 위치 자체의 재현율 상한 존재 |
| v3 | 후보별 O/X와 예상 위치 ±5발화 안에서 실제 경계 선택 | 탐색 범위 제한과 판정 누락이 남고 일부 요청 실패 |

아래는 버전 간 참고가 가능하도록 공통으로 기록된 **±3발화 허용 일대일 대응** 지표를 모은 것이다. P는 정밀도, R은 재현율이다. 버전별 입력 계약과 주 지표가 다르고 일부는 부분 완료이므로, 이를 동일 조건의 모델 순위나 개선 추세로 해석하지 않는다.

| 버전 | 조건 | 처리 상태 | P | R | F1 |
|---|---|---|---:|---:|---:|
| v1 | 미병합 | 완료 | 53.8% | 63.6% | 58.3% |
| v1 | 최대 900자 | 부분 완료, 2요청 실패 | 53.8% | 63.6% | 58.3% |
| v1 | 최대 1,200자 | 부분 완료, 1요청 실패 | 70.0% | 63.6% | 66.7% |
| v2 | 미병합 | 완료 | 66.7% | 36.4% | 47.1% |
| v2 | 최대 900자 | 완료 | 75.0% | 27.3% | 40.0% |
| v2 | 최대 1,200자 | 완료 | 66.7% | 54.5% | 60.0% |
| v3 | 미병합 | 부분 완료, 1요청 실패 | 60.0% | 27.3% | 37.5% |
| v3 | 최대 900자 | 완료 | 71.4% | 45.5% | 55.6% |
| v3 | 최대 1,200자 | 부분 완료, 1요청 실패 | 50.0% | 27.3% | 35.3% |

±300자 내 정답 포함이 100%였더라도, 발화 단위 후보 표현과 탐색 범위를 거치면 실제 선택 가능한 정답은 줄어들 수 있었다. v2의 고정 예상 위치는 정확 일치 기준 2/11개, ±3발화 기준 8/11개까지만 정답과 대응할 수 있었다. v3의 ±5발화 탐색 범위에도 정답은 9/11개만 포함되었다. 따라서 누락 원인을 전부 LLM의 판단 능력으로 돌릴 수 없다. 후보 위치의 표현, 탐색 범위, LLM 판정, 응답 검증 실패가 함께 영향을 주었다.

그럼에도 모든 요청이 완료된 조건에서도 재현율은 100%에 도달하지 못했다. 이번 구성으로는 후보 포함의 장점을 최종 경계 확정 성능으로 충분히 연결하지 못했다고 판단한다.

보고서상 누적 요청 지연은 버전별 약 497~733초였다. 이는 전체 서비스의 실제 경과 시간과 동일한 지표는 아니지만, 경계 검증에 별도 추론 처리가 필요하다는 근거다. 일부 재호출 사용량이 기존 집계에서 빠져 있어 비용을 완전한 총비용으로 합산하지 않는다. 본 결정은 API 금액 자체가 크다는 주장보다, 추가 호출·위치 보정·응답 검증·실패 처리의 부담에 비해 얻은 품질이 충분하지 않았다는 판단에 따른다.

## 6. LLM 경계 검증을 철회한 이유

첫째, 후보 추출과 병합의 최적화가 단순 분할 대비 충분한 이득을 보장하지 않았다. TS3003c의 본문은 12,159자이므로, 문장·발화를 보존하지 않고 오버랩 없이 1,200자씩 자르면 `ceil(12,159 / 1,200) = 11`개 청크가 된다. 이는 임베딩 후보를 최대 1,200자로 병합한 16묶음보다 적다. 앞서 논의한 ‘약 10~12개’는 이 회의의 규모를 가리키며, 20개 회의 전체의 일반적인 청크 수는 아니다.

다만 이 비교는 입력 묶음 수에 대한 산술 비교다. 단순 1,200자 분할로 동일한 경계 추출이나 액션 추출·요약 품질을 달성했다고 검증한 결과는 아니다. 임베딩 후보 중심 문맥과 전체 본문 분할은 입력 범위와 목적이 다르므로, 호출 수만으로 품질 우열을 판단하지 않는다. 그럼에도 복잡한 전처리·검증 단계를 추가하려면 그에 상응하는 품질 이득을 입증해야 한다는 판단 근거는 된다.

둘째, v1·v2·v3에서 입력 및 위치 선택 방식을 조정했지만 경계 누락이 해결되지 않았다. 높은 후보 포함률만으로 최종 파이프라인의 신뢰성을 보장할 수 없었으며, 검증 단계 자체에 추가적인 설계와 예외 처리가 필요했다.

셋째, 본래 목적은 정확한 주제 경계 목록을 만드는 것 자체가 아니라 액션 추출과 요약의 입력 품질을 높이는 것이다. 그 입력을 나누기 위해 별도의 LLM을 반복 호출하는 구조는 전체 처리 단계와 운영 부담을 늘린다. 현재 결과에서는 그 비용과 복잡성을 정당화할 후속 작업의 품질 향상이 확인되지 않았다.

따라서 **현재 구현과 평가 범위에서는 LLM 경계 검증을 제품 파이프라인에 채택하지 않는다.** 이는 단일 회의·특정 모델·현재 프롬프트와 입력 구성에 대한 도입 결정이며, 다른 모델이나 모든 LLM 경계 검증 방식이 효과가 없다는 일반적 결론은 아니다.

## 7. 후속 방향과 이번 실험에서 남긴 것

후속 방향은 팀원의 임베딩 기반 방법으로 임시 의미 청크를 만들고, 이를 액션 추출·요약 단계에 직접 제공하는 것이다. 청크를 확정된 단일 안건으로 간주하지 않고 작업용 문맥 단위로 취급한다. 이번 BGE 설정을 새 방법의 확정 설정으로 자동 승계하지 않으며, 구체 구현과 파라미터는 채택 방법에 맞게 결정한다.

이번 실험은 다음 근거를 남겼다.

- 프로젝트의 논의 대상 기준을 적용한 LLM 참조 정답과 평가 데이터 목록.
- BGE 기반 후보 추출에서 ±300자 범위로 153개 정답을 포함한 설정.
- 범위 보존 1,200자 병합의 요청 묶음 감소 효과와 복수 경계 처리의 필요성.
- 후보 포함, 선택 가능한 경계 범위, 최종 경계 판정 정확도를 구분해야 한다는 실험적 근거.
- LLM 경계 검증의 품질·처리 부담과 도입 철회 이유를 확인할 수 있는 버전별 결과.

후속 검증에서는 경계 일치율만을 최종 목표로 두지 않는다. 동일한 액션 추출·요약 모델과 프롬프트를 유지한 상태에서 단순 길이 분할과 임베딩 기반 임시 청킹을 비교하고, 액션 누락·중복, 담당자·기한 정확성, 요약의 사실성·핵심 논의 포함, 총 입력 토큰·처리 시간을 평가하는 것이 적절하다. 이는 후속 검증 제안이며 이번 실험에서 수행한 결과가 아니다.
