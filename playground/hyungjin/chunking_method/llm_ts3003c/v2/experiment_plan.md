# TS3003c 실제 LLM 경계 검증 비교 실험 계획

작성일: 2026-10-27

## 1. 목적과 고정 조건

동일한 경계 후보에 세 가지 문맥 구성 방식을 적용하여 호출 감소가 실제 경계 검증 성능과 비용에 미치는 영향을 확인한다.

| 항목 | 설정 |
|---|---|
| 회의 | TS3003c |
| 입력 | `test/input/TS3003c.txt` |
| 정답 | `test/llm_golden/TS3003c.json` |
| 정답 경계 | 11개 |
| 임베딩 | `BAAI/bge-m3` |
| 윈도우 | 목표 200자, 오버랩 100자, 문장 보존 |
| 후보 선출 | depth ≥ 0.10 |
| 원래 후보 | 39개 |
| 비교 변수 | 미병합 / 범위 보존 최대 900자 / 범위 보존 최대 1,200자 |

입력·정답 경로의 기준은 `remeet/playground/hyungjin/`이다. 기존 후보와 `chunking_method/merge_experiment/inputs_not_sent/TS3003c/`의 병합 결과를 재사용한다. 임베딩을 다시 계산하지 않는다. 정답은 입력 정합성·사전 포함률 점검과 호출 완료 후 평가에만 사용하며 LLM 요청에는 넣지 않는다.

## 2. 비교 조건

| 조건 | 문맥 구성 | 예정 호출 수 | 본문 문자 합계 | 사전 정답 포함 |
|---|---|---:|---:|---:|
| 미병합 | 후보 좌우 각각 300자 | 39 | 23,249 | 11/11 |
| 병합 900 | 겹치는 문맥을 최대 900자로 병합 | 26 | 18,108 | 11/11 |

총 기본 호출은 **81회**다. 이는 저장된 문맥 묶음당 요청 1회를 가정한 수이며, 실패 재시도는 별도 집계한다. 병합 요청의 복수 후보 처리 방식이 확정되면 실제 요청 구조와 호출 수를 다시 검증한다.

세 조건 모두 같은 LLM 모델·추론 설정·출력 한도·시스템 프롬프트·검증 규칙을 사용한다. 이번 실험에서는 모델 등급 비교까지 추가하지 않는다. 실행 모델은 `gpt-6-luna`, 추론 설정은 `low`, 최대 완료 토큰은 요청당 16,384, 서비스 등급은 기본값으로 고정했다. API 요청은 OpenAI Chat Completions의 구조화 JSON 출력을 사용한다.

문맥 구성 외의 조건을 고정하기 위해 호출은 단일 동시 요청으로 진행하고, 세 조건을 순환하며 실행한다. 각 조건은 우선 1회씩 수행하는 탐색 실험으로 한다.

## 3. 시스템 프롬프트

아래 삼중 따옴표 안의 **전체 문자열을 원문 그대로** 시스템 메시지에 사용한다. `##`, 목록 기호, 번호, 따옴표도 프롬프트 내용이다. 도입부 교체·요약·추가 문구 삽입은 하지 않는다. Python 변수 대입문과 삼중 따옴표 구분자 자체는 API에 보내는 문자열 내용이 아니다.

```python
SYSTEM_PROMPT = """당신은 회의 전사문에서 주제 경계를 검증하는 분석가입니다.
임베딩 유사도로 찾은 '경계 후보' 하나와 그 앞/뒤 발화가 주어집니다. 이 후보가 실제 주제 경계인지 판정하세요.

## 경계 기준
- 주제 = 하나의 결론(결정·보류·이관)을 목표로 하는 논의(안건) 단위
- 주제 경계 = 논의 대상, 즉 "회의 참여자가 무엇에 대해 결론을 내리려 하는가?"가 바뀌는 지점
- 단어나 화제가 아니라 의미 단위(논의 대상)를 기준으로 판단

## 판단 순서
1. 앞 구간(경계 후보 이전)의 논의 대상을 한 문장으로 작성 (before_subject)
2. 뒤 구간(경계 후보 이후)의 논의 대상을 한 문장으로 작성 (after_subject)
3. 아래 판정 질문 3가지에 각각 답할 것 (checks)
   - subject_change (대상 변경): 뒤 구간이 앞 구간과 다른 대상(다른 기능, 문서, 이슈, 일정, 의사결정 건)을 다루는가?
   - closure_signal (종결 신호): 앞 구간이 결론(결정·보류)으로 정리되었거나, "다음 안건", "그건 그렇게 하고" 같은 전환 표현이 있는가?
   - independent_summary (독립 요약 가능성): 뒤 구간을 앞 구간 내용 없이 따로 요약해도 의미가 통하는가?
4. 아래 '경계 제외 기준'에 해당하는지 확인. 제외 기준은 판정 질문보다 우선할 것.
   - same_subject_aspect: 같은 대상 안에서 측면만 바뀌는 경우 (예: 같은 버튼 논의에서 개수 → 크기)
   - digression_return: 잡담 등으로 잠시 다른 이야기를 하다가 원래 논의 대상으로 돌아오는 경우
   - re_discussion: 같은 결정에 대한 재논의나 번복인 경우
5. shift_type을 선택할 것
   - 제외 기준에 해당하면 그 값(same_subject_aspect / digression_return / re_discussion)
   - 제외 기준에 해당하지 않고 판정 질문 중 하나라도 true이면 new_agenda
   - 그 외(판정 질문이 모두 false)는 no_shift
6. shift_result는 shift_type이 new_agenda일 때만 true, verdict는 shift_result가 true이면 "O", 아니면 "X"으로 표기
7. evidence에는 판정 근거를 2~3문장으로 쓰고, 근거가 된 발화 번호를 [번호] 형식으로 인용할 것

## 주의
- 주어진 문맥은 경계 후보 주변 일부임. 문맥 밖 내용은 절대 추측하지 말 것.
- "네.", "음.", "좋아요." 같은 맞장구만으로 경계를 판단하지 말 것. 단, 결론을 정리하는 맥락의 "좋아요", "그럼" 등은 종결 신호가 될 수 있음.
- 모든 출력은 한국어로 작성할 것."""
```

### 입력 구성 (v2: 예상 경계 O/X 판정)

LLM 입력은 세 가지뿐이다.

1. **시스템 메시지**: 위 `SYSTEM_PROMPT` 원문.
2. **청크 원문**: 조건별로 생성한 청크(미병합 또는 900/1,200자 병합 묶음)의 원문이다. 각 발화 앞에 시스템 프롬프트가 인용에 쓰는 `[발화 번호]`만 붙이고 한 줄에 하나씩 둔다. 청크 끝에 걸려 잘린 발화는 잘린 그대로 둔다. 청크 양 끝의 빈 줄 구분자 외에는 원문을 바꾸지 않는다.
3. **예상 경계**: 청크 안의 임베딩 후보마다 `- 후보 <ID>: [n-1] 다음, [n] 앞` 한 줄을 쓴다. `n`은 임베딩 후보 문자 위치에서 가장 가까운 발화 시작점이다(같은 거리면 뒤쪽). 후보 39개 중 36개는 문자 위치가 발화 중간에 있으므로 이 규칙으로 발화 사이 경계에 맞춘다. 이 규칙은 호출 전에 확정했다.

사용자 메시지 형식:

```
## 청크 원문
[1] 좋아요. 어
[2] 안녕하세요.
…
[30] 어, 요구 사항은 어, 문자 방송, 거치대, 소리 신

## 예상 경계
- 후보 0: [13] 다음, [14] 앞
```

요청 ID, UID, 문자 좌표, 경계 선택지, 출력 지시문은 넣지 않는다. 정답도 넣지 않는다.

### 출력 계약

LLM은 예상 경계를 후보로 두고 그 위치가 주제 경계인지 O/X만 판정한다. 위치는 보정하지 않는다. 응답은 구조화 JSON 스키마로 받는다. `judgments` 배열에 예상 경계마다 `candidate_id`, `before_subject`, `after_subject`, `checks`, `shift_type`, `shift_result`, `verdict`, `evidence`를 정확히 한 번 반환한다.

`position`은 응답에 받지 않고 로컬에서 예상 경계 `n`으로 채운다. 실험 후보 ID는 후보 집합에서 안정적인 0–38 정수다. 원래 `C####` ID와 문자 좌표는 `verification`에 보존한다.

시스템 프롬프트 문자열은 계획서 원문 그대로이며 실행 코드가 계획서에서 자동 추출한다. 시스템 프롬프트는 수정하지 않는다.

## 4. 실행 및 검증 절차

### 1단계: 호출 전 점검

- TS3003c 입력·정답·후보 파일의 해시를 기존 명세와 대조한다.
- 세 조건의 문맥 묶음 수 39·26·16개를 재현한다.
- 모든 청크에서 다음을 확인한다.
  - `[번호]`가 연속되며 해당 발화의 원문(가장자리는 잘린 일부)과 일치한다.
  - 청크 원문이 묶음 원문과 같다(양 끝 줄바꿈 제외).
  - 각 예상 경계의 `[n-1]`과 `[n]`이 청크 안에 있다.
  - 각 조건에서 후보 39개가 정확히 한 번씩 나온다.
- 예상 경계로 도달할 수 있는 정답 수(재현율 상한)를 계산한다. 정확 일치는 2/11([28], [49]), ±3 이내는 8/11이다.
- LLM 모델 ID, 지원하는 생성 설정, 출력 한도, 단가를 고정한다.
- 토큰 기준 전체 예상 비용을 계산하고 기존 총예산 30,000원 안에서 실행 가능한지 확인한다.

### 2단계: 실제 API 호출

- 각 요청의 전송 내용·원응답·응답 모델 ID·사용량·소요 시간을 즉시 저장한다.
- 조건별 독립 호출을 수행한다. 다른 조건의 응답을 복사하지 않는다.
- 중단 후에는 동일한 요청·모델·설정·프롬프트의 완료 응답만 재사용한다.
- 일시적인 통신·서버 오류는 최대 2회 재시도하며 추가 호출·비용을 기록한다.
- 형식 오류·출력 잘림은 실패로 남긴다. 정답을 보면서 프롬프트나 응답을 수정하지 않는다.

### 3단계: 응답 검증

- 요청 안의 후보 ID가 모두 정확히 한 번 판정되었는지 확인한다.
- `checks`, `shift_type`, `shift_result`, `verdict`가 제공한 판정 규칙과 일치하는지 확인한다. `no_shift`는 세 질문이 모두 false여야 한다.
- 근거에 청크 안의 발화 번호가 1개 이상 인용되었는지 확인한다. 입력에 인용 개수 지시가 없으므로 골든의 2개 이상 규칙 대신 1개 이상을 적용한다. `[uNNNN]` 형식도 같은 번호로 인정한다. 범위 표기 `[81-89]`도 인정하며, 이때 양 끝 번호가 청크 안에 있어야 한다. 범위 인정은 v2 실행 후 사용자 결정으로 추가한 사후 규칙이다.
- 필수 필드 누락·중복 ID·잘못된 자료형을 검사한다.
- 잘못된 응답은 임의로 보정하지 않고 오류로 기록한다.

### 4단계: 회의 전체 경계 통합

- O로 판정된 예상 경계 위치를 합친다.
- 같은 위치는 한 경계로 중복 제거하고 지지 후보 ID를 보존한다.
- 서로 다른 위치는 가깝다는 이유만으로 병합하지 않는다.
- 같은 위치가 O/X로 갈리면 충돌을 기록한다. 유효한 O가 하나 이상이면 채택하는 규칙을 세 조건에 동일하게 적용한다.
- 채택한 경계를 원문 순서로 정렬하고 주제별 연속 구간을 만든다.
- 구간을 연결했을 때 본문과 정확히 일치하는지 확인한다.

처리 실패 요청이 남으면 결과를 부분 완료로 표시한다.

## 5. 평가와 조건 선택

### 정확도

정답 `boundary_positions`의 11개 경계와 비교한다.

#### 결과 저장 양식 (`test/llm_golden` 준수)

조건별 결과는 `results/<조건>/TS3003c.json`에 저장한다. 조건은 `baseline`, `merge_900`, `merge_1200`이다. 파일 이름과 구조는 `test/llm_golden/TS3003c.json`과 같게 한다.

- 최상위 키와 순서: `meeting_id`, `created_date`, `annotation_basis`, `source_transcript`, `utterance_mapping_source`, `utterance_count`, `position_definition`, `annotation_scope`, `segment_note`, `verification_note`, `boundary_positions`, `segments`, `candidates`. 그 밖의 최상위 키(실험 설정·점수)는 넣지 않는다.
- 경로는 골든과 같이 `test/` 기준으로 적는다: `input/TS3003c.txt`, `meetings/TS3003c.json`. 실행 전 점검에서 입력 발화가 `meetings/TS3003c.json`의 `uid`·`text_ko`와 일치하는지 확인한다.
- 설명 필드는 한국어로 쓴다. `annotation_scope`에 조건, 모델, 임베딩, 목표 윈도우 200자, 오버랩 100자, depth 기준을 명시한다.
- `candidates`의 키와 순서는 골든과 같다: `candidate_id`, `position`, `before_subject`, `after_subject`, `checks`, `shift_type`, `shift_result`, `verdict`, `evidence`, `verification`.
- `position`은 골든 정의대로 새 구간의 첫 발화이며, LLM에 제시한 예상 경계 `n`이다. 현재 39개 후보의 예상 경계는 모두 다르다. 그래도 같은 `position`에 놓인 판정이 생기면 한 후보로 합친다. 유효한 O가 하나라도 있으면 O로 채택한다. 대표 필드는 채택 판정 중 실험 후보 ID가 가장 작은 판정에서 가져온다. 이후 `position` 오름차순으로 `candidate_id`를 0부터 다시 매긴다.
- `verification`은 골든의 `checked: true`와 `rule` 문자열을 따른다. 규칙 문자열은 new_agenda, 제외 기준, no_shift 분기별로 골든과 동일하다. 그 밖에 합쳐진 원래 판정 전체(`judgments`: 실험 후보 ID, 원래 `C####` ID, 요청 ID, 후보 문자 좌표, verdict, shift_type)와 O/X 충돌 여부(`conflict`)를 추가로 보존한다. 정답 검증 내용은 복사하지 않는다.
- `boundary_positions`는 O 후보 `position`의 오름차순 목록이다.
- `segments`는 골든 키 순서(`start_utterance`, `subject`, `summary`, `segment_id`, `end_utterance`, `excluded_candidate_positions`)를 따른다. `subject`는 시작 경계 후보의 `after_subject`이고, 첫 구간은 첫 경계의 `before_subject`를 쓴다. LLM에 구간 요약을 요청하지 않으므로 `summary`에는 요약을 생성하지 않았다는 사실과 시작 경계 근거만 적는다. `excluded_candidate_positions`는 구간 안에 있는 X 후보의 `position`이다.
- 저장 전에 `test/llm_golden/validate.ps1`의 구조 검사를 같은 규칙으로 수행한다. 검사 항목은 후보 순서, 판정 규칙, 근거 인용, 경계 목록과 O 후보의 일치, 구간 연결, 제외 후보 연결이다. 근거 인용만 골든의 2개 이상 대신 1개 이상을 검사한다.
- 알고리즘 후보 39개의 요청별 판정 원본은 `results/<조건>/candidate_judgments.json`에 그대로 둔다. 조건별 설정·점수·충돌 위치는 `evaluation.json`에 기록한다.

위치는 임베딩 후보에서 정해지고 LLM은 O/X만 판정한다. 따라서 위치 대응 규칙(가장 가까운 발화 시작점)을 호출 전에 확정했다. 결과를 정확한 발화 ID 추출 성능으로 표현하지 않는다.

- 주 지표: ±3발화 허용 기준 Precision·Recall·F1. 재현율 상한은 8/11(72.7%)이다.
- 참고 지표: 정확한 발화 일치 기준 Precision·Recall·F1. 재현율 상한은 2/11(18.2%)이다.
- 정답·예측은 일대일로 대응시킨다.
- 누락·과분할·요청 간 판정 충돌을 분리한다.

오류 요청을 조용히 제외하지 않는다. 부분 결과의 지표에는 처리 실패가 있다는 사실을 함께 표시한다.

### 호출·비용·시간

- 기본 호출 수와 재시도 횟수.
- 입력·출력·추론·캐시 토큰 중 API가 제공하는 항목.
- 실제 사용량과 확인한 단가로 계산한 비용.
- 전체 처리 시간과 요청당 지연.
- 형식 오류·출력 잘림·실패 비율.

문자 수 감소를 비용 감소로 대신 해석하지 않는다. 사용량을 확인할 수 없는 실패 호출은 비용 0원으로 처리하지 않는다.

### 선택 기준

1. 처리 실패 없이 완료된 조건끼리 비교한다.
2. ±3발화 기준 재현율을 우선한다.
3. 재현율이 같으면 정밀도가 높은 조건을 선택한다.
4. 정확도가 같으면 비용이 낮은 조건, 이후 호출 수·처리 시간 순으로 선택한다.

병합 조건에서 미병합이 찾은 정답을 놓치면 해당 사례를 별도 검토한다. 호출 수가 줄었다는 이유만으로 병합 조건을 채택하지 않는다.
