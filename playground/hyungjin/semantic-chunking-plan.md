# 로컬 Semantic Chunking Web 실험 도구 개발 계획서

작성일: 2026-10-21 | 작성 기준: 제공된 손그림 기획 1쪽 및 현재 01~03번 실험 노트북

## 1. 목적과 개발 범위

노트북 셀을 순서대로 실행하는 대신, 로컬 브라우저에서 회의를 선택하고 설정을 바꾸며 청킹 결과를 읽을 수 있는 도구를 만든다. 현재 01~03번 노트북의 분석 함수를 재사용한다. 입력 파일, 중간 결과와 최종 JSON은 사용자 PC에 저장한다.

사용 형태는 **개인 PC의 Python 프로세스 1개 + 브라우저 화면 1개**다. Python 분석 코드를 바로 연결하기 위해 Streamlit을 사용한다. 주소는 `127.0.0.1`로 제한하고 별도 프런트엔드 서버나 데이터베이스 없이 실행한다. OpenAI·Gemini를 선택한 분석에는 기존과 같이 외부 모델 API를 사용하므로, 로컬 Web UI가 완전한 오프라인 분석을 뜻하지는 않는다.

핵심 흐름은 다음과 같다.

`회의 전사문 → 문자 길이 기준 오버랩 윈도우 → 임베딩 → 경계 후보 선택 → 후보별 LLM 검증 → 주제별 전문·근거 열람 → JSON 저장`

이번 단계의 완료 결과는 한 명이 로컬에서 여러 설정을 바꿔 실험하고, 생성된 주제 구간과 근거를 확인할 수 있는 화면이다. 로그인, 다중 사용자, 서버 배포, 작업 큐와 운영 DB는 만들지 않는다. 회의 요약과 액션 추출도 이번 청킹 도구의 범위 밖이다.

### 현재 구현과 추가 작업

| 구분 | 현재 확인한 내용 | 이번 계획의 추가 작업 |
|---|---|---|
| 입력 | 한국어 TXT 전사문 20개, 파일·문자열 입력 | 회의 목록 선택, TXT 업로드, 기본 DOCX 본문 입력 |
| 윈도우 | 문자 길이 기반 분할, 크기·오버랩 조절 | UI 입력과 유효성 검사 연결 |
| 임베딩 | Hugging Face·OpenAI·Gemini 선택 코드 | 모델 선택 UI와 실행 정보 표시 |
| 경계 후보 | 임계값·분위수·Top-K·국소 최저점·depth | 방법 선택, 점수 그래프, 후보 위치 표시 |
| LLM 검증 | 후보 중심 좌우 문맥, keep/reject/uncertain | 요청 문맥과 판단 근거를 나란히 열람 |
| 최종 결과 | 주제별 전문 JSON과 노트북 읽기 화면 | 브라우저의 전문 읽기 화면, JSON 다운로드와 로컬 저장 |

현재 저장된 완료 실행 1건에서는 후보 4개를 검토해 2개를 유지하고 2개를 기각했으며, 전사문이 3개 구간으로 나뉘었다. 이는 실행 사례이며, 모델 정확도나 일반화 성능을 검증한 결과는 아니다. 다중 모델의 전체 실험과 Gemini 실호출 검증은 별도 수행 항목이다.

## 2. 분석 파이프라인과 설정

### 2.1 입력과 원문 기준

- 회의 목록에서 기존 TXT를 선택하거나 TXT/DOCX를 입력한다. 기본 DOCX 지원은 본문 문단을 대상으로 한다. 표·이미지가 있는 문서는 지원 범위를 알리고, 내용을 조용히 누락하지 않는다. OCR은 후속 범위다.
- UTF-8 BOM을 제거하고 줄바꿈을 LF로 통일한다. 이 정규화된 텍스트를 `source.txt`로 저장한다.
- 회의 머리말이 있으면 제목·참석자·일시를 별도 메타데이터로 보관한다. 알 수 없는 값은 비워 두며 추정해서 채우지 않는다.
- 원문 파일 해시와 정규화된 텍스트 해시를 기록한다. 문자 좌표는 `source.txt` 기준이며 끝 위치를 포함하지 않는다.
- 원문 발화·문단 위치는 추적용으로 보존한다. 짧은 응답을 삭제하거나, 발화 수로 윈도우 크기를 정하지 않는다.

### 2.2 문자 길이 기준 슬라이딩 윈도우

| 설정 | 기준값 | 제약과 의미 |
|---|---:|---|
| 윈도우 크기 | 500자 | 양의 정수, 공백·줄바꿈 포함 |
| 오버랩 | 100자 | 0 이상, 윈도우 크기 미만 |
| 이동 간격 | 400자 | 윈도우 크기 - 오버랩 |
| LLM 왼쪽 문맥 | 400자 | 1~400자, 후보 앞 원문 |
| LLM 오른쪽 문맥 | 400자 | 1~400자, 후보 뒤 원문 |

마지막 윈도우는 남은 텍스트를 포함하며 짧아질 수 있다. 문자 크기를 일정하게 유지하므로 문장이나 발화 중간에서 잘릴 수 있다. 문자 수는 모델 토큰 수와 다르며, 임베딩·LLM 입력 한도는 별도로 확인한다.

### 2.3 임베딩 생성

현재 선택 가능한 경로는 Hugging Face의 `BAAI/bge-m3`, OpenAI의 `text-embedding-3-small`, Google의 `gemini-embedding-001`이다. 모델 선택은 동일한 원문·윈도우·후보 선택 조건으로 비교한다.

윈도우의 전체 텍스트를 직접 임베딩하고 L2 정규화한다. 모델·공급자·차원·실행 시간·사용량과 윈도우 좌표를 저장한다. 서로 다른 모델의 벡터를 직접 내적하지 않는다. 기존 Gemini 경로의 블록당 1,800 UTF-8 바이트 제한은 실험 코드의 보수적 제한이므로, 문자·토큰 한도와 구분해 표시한다.

### 2.4 유사도 기반 경계 후보

인접 윈도우 벡터의 코사인 유사도를 계산한다. 후보 대표 위치는 두 윈도우의 겹침 구간 가운데로 잡고, 원문 문자 좌표와 겹침 범위를 함께 저장한다. 이 위치는 의미 경계의 추정 위치다.

| 방법 | 선택 기준 | 주요 설정 |
|---|---|---|
| threshold | 고정 유사도 이하 | 유사도 임계값 |
| quantile | 유사도 하위 분위수 | 선택 분위수 |
| top_k | 낮은 유사도 순으로 최대 K개 | K |
| local_minima | 주변보다 낮은 국소 골짜기 | 분위수, 최소 후보 간격 |
| depth | 국소 골짜기 중 하락 깊이가 큰 곳 | 주변 범위, 최소 depth |

`depth = (왼쪽 주변 최대 유사도 - 현재 유사도) + (오른쪽 주변 최대 유사도 - 현재 유사도)`

depth는 확률이 아니다. 후보 사이와 본문 양 끝의 최소 간격도 문자 수로 제한한다. 모든 점수가 평평하거나 조건을 만족하지 않으면 후보 0개를 허용한다. 후보가 없는 상태를 자동으로 ‘전체가 한 주제’라고 해석하지 않는다.

### 2.5 후보별 LLM 검증

각 후보 `p`에 대해 `source[p-left:p] | 후보 | source[p:p+right]`를 제공한다. 좌우 길이는 독립적으로 조정하되 각각 최대 400자를 넘지 않으며, API 호출 직전에도 실제 문자열 길이를 검사한다. 본문 양 끝에서는 가능한 범위만 사용하고 실제 제공 길이를 표시한다.

시스템 프롬프트는 별도 편집 영역으로 둔다. OpenAI 호환 라우터의 base_url·모델·키 환경변수를 함께 선택한다. 기본 연결은 OpenAI와 Gemini이며, 그림의 Claude는 호환 경로를 확인한 후 추가할 확장 후보로 둔다.

- `keep`: 해당 후보 위치를 유지한다.
- `reject`: 후보를 기각한다.
- `uncertain`: 문맥 부족 또는 모호함을 표시한다. 기각과 구분해 남긴다.

판단 이유·모델 confidence·좌우 원문 인용을 저장한다. confidence는 검증된 확률로 표시하지 않는다. 인용 비교는 연속 공백·줄바꿈·탭 및 유니코드 NFC 차이를 허용하되, 다른 문구를 같은 인용으로 인정하지 않는다. 원문 자체와 문자 좌표는 변경하지 않는다.

현재 방식은 후보의 유지 여부만 판단한다. 경계가 문장 중간에 있으면 그 사실을 표시하며 자동 이동하지 않는다. 더 정확한 발화 경계로 옮기는 기능은 별도 실험으로 분리한다.

## 3. Web UI 구성과 사용 흐름

손그림의 설정 영역과 결과 영역을 다음과 같이 구현한다.

| 영역 | 화면에 제공할 내용 |
|---|---|
| 회의 선택 | 기존 회의 목록, TXT/DOCX 입력, 제목·일시·참석자, 입력 미리보기 |
| 윈도우 설정 | 크기·오버랩, 계산된 이동 간격, 예상 윈도우 수 |
| 모델·후보 설정 | 임베딩 모델, 후보 선택 방법과 설정, 검증 LLM, 좌우 문맥 길이 |
| 실행 상태 | 전처리·임베딩·후보 탐색·LLM 검증 진행, 완료 후보 수, 실패 사유 |
| A. 후보 문맥 | 후보 ID·위치·유사도·depth, 실제 LLM에 제공한 왼쪽/오른쪽 전문 |
| B. 경계 판단 | keep/reject/uncertain, 이유, 좌우 인용, 미검토 후보 |
| C. 주제별 전문 | 주제 번호, 각 구간 전사문 전체, 일부 범위 여부, 경계 근거 |
| JSON 저장 | `회의이름_사용된모델` 이름으로 내보내기, 최종 결과에는 임베딩·LLM 두 모델 모두 표기 |

사용 순서는 ‘회의 선택 → 설정 → 실행 → 후보·근거 확인 → 주제별 전문 읽기 → JSON 저장’이다. 후보 목록에서 항목을 선택하면 A와 B가 같은 후보를 보여준다. 주제별 전문은 긴 텍스트를 생략하지 않고 줄바꿈을 유지해 표시한다. 제목은 우선 ‘주제 1, 주제 2’ 같은 번호형이며, 내용 요약과 의미 제목 생성은 이번 필수 범위에서 제외한다.

### 상태와 재실행

- 모든 후보 검토가 끝나고 보류가 없을 때 주제별 결과를 완성한다.
- 보류·부분 실행·오류가 있으면 해당 상태와 원문을 보여주고 완성 결과로 표시하지 않는다.
- 선택한 입력이 전체 회의의 일부라면 그 범위를 명시한다.
- 후보·문맥·프롬프트·모델·엔드포인트가 같을 때만 저장된 원본 응답을 재검증해 사용한다. 없는 응답만 새로 호출한다.
- 임베딩 설정 변경은 임베딩부터, 후보 방식 변경은 저장된 임베딩부터, LLM 설정 변경은 후보 검증부터 실행한다.
- API 키는 서버의 `.env` 또는 환경변수로만 읽고 브라우저·JSON·로그에 기록하지 않는다.

### 로컬 구현 구조

```text
브라우저(localhost)
    ↓
app.py - Streamlit 설정 화면·실행 버튼·결과 열람
    ↓
pipeline.py - 기존 노트북에서 분리한 분석·검증·저장 함수
    ├─ 로컬 Hugging Face 모델
    ├─ OpenAI / Gemini API
    └─ outputs/ 아래 실행별 로컬 파일
```

| 파일·위치 | 역할 |
|---|---|
| `embedding-test/app.py` | 회의·설정 선택, 단계별 실행, 결과 화면 |
| `embedding-test/pipeline.py` | 전처리, 윈도우, 임베딩, 후보 선택, LLM 검증, JSON 생성 |
| `embedding-test/outputs/` | 기존 결과를 포함한 실행별 산출물 |
| 루트 `pyproject.toml` | 기존 통합 환경에 Streamlit·DOCX 입력 의존성 추가 |
| `embedding-test/test_pipeline.py` | 원문 보존·길이 상한·응답 검증·재사용 조건 검사 |

기존 노트북은 실험 기록으로 유지하고 Web은 분리된 Python 함수를 직접 호출한다. 실행 시 노트북 파일을 읽어 `exec`하는 구조는 사용하지 않는다. 최초 함수 분리에서는 현재 동작을 유지하고, UI 연결과 알고리즘 개선을 한 번에 섞지 않는다.

구현 후 `remeet` 폴더에서 실행할 명령은 다음과 같다. 아래 파일은 이번 계획 단계에서는 아직 생성하지 않았다.

```powershell
uv run streamlit run playground/hyungjin/embedding-test/app.py --server.address 127.0.0.1
```

화면은 왼쪽 설정 패널과 오른쪽 결과 영역으로 구성한다. 결과 영역은 `주제별 전문 / 후보 검토 / 유사도 그래프 / JSON` 탭으로 나눈다. 기본 탭은 사용자가 전문을 바로 읽을 수 있는 `주제별 전문`으로 한다.

Streamlit은 화면 조작에 따라 코드를 재실행할 수 있으므로, 모델 호출은 실행 버튼을 누른 경우에만 수행한다. 설정 입력은 form으로 묶고, 선택한 회의·실행 결과는 세션 상태에 보관한다. 후보 선택이나 결과 탭 이동으로 임베딩·LLM을 다시 호출하지 않는다. 로컬 모델은 모델명·장치 기준으로 재사용하고, API 응답은 기존 파일 재사용 조건을 적용한다.

## 4. 결과 JSON과 저장 계약

현재 `topic_transcript.json`의 사용자용 구조를 유지하고, 그림의 메타데이터·전사문·경계 이유를 포함하는 통합 결과 JSON을 추가한다. 두 파일은 같은 실행 결과에서 생성하며, Web 도구에서 새로 저장하는 파일명에는 아래 규칙을 적용한다. 기존 노트북의 저장 파일은 변경하지 않는다.

### 저장 폴더·파일명 규칙

기본 이름은 **`회의이름_사용된모델`**로 한다. 최종 결과는 **`회의이름_임베딩모델_LLM모델`** 순서로 두 모델 이름을 모두 포함한다. 모델명은 실제 실행에 사용한 ID를 기준으로 하며, `small`이나 `gemini`처럼 모호한 별칭으로 줄이지 않는다.

| 산출물 | 이름 규칙 | 예시 |
|---|---|---|
| 임베딩 결과 폴더 | `회의이름_임베딩모델` | `리모컨회의_BAAI-bge-m3` |
| 후보 결과 JSON | `회의이름_임베딩모델_candidates.json` | `리모컨회의_BAAI-bge-m3_candidates.json` |
| 최종 통합 JSON | `회의이름_임베딩모델_LLM모델.json` | `리모컨회의_BAAI-bge-m3_gpt-4.1-mini.json` |
| 주제별 전문 JSON | `회의이름_임베딩모델_LLM모델_topics.json` | `리모컨회의_BAAI-bge-m3_gpt-4.1-mini_topics.json` |

회의 이름은 회의 제목을 우선 사용하고, 제목이 없으면 입력 파일명에서 확장자를 제외한 이름을 사용한다. 둘 다 없으면 `m_id`를 사용한다. 파일명에 사용할 수 없는 문자와 경로 구분자는 `-`로 치환하고 끝의 공백·마침표를 제거한다. 예를 들어 모델 ID `BAAI/bge-m3`는 파일명에서 `BAAI-bge-m3`로 표시한다. JSON 메타데이터에는 치환 전의 전체 모델 ID를 그대로 보관한다.

동일 회의·모델로 여러 번 실행할 때도 이 기본 이름은 유지한다. 실행별로 다른 하위 폴더를 만들어 윈도우·프롬프트 등이 다른 결과가 덮어써지지 않게 한다.

```text
outputs/
  리모컨회의_BAAI-bge-m3_gpt-4.1-mini/
    <실행시각-고유ID>/
      리모컨회의_BAAI-bge-m3_gpt-4.1-mini.json
      리모컨회의_BAAI-bge-m3_gpt-4.1-mini_topics.json
```

Web의 저장 경로 표시와 JSON 다운로드 이름에 같은 규칙을 사용한다. 경로·파일명은 결과를 식별하는 표시이고, 응답 재사용 여부는 원문 해시·실제 모델 ID·설정으로 검증한다.

### 통합 결과의 필수 항목

| 항목 | 내용 |
|---|---|
| m_id | 회의 식별자, 실행 식별자와 구분 |
| meta | 제목, 참석자, 일시, 임베딩 모델·공급자, 검증 LLM·공급자 |
| config | 윈도우·오버랩, 후보 선택 방법·설정, 좌우 문맥, 프롬프트 버전 |
| transcript | 문자 좌표의 기준인 정규화된 전체 입력 텍스트 |
| analysis_scope | 실제 분석한 시작·끝 문자와 일부 입력 여부 |
| result.chunks | 주제 ID·번호형 제목·원문 전문·좌표·이전 구간과 나눈 이유 |
| result.boundary_reviews | 모든 후보의 위치·판정·이유·인용·검증 상태 |
| provenance | 실행 ID, 원문 해시, 처리 시간, 응답 재사용 여부 |
| status | complete / partial / needs_review / failed / no_candidates 등 |

첫 주제는 앞선 주제와의 경계가 없으므로 분할 이유를 `null`로 둔다. 이후 주제의 시작 근거는 해당 구간 앞 경계를 `keep`으로 판단한 이유를 연결한다. 후보 ID와 주제 ID는 별도 관리한다.

아래는 저장 구조를 설명하는 예시이며 실제 실험 결과가 아니다.

```json
{
  "m_id": "demo-meeting",
  "meta": {
    "title": "회의 예시",
    "members": [],
    "date": null,
    "embed_model": "BAAI/bge-m3",
    "llm_model": "gpt-4.1-mini"
  },
  "transcript": "안건 A를 검토합니다.\n\n다음 안건 B입니다.",
  "result": {
    "chunks": [
      {
        "chunk_id": "T001",
        "title": "주제 1",
        "transcript": "안건 A를 검토합니다.\n\n",
        "reason": null
      },
      {
        "chunk_id": "T002",
        "title": "주제 2",
        "transcript": "다음 안건 B입니다.",
        "reason": "새 안건 B에 대한 논의가 시작됨"
      }
    ]
  }
}
```

예시는 핵심 필드만 표시한 것이다. 실제 저장에는 위 표의 설정·좌표·상태·출처 정보를 함께 기록한다. 모든 chunk의 전문을 이어 붙인 결과는 `transcript[analysis_scope.start_char:analysis_scope.end_char]`와 정확히 같아야 한다. 원문 복원 검사에 실패하면 결과를 완성 상태로 저장하지 않는다.

## 5. 구현 순서와 완료 기준

### 예상 작업 순서

다음 순서로 작은 기능 단위를 완성한다. 일정은 정하지 않고, 각 단계가 실제로 동작하면 다음 단계로 넘어간다.

| 단계 | 작업 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 1. 함수 분리 | 기존 분석 함수를 `pipeline.py`로 옮기고 저장 결과 로딩 지원 | 기존 완료 결과를 추가 API 호출 없이 브라우저 연결용 데이터로 읽을 수 있음 |
| 2. 로컬 화면 | 회의·설정 선택, 실행 버튼, 후보·근거·전문 탭 연결 | 기존 TXT 한 건을 끝까지 처리하고 주제별 전문을 읽을 수 있음 |
| 3. 입력·저장 마무리 | TXT/DOCX 입력, JSON 다운로드, 중단·재사용·입력 검증 | 파일 선택부터 읽기·JSON 저장까지 한 화면에서 완료됨 |
| 4. 비교 실험 | 모델·후보 방법·문맥 설정을 바꿔 같은 도구로 실험 | 조건과 결과를 로컬 실행 기록으로 비교 가능 |

### 비교 실험

1. 공통 기준 500자/100자에서 임베딩 3경로와 후보 방법 5가지를 비교한다. 후보 방법 변경 시 임베딩을 다시 생성하지 않는다.
2. 유망 설정에 대해 윈도우 300·400·500자, 오버랩 50·100·150자로 민감도를 확인한다. 유효한 모델 입력 한도를 먼저 점검한다.
3. 같은 후보에서 OpenAI와 Gemini, 좌우 문맥 200/200·200/400·400/200·400/400자를 비교한다. 어느 쪽도 400자를 초과하지 않는다.
4. 설정 조정에 사용하지 않은 회의로 최종 평가한다. 기존 AMI 주제 라벨을 사용할 때는 목표 주제 단위와 번역 전사문의 문자 좌표가 맞는지 먼저 검토한다. 정답 라벨은 모델 입력에 넣지 않는다.

기록할 지표는 후보·최종 경계 수, 구간 길이 분포, 보류·실패율, 처리 시간, API 사용량·비용이다. 정답 경계가 준비되면 일대일 대응 기준의 precision/recall/F1과 엄격 일치·문자 오차 허용 결과를 함께 측정한다. 오차 허용 범위는 평가 전에 고정하고, 같은 정답 경계를 여러 후보가 중복 정답 처리하지 않게 한다. 현재 단계에서 검증되지 않은 정확도 목표를 약속하지 않는다.

### 기능 완료 기준

- 회의 선택부터 주제별 전문 열람과 JSON 저장까지 한 흐름으로 실행된다.
- 저장 이름은 `회의이름_사용된모델`을 따르고 최종 JSON에는 임베딩 모델과 LLM 모델이 모두 포함된다.
- 같은 회의·모델 조합의 재실행도 실행별 하위 폴더에 저장되어 이전 결과를 덮어쓰지 않는다.
- 명령 하나로 로컬 서버를 띄우고 브라우저에서 사용할 수 있다.
- 탭 이동·후보 선택·화면 새로고침만으로 모델 API를 재호출하지 않는다.
- 윈도우·오버랩은 문자 길이 기준이며 유효하지 않은 설정을 실행 전에 거부한다.
- 실제 LLM 요청의 좌우 원문은 각각 400자 이하이다.
- UI에서 실제 요청 문맥과 모델의 경계 이유·인용을 확인할 수 있다.
- 주제 전문이 원문을 누락·중복·요약하지 않고 분석 범위를 정확히 복원한다.
- 공백·줄바꿈 차이는 허용하고, 원문에 없는 인용·잘린 응답·실패를 성공 판정으로 바꾸지 않는다.
- 보류·일부 실행·후보 없음·API 실패를 완성된 주제 분할과 구분한다.
- 같은 설정의 응답은 재사용되며, 프롬프트나 문맥이 달라진 결과는 재사용하지 않는다.
- 키가 화면·결과 파일에 노출되지 않으며 기존 실행 결과가 새 실행으로 덮어써지지 않는다.

### 주요 제한과 대응

| 제한 | 대응 |
|---|---|
| 문자 윈도우가 발화 중간에서 잘림 | 원문 위치와 겹침 범위를 표시하고 정확한 경계 이동은 별도 실험 |
| 오버랩 때문에 전환의 유사도가 높아짐 | 같은 오버랩 조건에서 후보 방법을 비교하고 놓친 경계도 확인 |
| 좌우 400자만으로 판단이 어려움 | uncertain 유지, 자동 확정 금지 |
| API 제공자의 옵션·한도 차이 | 공급자별 설정과 오류 보존, 다른 모델로 자동 대체하지 않음 |
| 주제명과 메타데이터의 불확실성 | 번호형 주제명 사용, 없는 참석자·일시를 추정하지 않음 |
