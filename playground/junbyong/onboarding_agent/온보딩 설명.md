# onboarding_agent.py — 온보딩 질의 에이전트 (1차, 임시)

신입사원·이직자가 "무엇을 왜 결정했는지", "그동안 무엇을 했는지", "누구에게 물어야 하는지", "어떤 스킬이 필요한지"를 자연어로 물으면, Neo4j의 회의 기록을 근거로 답한다. 모든 답변 문장에는 근거(회의 안건·결정)가 달리고, 근거가 없으면 "관련 회의 기록이 없어요"라고 답한다.

`onboarding_agent_prompt.md`(전체 지시서)에서 범위를 줄인 1차 버전이다.

| 포함 | 제외 (2차 이후) |
| --- | --- |
| Decision 노드 적재 + SUPERSEDES 판정 | Term(용어) 추출·정합 |
| decision / history / action / overview / people / skill 질문 | my_work, 용어 설명 |
| 코드로 하는 grounding 검사 | CONTRIBUTED_TO, API, followups, ReviewTask 노드 |
| 유형별 2\~3문항 평가 | visibility 권한 정책 (지금은 전부 public) |

## 실행

저장소 루트 `.env`(`OPENAI_API_KEY`, `NEO4J_PASSWORD`)를 쓴다. `eunje/ontology/scripts/load.py`로 회의가 적재된 Neo4j가 켜져 있어야 한다.

```bash
python onboarding_agent.py --self-check                 # 가짜 DB·LLM으로 전체 검사 (Neo4j, API 키 불필요)
python onboarding_agent.py backfill                     # dry-run: DB에 쓰지 않고 결과만 출력
python onboarding_agent.py backfill --write             # Decision / SUPERSEDES 적재 (재실행해도 안전)
python onboarding_agent.py ask "결제 화면 어떻게 바꾸기로 했어요?"
python onboarding_agent.py eval --today 2026-11-12      # eval_questions.json으로 평가 → eval_result.json
```

`--today`는 "지난달" 같은 상대 날짜의 기준일이다. 기본값은 오늘(Asia/Seoul)이다. `--model`로 LLM 모델을 바꿀 수 있다 (기본은 `OPENAI_MODEL` / `LLM_MODEL`, 없으면 `gpt-5.5`).

## 파일 구성

```
onboarding_agent/
├─ onboarding_agent.py        backfill, ask 그래프, eval, self-check (한 파일)
├─ onboarding_agent_prompt.md 전체 구현 지시서 (원본)
├─ prompts/
│  ├─ supersede.md            새 결정이 앞선 결정을 대체하는지 판정
│  ├─ classify.md             질문 → intent, topic_ids, 기간
│  └─ compose.md              근거 → 문장별 source_ids가 달린 답변
├─ eval_questions.json        평가 질문 (decision 3, history 3, action 2, overview 2, people 2, skill 2, no_evidence 2)
└─ eval_result.json           평가 결과 (eval 실행 시 생성)
```

전체 과정은 **① backfill(지식 적재) → ② ask(질의 응답) → ③ eval(평가)** 순서다. ① 은 회의가 추가될 때 한 번 돌리면 되고, ② 는 질문마다 돈다.

## ① backfill: 회의 결정사항을 Decision 노드로 적재

`AgendaItem.decisions[]` 배열(요약 단계에서 이미 뽑힌 확정 결정)을 그래프 노드로 승격한다. 그래야 결정끼리 "대체됨(SUPERSEDES)" 관계를 걸 수 있고, 질문할 때 현재 유효한 결정만 골라낼 수 있다.

```
회의 시간순으로 AgendaItem 순회
  ├─ 이미 DECIDED가 있는 안건 → 건너뜀 (재실행 안전)
  └─ decisions[]의 각 항목
       1. Decision 생성: decision_id = {agenda_item_id}-d{순번}, status='active'
       2. 비교 후보 찾기: 같은 Topic 계열(상위·하위 Topic)의 앞선 active 결정 (같은 안건 것은 제외)
       3. 후보가 있으면 LLM 판정 (prompts/supersede.md): supersedes / complements / unrelated
            supersedes + confidence ≥ 0.7 → SUPERSEDES 관계, 이전 결정은 status='superseded'
            supersedes + confidence < 0.7 → HITL 후보 목록에만 출력 (DB 반영 안 함)
            LLM 호출 실패               → HITL 후보에 "판정 실패"로 기록하고 계속 진행
--write일 때만 한 트랜잭션으로 DB 저장 (MERGE라 중복 생성 없음)
```

- **시간순인 이유:** 앞선 결정이 먼저 있어야 나중 결정이 그것을 대체하는지 판정할 수 있다.
- **Topic 계열로 비교하는 이유:** 같은 이야기라도 회의마다 하위 안건(SUBTOPIC_OF)으로 나뉘어 있기 때문이다.
  - 예: "블프 프로모션 일정"(보류) ← 하위 → "블랙프라이데이 프로모션 재개"(재개)
- **LLM 판정 결과 검증:** 코드가 후보에 없는 ID와 정해지지 않은 relation을 버린다.

생성되는 그래프:

```
(AgendaItem)-[:DECIDED]->(Decision {decision_id, content, decided_at, status, confidence, verified_by:'auto'})
(Decision)-[:ABOUT]->(Topic)
(Decision)-[:SUPERSEDES {reason, confidence, detected_by:'auto'}]->(Decision)
```

기존 노드와 관계(`decisions[]` 배열, `RECOMMENDED_FOR` 등)는 건드리지 않는다.

## ② ask: 질문 → 근거 달린 답변 (LangGraph)

```
classify(LLM) → retrieve ─┬─▶ compose(LLM) → ground → END
                          └─▶ ground (근거 없음) ─────▶ END
```

LLM은 \*\*질문 해석(classify)과 문장화(compose)\*\*만 한다. 검색은 고정 Cypher 템플릿으로 하고, 근거 검사(ground)는 코드가 한다.

### 노드별 동작

| 노드 | LLM | 하는 일 |
| --- | --- | --- |
| `classify` | ✔ | 질문을 intent(`decision` / `history` / `action` / `overview` / `people` / `skill` / `other`), 관련 topic_ids, 기간(date_from / date_to)으로 해석한다. 코드가 없는 topic_id와 잘못된 날짜를 버린다. 실패하면 `other`로 처리 |
| `retrieve` |  | topic_ids를 Topic 계열(상위·하위)로 넓힌 뒤 intent에 맞는 템플릿으로 근거를 조회한다. 조건이 없으면 조회하지 않는다 |
| `compose` | ✔ | 근거(evidence)만으로 2\~5문장 답변을 만들고, 문장마다 근거의 `source_id`를 단다 |
| `ground` |  | 문장의 근거를 코드로 검사하고 최종 답변을 만든다 (아래 규칙) |

### retrieve 조회 조건

| intent | 조회하는 경우 | 템플릿 | 근거(source_id) |
| --- | --- | --- | --- |
| decision | topic_ids가 있을 때 | `DECISION_EVIDENCE`: Topic 계열의 Decision(active·superseded 모두) + 안건 배경·논의 + 대체한 결정 | `decision_id` |
| history | topic_ids 또는 기간이 있을 때 | `HISTORY_EVIDENCE`: 기간·Topic 안의 회의 안건을 시간순으로, 안건별 결정·액션아이템 포함 | `agenda_item_id` |
| action | 항상 (topic_ids가 없으면 전체 Topic, 예: "지금 누가 뭘 하고 있어요?") | `ACTION_EVIDENCE`: Topic 계열 안건의 액션아이템(마감일, 상태) + 확정 담당자(`ASSIGNED_TO`) + 담당자 추천 에이전트의 pending 추천(`RECOMMENDED_FOR`, 추천 이유, 후보 스킬) | `action_item_id` |
| overview | 항상 (topic_ids가 없으면 전체) | `OVERVIEW_EVIDENCE`: Topic별 상위 주제·상태·마지막 논의일 + 다룬 안건과 현재(active) 결정 | `topic_id` |
| people | 항상 (topic_ids가 없으면 재직자 전체) | `PEOPLE_EVIDENCE`: 재직자(`is_active`)의 팀·역할·스킬 + 그 주제 회의 참석(`ATTENDED`) 안건 + 그 주제 액션아이템 추천 후보 여부 | `user_id` |
| skill | 항상 (topic_ids가 없으면 전체) | `SKILL_EVIDENCE`: 스킬별 보유자(재직자, 팀·직급·레벨) + 보유자가 추천된 액션아이템과 추천 이유 | `skill_id` |
| other | 조회 안 함 | – | – |

- 근거가 하나도 없으면 compose(LLM)를 부르지 않고 바로 ground로 가서 `no_evidence`로 답한다.
- 모든 템플릿에 `coalesce(m.visibility, 'public') IN $visibility` 필터가 들어 있다.
- overview / people / skill 근거는 근거 회의를 `refs` 목록으로 갖는다. ground가 `refs`에서 `sources`(근거 회의)를 만든다. "디자인팀에는 누가 있어요?"처럼 회의와 무관한 답은 `sources`가 빈 채로 `grounded`일 수 있다.

### ground 규칙 (근거 검사)

1. **근거 없는 문장 제거:** `source_ids`가 비었거나, 조회한 근거에 없는 ID가 섞인 문장은 버린다.
2. **결정 분류:** 남은 문장이 인용한 결정을 현재 결정(`active`)과 변경 이력(`superseded`)으로 나눈다.
3. **변경 경고:** superseded 결정이 쓰였으면 코드가 "참고: 'A' 결정은 이후 'B'(으)로 변경됐어요." 문장을 붙인다.
4. **answer_status 결정:**

| answer_status | 조건 |
| --- | --- |
| `grounded` | 모든 문장에 근거가 있음 |
| `partial` | 일부 문장이 근거 없음으로 제거됨 |
| `no_evidence` | 남은 문장이 없음 → summary는 "관련 회의 기록이 없어요. 담당자에게 문의해 주세요." |
| `error` | 답변 생성(compose) LLM 호출 실패 |

### 출력 예시 (`ask`)

```json
{
  "question": "블프 프로모션은 왜 보류됐었고 지금은 어떻게 됐어요?",
  "intent": "decision",
  "slots": {"topic_ids": ["tp-m-1106-a2"], "date_from": null, "date_to": null},
  "answer_status": "grounded",
  "summary": "2026년 11월 6일 정기회의에서는 할인 예산이 확정되지 않아 ... 참고: '예산 확정 전까지 프로모션 진행을 보류' 결정은 이후 '프로모션 재개, 11/24 오픈'(으)로 변경됐어요.",
  "sentences": [{"text": "...", "source_ids": ["m-1106-a2-d1"]}],
  "current_decisions": [{"decision_id": "m-1110-a1-d1", "content": "프로모션 재개, 11/24 오픈", "status": "active", "decided_at": "..."}],
  "decision_history": [{"decision_id": "m-1106-a2-d1", "content": "예산 확정 전까지 프로모션 진행을 보류", "status": "superseded", "decided_at": "..."}],
  "sources": [{"meeting_id": "m-1106", "meeting_title": "...", "held_at": "...", "agenda_item_id": "m-1106-a2", "agenda_title": "블프 프로모션 일정"}],
  "warnings": []
}
```

- `sources`는 화면의 근거 칩, `sentences[].source_ids`는 문장별 근거 표시에 쓴다.
- 질문은 `eval_questions.json`에 있는 것만이 아니라 아무거나 할 수 있다. 다만 지금 잘 답하는 것은 위 6개 유형이다.

### 질문 유형 (신입·이직자 관점)

| intent | 신입이 묻는 말 |
| --- | --- |
| overview | "이 프로젝트는 어떤 주제들을 다루고 있어요?", "결제 쪽 업무는 전체적으로 어떤 일들이 있어요?" |
| decision | "결제 화면은 어떻게 바꾸기로 했어요?" |

| people | "PG사 교체 건은 누구한테 물어보면 돼요?", "디자인팀에는 누가 있어요?" |
| skill | "신입사원이 갖춰야 할 스킬은?", "결제 업무에는 어떤 역량이 필요해요?" |

## ③ eval: 평가

`eval_questions.json`의 질문마다 ask를 돌려서, 미리 적어 둔 정답 근거(`expected_agenda_ids`)와 비교한다.

| 지표 | 계산 |
| --- | --- |
| `intent_acc` | 예측 intent가 질문의 기대 intent와 같은 비율 |
| `recall` | 정답 안건 중 답변 `sources`에 인용된 비율 |
| `no_evidence_acc` | "근거 없음이어야 하는 질문"을 맞게 판단한 비율 |
| `superseded_ok` | 변경된 결정을 다루는 질문(D2)에서 `decision_history`가 채워졌는지 |

질문의 `group`은 집계 단위(intent별 + no_evidence)이고, `intent`는 기대하는 분류 결과다. no_evidence 질문("복지 포인트 정책은 어떻게 정했어요?")은 기대 intent가 decision이다. 결정을 묻는 질문인데 관련 기록이 없는 경우이기 때문이다.

### 결과 (2026-11-03, 로컬 Neo4j + 실제 LLM, `--today 2026-11-03`)

| 그룹 | 문항 | intent_acc | recall | no_evidence_acc |
| --- | --- | --- | --- | --- |
| decision | 3 | 1.0 | 1.0 | 1.0 |
| history | 3 | 1.0 | 0.83 | 1.0 |
| action | 2 | 1.0 | 1.0 | 1.0 |
| overview | 2 | 1.0 | 1.0 | 1.0 |
| people | 2 | 1.0 | 1.0 | 1.0 |
| skill | 2 | 1.0 | 1.0 | 1.0 |
| no_evidence | 2 | 1.0 | – | 1.0 |

- history 0.83은 H3에서 LLM이 m-1106-a1을 인용하지 않은 경우다. 코드 경로는 그대로이고, 다시 실행하면 1.0이 나온다 (LLM 답변 편차).
- 첫 skill 실행에서 S1("신입사원이 갖춰야 할 스킬")이 junior가 가진 스킬만으로 좁혀졌다. compose에 "신입이 이미 가진 스킬로 좁히지 않는다" 규칙을 넣어 고쳤다.

- 첫 실행에서 H1("10월에 … 결정했어요?")이 decision으로 분류됐다. classify 프롬프트에 "기간이 있으면 history" 규칙을 추가해 고쳤다.
- 문항이 16개뿐인 임시 평가라 점수 자체보다 실패 사례를 찾는 용도로 본다.

## 테스트

- **self-check** (`--self-check`): 아래 경우를 assert로 확인한다.
  - backfill: 시간순 처리, dry-run이면 쓰지 않음, SUPERSEDES 생성, 낮은 confidence는 HITL, 없는 ID는 버림, 재실행 시 새로 쓰는 것 없음
  - ask: 없는 topic_id 제거와 Topic 계열 조회, 근거 없는 문장 제거(`partial`), superseded 경고, history 기간 전달, people은 refs로 출처 생성, skill은 주제 없으면 전체 조회, 근거 없으면 compose를 부르지 않고 `no_evidence`
- **실제 DB backfill**
  - Decision 9개(active 8, superseded 1), SUPERSEDES 1건("프로모션 보류 → 재개")
  - "원인 파악 → 원인 확정"처럼 이어지는 결정은 complements로 판정돼 active로 남음
  - 다시 실행하면 새로 적재할 결정이 0건이고, 담당자 추천의 `RECOMMENDED_FOR` 13개는 그대로

## 알아둘 점

- **답변 범위:** Neo4j에 적재된 회의 5건(10/23\~11/10) 안에서만 답한다.
- **담당자 질문(action):** 회의에서 말한 담당자(`actions[].owner`, 예: 10/23 "김결제")는 `load.py`의 `assign_owner`가 주석 처리돼 있어 DB에 없다. 그래서 지금은 "담당자 미확정 + 추천 후보"로 답한다. `ASSIGNED_TO`가 생기면 확정 담당자로 답한다.
- **스킬 질문(skill):** DB에 액션아이템별 "필요 스킬" 속성이 없다. 그래서 재직자의 보유 스킬(`HAS_SKILL`, 지금 7건)과 추천 이유로 답한다. 회사가 정한 필수 스킬 목록은 아니다.
- **사람 질문(people):** `CONTRIBUTED_TO`(발언·기여 기록)가 없어 "주제 관련자"를 회의 참석과 추천 후보 여부로 판단한다. 참석만 한 사람도 나올 수 있다 (코드에 `shortcut` 주석). 퇴사자(`is_active=false`)는 제외한다.
- **Decision 추출:** LLM 추출 대신 `decisions[]` 배열을 그대로 쓴다. 요약 단계에서 결정이 빠지면 여기서도 빠진다.
- **visibility:** 회의에 값이 아직 없어 전부 public으로 처리한다 (코드에 `shortcut` 주석).
- **중복 안내:** 변경된 결정은 LLM 문장과 코드 경고가 "변경됨"을 두 번 말할 수 있다.
- **HITL:** HITL 후보는 backfill 결과에 출력만 되고, 저장하는 큐는 아직 없다.
- **프롬프트 형식:** `prompts/*.md`는 LLM에 그대로 들어가는 텍스트다. Markdown 미리보기 편집기로 저장하면 `[`가 `\[`로 바뀔 수 있으니 일반 텍스트로 편집한다.
