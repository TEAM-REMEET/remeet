# 온보딩 에이전트 통합 사용설명서

신입사원·이직자가 회의 기록에 대해 자연어로 물으면, Neo4j에 적재된 회의 데이터를 근거로 답하는 에이전트다.
"무엇을 왜 정했는지", "그동안 뭘 했는지", "누가 맡았는지", "누구에게 물어야 하는지", "어떤 스킬이 필요한지" 같은 질문을 받는다.

- 모든 답변 문장에 근거(결정·안건·할 일 ID)가 달린다. 문장마다 회의록 원문 발화까지 따라갈 수 있다.
- 근거가 없으면 지어내지 않고 "관련 회의 기록이 없어요. 담당자에게 문의해 주세요."라고 답한다.
- 코드는 `onboarding_agent.py` 한 파일이다. `onboarding_agent_prompt.md`(전체 지시서)에서 범위를 줄인 1차 버전이다.

| 포함 | 제외 (2차 이후) |
| --- | --- |
| 결정(Decision) 노드 적재 + 대체(SUPERSEDES) 판정 | 용어(Term) 추출·설명 |
| decision / history / action / overview / people / skill 질문 | "내 업무" 질문(my_work) |
| 코드로 하는 근거 검사, 원문 발화 연결 | 발언·기여 기록(CONTRIBUTED_TO), API 서버, 검토 큐(HITL) 저장 |
| 웹 화면용 출력 (배지·결정 이력·문의 대상·후속 질문·원문) | 열람 권한(visibility) 정책 — 지금은 전부 공개 |

## 1. 준비 (처음 한 번)

### ① `.env` 두 곳에 값 넣기

| 파일 | 읽는 쪽 | 넣을 값 |
| --- | --- | --- |
| `playground/eunje/ontology/.env` | Neo4j 컨테이너, `load.py`, `recommend_agent.py` | `NEO4J_PASSWORD` |
| 저장소 루트 `.env` | `onboarding_agent.py` | `OPENAI_API_KEY`, `NEO4J_PASSWORD`(위와 같은 값) |

저장소 루트 `.env` 예:

```
OPENAI_API_KEY=sk-...
NEO4J_PASSWORD=...           # ontology/.env와 같은 값
# 선택 (생략하면 아래 기본값)
NEO4J_URI=bolt://localhost:7687
NEO4J_USERNAME=neo4j
```

### ② Neo4j 켜기

1. Docker Desktop을 켠다. 이 PC에서는 `C:\Users\jwnsq\AppData\Local\Programs\DockerDesktop\Docker Desktop.exe`에 설치돼 있다.
2. 컨테이너를 켠다. 자동 재시작 설정이 없어서, PC나 Docker를 다시 켤 때마다 해야 한다.
   ```bash
   docker start ontology-neo4j-1
   ```
3. 20초쯤 뒤 브라우저에서 `http://localhost:7474`가 열리면 정상이다. 로그인은 사용자 `neo4j`, 비밀번호는 `.env`의 `NEO4J_PASSWORD`다.

- 컨테이너에는 APOC 플러그인이 설치돼 있어야 한다. skill 질문 쿼리가 APOC 함수를 쓴다.
- 예전 문서의 `docker compose -p ontology up -d`는 `playground/eunje/ontology`에 compose 파일이 없어져서 지금은 동작하지 않는다. 컨테이너를 새로 만들어야 하면 은제 님 ontology 설정을 따른다.

### ③ 데이터 적재 (순서대로, DB가 비어 있을 때만)

```bash
# playground/eunje/ontology 에서
uv run python scripts/load.py --reset --effort low   # 회의·안건·논의·할 일·사람·스킬 적재 (--reset은 기존 회의 데이터 삭제)
uv run python scripts/recommend_agent.py            # 담당자 추천(RECOMMENDED_FOR). action·skill 질문에 필요

# playground/junbyong/onboarding_agent 에서
python onboarding_agent.py backfill                 # dry-run: 적재될 결정을 미리 확인
python onboarding_agent.py backfill --write         # Decision / SUPERSEDES 적재. decision 질문에 필요
```

- `backfill --write`는 여러 번 돌려도 안전하다. 이미 처리한 안건은 건너뛴다. 회의가 새로 적재되면 다시 돌린다.
- `load.py --reset`은 Decision·예전 Person 등 일부 노드를 남긴다. 예전 구조를 완전히 지우려면 Neo4j 브라우저에서 `MATCH (n) DETACH DELETE n` 후 다시 적재한다. DB 전체가 지워지므로 주의한다.

### ④ 동작 확인

```bash
python onboarding_agent.py --self-check     # Neo4j·API 키 없이 로직만 검사
```

Windows에서 한글이 깨지면 먼저 `PYTHONUTF8=1`을 설정한다. PowerShell에서는 `$env:PYTHONUTF8=1`.

## 2. 질문하기

```bash
cd playground/junbyong/onboarding_agent
python onboarding_agent.py ask "음성 인식 기능은 왜 빠졌어요?"
python onboarding_agent.py ask "거치대 관련 논의는 지금까지 어떻게 진행돼 왔어요?"
python onboarding_agent.py ask "회의록은 누가 올리기로 했어요?" > result.json   # 길면 파일로
```

| 옵션 | 뜻 |
| --- | --- |
| `--today YYYY-MM-DD` | "지난달", "이번 주" 같은 상대 날짜의 기준일. 생략하면 오늘(Asia/Seoul) |
| `--model`, `--effort` | 시험용. 기본은 `gpt-6-luna`, reasoning_effort `low`로 코드에 고정(`LLM_MODEL`, `LLM_EFFORT`). `.env`의 `LLM_MODEL`은 보지 않는다. effort는 none / low / medium / high / xhigh |

### 물어볼 수 있는 질문

질문은 자유롭게 하면 된다. 에이전트가 6가지 유형 중 하나로 분류해서 정해진 범위의 데이터를 찾는다.

| 유형 | 이런 걸 물을 때 | 예시 |
| --- | --- | --- |
| overview | 프로젝트·업무 전체 그림 | "이 프로젝트는 어떤 주제들을 다루고 있어요?", "리모컨 소재와 외관 쪽은 전체적으로 어떤 일들이 있어요?" |
| decision | 무엇을 왜 정했는지, 정해진 사실 | "음성 인식 기능은 왜 빠졌어요?", "지금까지 정해진 것들 정리해 줄래요?", "타깃 고객은 누구예요?" |
| history | 주제·회의별 진행 과정, 미결 사항, 다음 회의 | "1차 회의에서는 뭘 했어요?", "아직 결정 안 된 게 뭐예요?", "다음 회의에서는 뭘 다뤄요?" |
| action | 할 일의 담당자·마감·상태 | "회의록은 누가 올리기로 했어요?", "케이스 색상 비용 조사는 누가 맡아요?" |
| people | 누구에게 물어봐야 하는지, 팀 구성 | "버튼이랑 화면 인터페이스 관련해서는 누구한테 물어보면 돼요?", "산업 디자인팀에는 누가 있어요?" |
| skill | 필요한 스킬·역량 | "신입사원이 갖춰야 할 스킬은?", "인터페이스 설계 업무에는 어떤 역량이 필요해요?" |

위 유형에 안 맞거나 회의 기록과 무관한 질문("점심 뭐 먹지?")은 `other`로 분류된다. 이 경우 DB를 조회하지 않고 "기록 없음"으로 답한다.

**잘 답하는 질문의 요령**

- 주제어를 넣으면 정확해진다. 예: "버튼", "케이스 소재", "거치대", "자막 기능".
- 주제를 잘못 짚어도 한 번은 전체 회의에서 다시 찾는다. 이때 `warnings`에 안내가 붙는다.
- 날짜 대신 회의로 묻는다. 예: "1차 회의", "킥오프", "마지막 회의", "상세 설계 회의". 지금 데이터는 회의 4건의 날짜가 모두 같다.
- 회의 기록에 없는 내용(사내 복지 등)은 "관련 회의 기록이 없어요"로 답한다. 지어내지 않는다.

### 필드 설명과 웹 화면 연결

| 필드 | 뜻 | 웹 화면 |
| --- | --- | --- |
| `summary` | 사람이 읽는 최종 답변 (2~5문장, 400자 안쪽) | 답변 본문 |
| `answer_status` | `grounded` 모든 문장에 근거 있음 / `partial` 근거 없는 문장을 뺌 / `no_evidence` 기록 없음 / `error` LLM 호출 실패 | 상태 표시 |
| `intent`, `slots` | 에이전트가 분류한 질문 유형과 조건(주제·회의·기간) | 디버깅용 |
| `sentences[].source_ids` | 문장별 근거 ID (결정·안건·할 일·사람·스킬) | 문장별 근거 표시 |
| `sentences[].citations` | 문장별 원문 근거 최대 2개. `tags`(결정/제안/반대·우려/할 일), `point`(논의 한 줄 요약), `utterances`(발화 번호) | 각주 → 원문 이동 (`/meetings/{meeting_id}#u{번호}`) |
| `transcripts` | 인용된 발화 원문만 회의별로. `{회의ID: [{i, speaker, role, text}]}` | "원문 보기" 펼치기 |
| `badge` | `status`(active/superseded), `confidence`(인용 결정 중 최저값), `verified_by`(전부 사람 확인이면 human, 아니면 auto). 결정이 없는 답이면 null | 상단 배지 "현재 유효한 결정 · 신뢰도" |
| `decision_timeline` | 답변 문장이 실제로 말한 결정(결정 내용의 2글자 조각 30% 이상이 문장에 있을 때)만 + 회의 이름·회의 차수(`meeting_order`)·안건 번호(`agenda_no`)·대체 관계(`superseded_by`), 회의 순서로 정렬 | 결정 이력 |
| `current_decisions` / `decision_history` | 현재 유효한 결정 / 이후 바뀐 결정 (예전 형식, eval이 사용) | – |
| `sources` | 근거가 된 회의·안건 목록 (`meeting_order`, `agenda_no` 포함) | 근거 회의 · 안건 N |
| `contacts` | 더 물어볼 사람 최대 2명. 이름·직급·역할·이유(`why`) | 더 물어보려면 |
| `follow_ups` | 이어서 물을 만한 질문 최대 2개. 미결 사항·다음 회의 주제로 만든다 | 이어서 물어보기 |
| `warnings` | 근거 없는 문장을 뺐거나, 전체 회의로 다시 찾았거나, 조회·원문 읽기에 실패한 경우 안내 | 안내 문구 |

- 바뀐 결정을 인용하면 답변 끝에 "참고: 'A' 결정은 이후 'B'(으)로 변경됐어요."가 코드로 자동으로 붙는다.
- 원문의 앞뒤 맥락은 `transcripts`에 없다. 웹이 원문 파일(`playground/eunje/ontology/data/summary_action/{회의ID}/{회의ID}_summary.json`의 `transcript`)을 직접 읽어 보여주면 된다.
- 발화 번호는 회의마다 1부터 다시 센다. 항상 `meeting_id`와 함께 쓴다.

## 4. 동작 방식

전체 과정은 **① backfill(결정 적재) → ② ask(질의 응답) → ③ eval(평가)** 순서다.
①은 회의가 추가될 때 한 번 돌리면 되고, ②는 질문마다 돈다.

### 기준 DB (eunje/ontology `load.py`)

```
(Topic)-[:IN]->(Project)            (Meeting)-[:IN]->(Project)        (Person)-[:ATTENDED]->(Meeting)
(Meeting)-[:HAS_AGENDA]->(Agenda)-[:ABOUT]->(Topic)
(Agenda)-[:HAS_DISCUSSION]->(Discussion)-[:PRODUCED]->(ActionItem)
(Person)-[:MEMBER_OF]->(Team) / [:HAS_ROLE]->(Role) / [:HAS_SKILL {level}]->(Skill)
(Person)-[:RECOMMENDED_FOR {status:'pending', reason, total, ...}]->(ActionItem)   ← 담당자 추천 에이전트
(Agenda)-[:DECIDED]->(Decision)-[:ABOUT]->(Topic), (Decision)-[:SUPERSEDES]->(Decision)  ← 이 에이전트의 backfill
```

| 노드 | 이 에이전트가 쓰는 속성 |
| --- | --- |
| Agenda | `agenda_id`, `title`, `background[]`, `decisions[]`, `unresolved_issues[]`, `next_topics[]` |
| Discussion | `discussion_id`, `title`(소주제), `discussions[]`("[제안][결정] 문장"), `evidence[]`(문장마다 발화 번호 "109,110,121") |
| ActionItem | `action_item_id`, `description`, `status`, `due`(원문 그대로), `owner_raw`(회의에서 말한 담당자, 예: "프로젝트 매니저") |
| Decision | `decision_id`, `content`, `status`(active/superseded), `confidence`, `verified_by` |

DB 밖에서 읽는 파일이 하나 있다. 발화 원문은 Neo4j에 없어서, 요약 파이프라인 결과 파일 `summary_action/{회의ID}/{회의ID}_summary.json`에서 읽는다.

지금 데이터는 TS3003 "Real Reaction 신제품 TV 리모컨 개발 프로젝트" 회의 4건(TS3003a~d)이다.

| 노드 | 개수 |
| --- | --- |
| Agenda / Discussion / ActionItem | 16 / 47 / 14 |
| Topic | 8 |
| Decision | 27 (모두 active) |
| Person / Team / Role / Skill | 48 / 4 / 12 / 38 |

### ask 그래프 (LangGraph)

```
classify(LLM) → retrieve ─┬─▶ compose(LLM) ─┬─▶ ground → cite → END
                          │                 └─▶ widen ─▶ compose …   (답이 안 나오면)
                          ├─▶ widen ─▶ compose / ground              (근거가 비면)
                          └─▶ ground (근거 없음) → cite → END
```

LLM은 **질문 해석(classify)과 문장 만들기(compose)**만 한다. 검색은 고정 Cypher 템플릿으로 하고, 근거 검사(ground)와 원문 연결(cite)은 코드가 한다. LLM이 Cypher를 만들지 않는다(Text2Cypher 아님).

| 단계 | LLM | 하는 일 |
| --- | --- | --- |
| `classify` | ✔ | 질문을 intent(`decision`/`history`/`action`/`overview`/`people`/`skill`/`other`), 관련 주제(topic_ids, 최대 4개), 회의(meeting_ids: "1차 회의", "킥오프", "마지막 회의"), 기간(date_from/date_to)으로 바꾼다. DB에 없는 주제·회의 ID와 잘못된 날짜는 코드가 버린다. 실패하면 `other`로 처리한다 |
| `retrieve` |  | intent에 맞는 템플릿으로 근거를 조회한다 (아래 표) |
| `widen` |  | 고른 주제에서 근거가 비거나 답이 안 나오면, 주제 제한 없이 **한 번만** 다시 조회한다. `warnings`에 "질문한 주제에서 못 찾아 전체 회의에서 다시 찾았어요."가 붙는다 |
| `compose` | ✔ | 근거만으로 2~5문장 답변을 만들고 문장마다 `source_id`를 단다. 같은 호출에서 문의 대상(`contacts`)과 후속 질문(`follow_ups`)도 고른다. 문의 대상 후보는 호출 전에 Cypher로 가져온다 |
| `ground` |  | 문장의 근거를 코드로 검사하고 답변·배지·결정 이력·출처를 만든다 |
| `cite` |  | 문장마다 원문 근거(`citations`)를 붙이고 인용된 발화를 `transcripts`에 담는다 |

**widen이 필요한 이유:** classify는 주제 이름만 보고 고르기 때문에 엇나갈 수 있다. 예를 들어 "음성 인식 기능은 왜 빠졌어요?"는 "리모컨 기능 아이디어" 주제로 분류되지만, 실제 결정은 "버튼 및 화면 인터페이스" 주제의 3차 회의 안건에 있다.

### retrieve: intent별 조회 범위

| intent | 조회 조건 | 템플릿과 가져오는 것 | 근거 ID |
| --- | --- | --- | --- |
| decision | 항상. 주제가 없으면 전체 (예: "지금까지 정해진 것들") | `DECISION_EVIDENCE`: 결정(active·superseded) + 안건 배경·논의·미결 사항 + 대체한 결정. 최대 40개 | `decision_id` |
| history | 항상. 주제·회의·기간이 없으면 전체. **회의를 지정하면 주제로 좁히지 않고 그 회의 안건 전체** | `HISTORY_EVIDENCE`: 안건을 회의 순서대로. 결정·소주제·할 일·미결 사항(`unresolved_issues`)·다음 회의 주제(`next_topics`). 최대 30개 | `agenda_id` |
| action | 항상. 주제가 없으면 전체 | `ACTION_EVIDENCE`: 할 일(마감 원문, 상태, 회의에서 말한 담당자 `owner_raw`, 소주제) + 확정 담당자(`ASSIGNED_TO`) + 추천 후보(이유·스킬). 최대 20개 | `action_item_id` |
| overview | 항상. 주제가 없으면 전체 | `OVERVIEW_EVIDENCE`: 주제별 프로젝트·상태·마지막 논의일 + 다룬 안건과 현재 결정 | `topic_id` |
| people | 항상. 주제가 없으면 재직자 전체 | `PEOPLE_EVIDENCE`: 재직자의 팀·역할·스킬 + 그 주제 회의 참석 안건 + 그 주제 할 일 추천 후보 여부. 최대 30명 | `user_id` |
| skill | 항상. 주제가 없으면 전체 | `SKILL_EVIDENCE`: 스킬별 보유자(팀·직급·레벨) + 그 스킬이 쓰이는 할 일. 할 일마다 총점 1순위 후보의 추천 이유 하나만, 스킬당 5개, 스킬 20개까지 | `skill_id` |
| other | 조회 안 함 | – | – |

- 근거가 하나도 없고 widen도 할 수 없으면 compose(LLM)를 부르지 않고 바로 `no_evidence`로 답한다.
- overview / people / skill 근거는 근거 회의를 `refs` 목록으로 갖는다. ground가 `refs`에서 `sources`를 만든다. "산업 디자인팀에는 누가 있어요?"처럼 회의와 무관한 답은 `sources`가 빈 채로 `grounded`일 수 있다.
- 모든 템플릿에 `coalesce(m.visibility, 'public') IN $visibility` 필터가 있다. 지금은 전부 public이다.

### ground: 근거 검사 규칙

1. **근거 없는 문장 제거:** `source_ids`가 비었거나 조회한 근거에 없는 ID가 섞인 문장은 버린다.
2. **결정 분류:** 남은 문장이 **내용을 실제로 말한** 결정만 골라 현재 결정(active)과 변경 이력(superseded)으로 나눈다. 안건만 인용한 답("1차 회의 주제는 …")에 그 안건 결정이 전부 딸려 나오거나, LLM이 엉뚱한 결정 ID를 단 경우를 막는다. 결정을 말하지 않은 답은 `badge`가 null, `decision_timeline`이 빈 목록이다.
3. **변경 경고:** superseded 결정이 쓰였으면 코드가 "참고: … 변경됐어요." 문장을 붙인다.
4. **문의 대상·후속 질문 검증:** 후보 목록에 없는 사람과 근거 ID가 확인되지 않는 후속 질문은 버린다. 근거 안건에 할 일이 없는 사람(참석만 한 사람)을 "담당"이라고 쓰면 "참석"으로 바꾼다. 답이 `no_evidence`면 둘 다 비운다.
5. **answer_status 결정:**

| answer_status | 조건 |
| --- | --- |
| `grounded` | 모든 문장에 근거가 있음 |
| `partial` | 일부 문장을 근거 없음으로 제거함 |
| `no_evidence` | 남은 문장이 없음 → summary는 "관련 회의 기록이 없어요. 담당자에게 문의해 주세요." |
| `error` | 답변 생성(compose) LLM 호출 실패 |

### cite: 원문 연결 규칙

1. 문장의 근거 안건에 속한 논의 문장(Discussion의 `discussions[i]`와 발화 번호 `evidence[i]`) 중, 답변 문장과 글자(2글자 단위)가 많이 겹치는 것을 고른다. **인용한 안건마다 1개씩은 꼭** 넣고, 합쳐서 2개가 안 되면 다음 순위로 채운다. 그래서 여러 안건을 인용한 문장은 citations가 2개보다 많을 수 있다.
2. 할 일 문장이면 그 할 일 자체의 발화를 먼저 붙인다(`tags: ["할 일"]`). 할 일만 있는 논의 노드는 DB에 발화 번호가 없어서, 원문 파일에서 할 일 ID로 찾는다.
3. 논의 문장 앞의 `[제안][결정]` 태그는 떼서 `tags`로 옮긴다.
4. 인용된 발화 번호만 원문 파일에서 읽어 `transcripts`에 담는다. 파일이 없거나 읽기에 실패해도 답변은 그대로 나오고 `warnings`에 "○○ 원문을 읽지 못했어요"가 붙는다.

### 호출 수와 시간 (2026-11-05 측정, eval 22문항)

- **LLM 호출은 질문당 보통 2번**(classify 1번 + compose 1번)이다. 22문항에서 총 46번이었다.
  - 회의와 무관한 질문(`other`)은 1번이다.
  - widen 뒤 답변을 다시 만들면 3번이다(22문항 중 2문항).
  - 실패하면 호출마다 1번 다시 시도한다(`max_retries=1`).
- **시간:** LLM은 질문당 3~9초다(classify 평균 2.1초, compose 평균 3.4초). 프로그램 시작에 라이브러리 로딩으로 약 4초가 더 든다.
- **Neo4j 조회**는 쿼리당 11~59 ms로, 전체 시간의 1% 미만이다.
- **입력 토큰:** classify는 평균 약 1,300, compose는 평균 약 8,700이다. 가장 큰 질문은 "신입이 갖춰야 할 스킬"로 약 2만 5천이다.

## 5. 결정 적재 (backfill)

`Agenda.decisions[]` 배열(요약 단계에서 "결정"으로 뽑힌 항목)을 Decision 노드로 바꾼다. 그래야 결정끼리 "대체됨(SUPERSEDES)" 관계를 걸 수 있고, 질문할 때 현재 유효한 결정만 골라낼 수 있다.

```
회의 순서(held_at, 같으면 agenda_id)로 Agenda 순회
  ├─ 이미 DECIDED가 있는 안건 → 건너뜀 (재실행 안전)
  └─ decisions[]의 각 항목
       1. Decision 생성: decision_id = {agenda_id}-d{순번}, status='active', verified_by='auto'
       2. 비교 후보: 같은 주제의 앞선 active 결정 (같은 안건 것은 제외)
       3. 후보가 있으면 LLM 판정 (prompts/supersede.md): supersedes / complements / unrelated
            supersedes + confidence ≥ 0.7 → SUPERSEDES 관계, 이전 결정은 status='superseded'
            supersedes + confidence < 0.7 → HITL 후보 목록에만 출력 (DB 반영 안 함)
            LLM 호출 실패                → HITL 후보에 "판정 실패"로 기록하고 계속 진행
--write일 때만 한 트랜잭션으로 저장 (MERGE라 중복 생성 없음)
```

- **회의 순서대로 처리하는 이유:** 앞선 결정이 먼저 있어야 나중 결정이 그것을 대체하는지 판정할 수 있다.
- **LLM 판정 검증:** 후보에 없는 ID와 정해지지 않은 relation은 코드가 버린다.
- **주제 계열(`lineage`):** 상위·하위 주제까지 넓히는 코드가 남아 있다. 지금 DB에는 `SUBTOPIC_OF`가 없어서 같은 주제만 비교한다.
- 기존 노드와 관계(`decisions[]` 배열, `RECOMMENDED_FOR` 등)는 건드리지 않는다.
- **TS3003 결과:**
  - Decision 27개, SUPERSEDES 0건이다. 이어지는 결정(예: "LCD 채택" → "스크롤 휠 사용")은 대체가 아니라 구체화로 판정됐다.
  - 다시 실행하면 새로 적재할 결정이 0건이다.

## 6. 평가와 테스트

### eval

```bash
python onboarding_agent.py eval     # eval_questions.json 22문항 → eval_result.json
```

질문마다 ask를 돌려서, 미리 적어 둔 정답 안건(`expected_agenda_ids`)과 비교한다.
`eval_questions.json`은 에이전트가 답할 수 있는 질문 목록이 아니라 **채점용 시험지**다. 실제 질문은 아무거나 할 수 있다.

| 지표 | 계산 |
| --- | --- |
| `intent_acc` | 예측한 유형이 기대 유형과 같은 비율 |
| `recall` | 정답 안건 중 답변 `sources`에 인용된 비율 |
| `no_evidence_acc` | "기록 없음이어야 하는 질문"을 맞게 판단한 비율 |
| `superseded_ok` | `expect_superseded` 질문에서 `decision_history`가 채워졌는지 (지금 데이터에는 해당 문항 없음) |

질문을 추가하려면 같은 형식으로 넣는다.

```json
{"id": "P3", "intent": "people", "question": "질문",
 "expected_agenda_ids": ["정답 안건 ID"], "expect_no_evidence": false}
```

**최근 결과** (2026-11-05, 로컬 Neo4j(TS3003) + gpt-6-luna / low)

| 그룹 | 문항 | intent_acc | recall | no_evidence_acc |
| --- | --- | --- | --- | --- |
| decision | 5 | 1.0 | 1.0 | 1.0 |
| history | 7 | 1.0 | 1.0 | 1.0 |
| action | 2 | 1.0 | 0.67 | 1.0 |
| overview | 2 | 1.0 | 1.0 | 1.0 |
| people | 2 | 1.0 | 1.0 | 1.0 |
| skill | 2 | 1.0 | 1.0 | 1.0 |
| no_evidence | 2 | 1.0 | – | 1.0 |

- **A1("회의록은 누가 올리기로 했어요?")은 실행마다 결과가 흔들린다(recall 0~1).** 같은 질문을 3번 돌리면 1번쯤 다른 할 일을 인용한다. 프롬프트를 바꾸기 전에도 같았고, effort low에서 생기는 불안정으로 본다.
- **no_evidence 그룹의 intent_acc**는 복지 질문이 `other`로 분류되면 0.5로 떨어진다(실행마다 다름). 어느 쪽이든 답은 맞게 "기록 없음"이다.
- 문항이 22개뿐인 임시 평가라, 점수보다 실패 사례를 찾는 용도로 본다.
- **지금까지 eval에서 찾아 고친 것:**
  - D3가 주제를 잘못 골라 `no_evidence`였던 것은 widen을 넣어 고쳤다.
  - 신입 질문 15개 점검에서 5개가 `no_evidence`였다. 회의 지정, 주제 없는 질문의 전체 조회, 다음 회의 주제를 넣어 고쳤다.
  - 답변이 최대 609자까지 나오던 것을 400자 안쪽으로 줄였다.
- 위 결과는 스킬 쿼리 축소, 원문 연결(cite), 2026-11-05 수정(안건별 원문 근거, 결정 이력 조건, 회의 지정 시 전체 조회, 결정 날짜, "담당" 표현 교정)을 모두 넣은 뒤 돌린 것이다.

### self-check

```bash
python onboarding_agent.py --self-check
```

가짜 DB·LLM으로 아래를 assert로 확인한다. Neo4j와 API 키가 없어도 돈다.

- **backfill:** 회의 순서 처리, dry-run은 쓰지 않음, SUPERSEDES 생성, 낮은 confidence는 HITL, 없는 ID는 버림, 재실행하면 새로 쓰는 것 없음
- **ask:**
  - 없는 주제·회의 ID 제거와 주제 계열 조회
  - 근거 없는 문장 제거(`partial`), superseded 경고, 기간·회의 조건 전달
  - people·skill 출처 생성, 주제 오분류 시 전체 재조회(widen), 근거 없으면 compose 생략
- **웹 화면용 출력:**
  - 배지, 결정 이력 정렬
  - 후보에 없는 문의 대상과 근거 없는 후속 질문 제거
  - 원문 근거 선택, 태그 분리, 할 일 발화 연결, 원문 파일이 없을 때 경고만

## 7. 문제 해결

| 증상 | 확인할 것 |
| --- | --- |
| `OPENAI_API_KEY와 NEO4J_PASSWORD 설정이 필요합니다` | 저장소 루트 `.env` |
| `ServiceUnavailable` / 연결 거부(10061) | Docker Desktop이 켜져 있는지, `docker start ontology-neo4j-1`을 했는지 (`docker ps -a`에서 `Exited`면 꺼진 것) |
| `failed to connect to the docker API` | Docker Desktop 자체가 꺼져 있음. 먼저 Docker Desktop을 켠다 |
| `AuthError` / 인증 실패 | 두 `.env`의 `NEO4J_PASSWORD`가 같은지. Neo4j 비밀번호는 볼륨을 처음 만들 때 고정된다 |
| skill 질문만 오류 (`apoc` 관련) | 컨테이너에 APOC 플러그인이 있는지 |
| decision 질문이 전부 "기록 없음" | `backfill --write`를 돌렸는지 |
| 담당자가 늘 "미확정 + 회의 언급 + 추천 후보" | 정상. 확정 담당자(`ASSIGNED_TO`)가 DB에 아직 없다 |
| action·skill 답에 추천 후보가 안 나옴 | `recommend_agent.py`를 돌렸는지 (`load.py --reset` 후에는 추천이 지워진다) |
| `warnings`에 "○○ 원문을 읽지 못했어요" | `playground/eunje/ontology/data/summary_action/{회의ID}/{회의ID}_summary.json`이 있는지 |
| 한글이 깨짐 (Windows) | `PYTHONUTF8=1` 설정 후 실행 |
| 파일 실행 시 `ImportError` 등 이상한 문법 오류 | 에디터에서 한글 입력 상태로 잘못 눌린 글자가 없는지 (예: `datetime헷`) |
| 프롬프트 수정 후 이상한 답 | `prompts/*.md`를 Markdown 미리보기 편집기로 저장하면 `[`가 `\[`로 바뀌거나 줄이 합쳐질 수 있다. 일반 텍스트로 편집한다 |

## 8. 한계와 알아둘 점

**답변 범위**
- 적재된 TS3003 회의 4건 안에서만 답한다. 일반 상식으로 채우지 않는다.
- 회의 4건의 날짜가 같아서 기간 질문("10월에")은 구분이 안 된다. 회의로 물어야 한다.
- 데이터는 DB에 있는데 꺼내는 쿼리가 없는 질문이 있다. 예: "2차 회의에 누가 참석했어요?"는 답하지 못한다.

**유형별 한계**
- **action:** 확정 담당자(`ASSIGNED_TO`)가 아직 없다. 회의에서 말한 담당자 원문(`owner_raw`, 대부분 "프로젝트 매니저" 같은 역할)과 추천 후보로 답한다.
- **skill:**
  - 할 일별 "필요 스킬"이 DB에 따로 없다. 재직자 보유 스킬과 추천 이유로 답한다. 회사가 정한 필수 스킬 목록은 아니다.
  - 범위가 넓은 질문은 스킬 20개, 스킬당 할 일 5개까지만 본다.
  - 제대로 하려면 담당자 추천 에이전트가 할 일 → 스킬 관계를 저장해야 한다.
- **people / contacts:** 발언·기여 기록(`CONTRIBUTED_TO`)이 없어 회의 참석과 추천 후보 여부로 판단한다. 참석만 한 사람도 나올 수 있다. 퇴사자(`is_active=false`)는 제외한다.

**웹 화면용 출력의 한계**
- **"대체됨" 이력:** SUPERSEDES가 0건이라 지금은 모든 결정이 "유효"로만 나온다.
- **"HITL 검증됨":** 모든 결정이 `verified_by='auto'`, `confidence=1.0`이다. 사람이 검증한 결과를 기록하는 단계가 생기기 전에는 화면에 "자동 추출"로 표시해야 맞다.
- **원문 연결:** 글자 겹침으로 고르는 방식이라, 표현이 많이 다르면 같은 안건의 엉뚱한 논의가 붙을 수 있다. 원문은 은제 님 폴더의 파일 경로에 의존한다(`TRANSCRIPT_DIR`).

**비용과 기타**
- **주제 없는 질문:** "지금까지 정해진 것"이나 기록에 없는 질문은 전체 결정·안건을 LLM에 넘긴다. 회의가 많아지면 LIMIT에 걸려 일부만 보인다.
- **widen 비용:** 주제를 잘못 고른 질문은 답변 생성을 한 번 더 부른다. 답이 없는 질문(N2 등)은 이 때문에 토큰을 두 배로 쓴다.
- **Decision 추출:** LLM 추출 대신 `decisions[]` 배열을 그대로 쓴다. 요약 단계에서 빠진 결정은 여기서도 빠진다.
- **HITL:** HITL 후보는 backfill 결과에 출력만 된다. 저장하는 큐는 아직 없다.
- **visibility:** 회의에 값이 없어 전부 public으로 처리한다(코드에 `shortcut` 주석).

├─ eval_questions.json          평가 질문 22개 (TS3003 기준)
